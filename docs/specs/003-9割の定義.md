# 「AI が 9 割描けた」を何で測るか（Issue 003 / D3）

- 実装: `src/measure.ts` / `pnpm measure <図> ...`
- 基準線: `experiments/s3/results/baseline.md`（`pnpm s3` で再生成）
- 基準の図: `experiments/s3/fixtures/`（**実在の構成から起こした 2 枚**）

---

## 1. なぜ要るか

**この数字が無いと、出来上がりが従来の作図ソフトと同じでも気づけない。**

機能が増えるほど「使える」ようには見える。だが人が図形を並べ直しているなら、
それは高機能な作図ソフトであって、この企画ではない。

---

## 2. 測るもの — 2 つだけ

| 指標 | 数え方 | 合格 |
|---|---|---|
| **自力率** | 1 −（人が触った要素 ÷ 全要素） | **90% 以上** |
| **配置の自力率** | 1 −（人が幾何を決めた要素 ÷ 全要素） | **90% 以上** |

- 全要素 = ノード数 + エッジ数（**図は箱だけではない**）
- 「人が触った」= `pins` に `position` / `size` / `waypoints` / `label` / `appearance` がある
- 「人が幾何を決めた」= `position` / `size` / `waypoints` がある

### なぜ 2 つに分けるか

**この企画が壊れる形は「人が図形を並べ直す」だから。**
ラベルを 1 つ直すのは 1 割の範囲だが、**配置の直しが増えたら作図ソフトに戻っている。**
1 本にまとめると、この 2 つが打ち消し合って見えなくなる。

### 数えないもの

- **人の作業時間。** 測っているのは製品であって人ではない（Issue 003 の注意）
- **迷子の pin。** 居ない要素の手直しは、率を押し上げるだけで図の状態を表さない
- **`locked` だけの pin。** 競合を解いた記録であって、直しではない

---

## 3. なぜ別のログを取らないか

**人の手直しは `pins` にしか書かれない**（仕様 §3.4。AI は `pins` を書かない）。
だから**正本 1 つを見れば、人がどれだけ手を入れたかが分かる。**

計測を別に仕込む必要が無い。これは横着ではなく、
**「後から足した計測は、都合の良い数字が出た日だけ記録される」を構造的に防ぐ**ため
（Issue 003 の作業内容 1）。正本があれば、いつでも遡って測り直せる。

---

## 4. 基準の図

**実在の構成を使う。架空の綺麗な例で測らない。**

| 図 | 何か | 大きさ |
|---|---|---|
| `zumen-modules.zumen.yaml` | zumen 自身のモジュール構成（`src/*.ts` の import を読んで起こした） | 11 ノード / 18 エッジ |
| `md-business-packages.zumen.yaml` | md-business のパッケージ構成（`package.json` の依存を読んで起こした） | 15 ノード / 47 エッジ |

大きさを変えた 2 枚を置いたのは、**規模で指標が壊れないか**を見るため。

---

## 5. 現状値（2026-09-06）

**この時点で数字が良いことに意味は無い。**
意味があるのは、**後から下がっていないことを確かめられる**こと。

### 正直な現状 — S1 の往復は、8 回中 3 回が合格ラインを割っている

| | 自力率 | 判定 |
|---|---|---|
| R0 | 100.0% | OK |
| R1 | 94.7% | OK |
| R2 | 90.9% | OK |
| **R3 / R4 / R5** | **85.0%** | **NG** |
| REAL-1 | 94.7% | OK |
| REAL-2 | 95.7% | OK |

**指標を甘くして通すことはしない。**
S1 が測ったのは「手直しが**壊れないか**」であって「手直しが**少ないか**」ではないので、
S1 の Go 判定と矛盾はしない。**別のことを測っている。**

この 85.0% が意味するのは、**20 要素の図で人が 3 か所直した**ということ。
これを「9 割描けている」と呼ぶかどうかは、**合格ラインの置き方の問題**であり、
いまは原案の掲げる 9 割をそのまま線にしてある。

### 悪化することの確認

| | 自力率 |
|---|---|
| zumen-modules（手直し前） | 100.0% |
| zumen-modules（**全部を手で並べ直した**） | **62.1%** |
| md-business-packages（手直し前） | 100.0% |
| md-business-packages（**全部を手で並べ直した**） | **75.8%** |

**悪化しない指標は、この企画では役に立たない。**

### 100% を成績として読ませない（Issue #3）

上の表の「手直し前」が全部 100.0% であるとおり、**1 枚目は必ず 100% になる。**
手直しは `pins` にしか書かれないので、まだ誰も直していない図に手直しは 0 件しかない。

これは「AI が上手い」ではなく「**まだ何も測っていない**」。
そこで `pnpm measure` は、`pins` が空の図を数えて、

```
うち 1 件はまだ人の手直しがありません（pins が空）。この 100% は、まだ何も測っていないという意味です。
```

と断る。**指標のほうは変えない。**数字は正しく、読み方だけが誤解される所だったため。

---

## 6. 使い方の約束

- **`pnpm measure` は合格しなくても 1 を返さない。** これは検査ではなく物差し。
  ここで CI を落とすと、**数字を良くするために指標のほうを歪める**動機が生まれる
- 機能を足したくなったら、**この数字が改善するかで判断する**（D11）。
  改善しない機能は、この製品の機能ではない

---

## 7. これを止めるべき条件

- **合格ラインを動かしたくなったとき。** 動かすなら、
  「なぜ 9 割ではなくなったのか」を先に書く。**数字が届かないから下げる、をやらない**
- 指標を 3 つ目に増やしたくなったとき。**多いと誰も見ない**（Issue 003 の注意）
- `pins` 以外の場所に人の手直しが書かれるようになったとき。
  そのときは**この測り方の前提が崩れる**ので、測り方から作り直す
