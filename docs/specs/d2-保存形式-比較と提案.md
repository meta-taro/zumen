## 2. 比較 — 候補 5 つ

### 2.1 4 つの問い

Issue 002 が挙げる 4 点で比べる。**口で書かず、同じ編集を各形式で行った実物の差分で比べた**
（`experiments/d2/fixtures/`）。

編集の内容は、この製品がまさに扱う場面 1 つ。

> 人が DB を (620, 410) へ手で動かした。そのあと AI が Redis を足し、Web01 から線を引いた。

| | 翌日、何で図を読むか | `git diff` が読めるか | コメント・順序が保つか | **手直しを表せるか** |
|---|---|---|---|---|
| **zumen YAML**（採用） | Mermaid / SVG へ書き出す。YAML なので中身は素で読める | ◎ 実測 | ◎ 実測 | **◎ `pins` に分けて持つ** |
| Mermaid | そのまま。GitHub・VS Code・md-business が描く | ◎ | ○ 自前実装なら可 | **× 書く場所が無い** |
| draw.io XML | draw.io（OSS）で開ける・編集できる | △ 冗長。圧縮されると × | × コメントを持てない | **△ 座標はあるが人／自動の区別が無い** |
| Graphviz DOT | Graphviz で描ける | ◎ | ○ | **△ `pos` は neato 専用。区別も無い** |
| JSON + JSON Schema | 素で読める | ○ 引用符と順序でノイズ | **× コメントを持てない** | ◎ |

### 2.2 実物の差分（同じ編集）

**zumen YAML** — 人の手直しが `pins` に分かれて出る。

```diff
 # 監視は本番と同じ VPC に置く。
-pins: {}
+pins:
+  db:
+    position: { x: 620, y: 410 }
 
+  - id: redis
+    type: cache
+    label: Redis
```

**Mermaid** — AI の追加しか出ていない。**人が動かした分は、そもそも書けない。**

```diff
   db[(MariaDB)]
+  redis[Redis]
 
   lb --> web01
   web01 --> db
+  web01 --> redis
```

**draw.io XML** — 人の手直しは出るが、**自動配置の変更と見分けがつかない。**

```diff
         <mxCell id="db" value="MariaDB" style="shape=cylinder3;whiteSpace=wrap;html=1;" vertex="1" parent="1">
-          <mxGeometry x="200" y="360" width="160" height="60" as="geometry"/>
+          <mxGeometry x="620" y="410" width="160" height="60" as="geometry"/>
         </mxCell>
```

**Graphviz DOT** — 書けるが `pos` は neato 専用で、階層レイアウトでは効かない。

```diff
-  db    [label="MariaDB", shape=cylinder];
+  db    [label="MariaDB", shape=cylinder, pos="620,410!"];
```

### 2.3 決め手

**「手直しを表せるか」の列だけで決まった。**

- **Mermaid は書く場所が無い。** 位置・大きさ・線の曲げ方の語彙を持たない。
  正本にすると S1（Issue 001）の結論がそのまま乗らなくなる。
  **企画の中心を捨てることになるので、正本にはできない**
- **draw.io XML と DOT は、座標は持てるが「人が決めた」という印が無い。**
  すべての要素が座標を持つので、`pins` という考え方自体が消える。
  再生成のたびに全要素の座標が書き換わり、**人の手直しがどれだったか分からなくなる**
- **JSON はコメントを持てない。** 原案 §26 の 9 が最初から落ちる

## 3. 根拠 — 実測したこと

### 3.1 往復での保持（Issue 001）

`experiments/s1/results/report.md`。7 往復で Tier A の保持 100%、Tier B 欠落 0。
実 AI が正本を丸ごと書き直した回でも、人の正本に出た差分は AI が足した 9 行だけ。

### 3.2 Git の衝突（原案 §26 の 10）

`experiments/d2/results/git-conflict.md`。使い捨ての git リポジトリで実際に merge した。

| 場面 | 衝突 | 期待 | 判定 |
|---|---|---|---|
| 2 人が別々のノードを動かす | した | しないのが正しい | **NG** |
| 2 人が別々のノードを足す | した | しないのが正しい | **NG** |
| 2 人が別々のノードのラベルを直す | しない | しないのが正しい | OK |
| 一方がノードを足し、他方がラベルを直す | しない | しないのが正しい | OK |
| 2 人が同じノードを別の場所へ動かす | した | するのが正しい | OK |
| 2 人が隣り合うノードのラベルを直す | しない | しないのが正しい | OK |

**6 場面中 4 場面が期待どおり。落ちた 2 つは同じ原因である。**

どちらも「2 人が**同じ位置へ挿入**した」形で、Git の行単位マージが原理的に解けない。
`pins` へ最初の 1 件を書く場所も、`nodes` の末尾も、両者にとって同じ 1 行だからである。

**これは YAML の欠点ではない。** Mermaid でも DOT でも draw.io XML でも同じことが起きる。
行で管理する以上、同じ場所への同時挿入は必ずぶつかる。

**ただし、ぶつかった中身は読める。**

```yaml
<<<<<<< HEAD
  db:
    position: { x: 620, y: 410 }
=======
  lb:
    position: { x: 100, y: 100 }
>>>>>>> theirs
```

人が 5 秒で解ける形になっている。draw.io XML で同じことが起きた場合、
衝突するのは `<mxGeometry x="200" y="360" .../>` の行で、**どちらが誰の意図か読めない。**

**この 2 件は形式では解けない。マージドライバ（`.gitattributes` の `merge=zumen`）が要る。**
既に持っている `merge()` がほぼそのまま使えるので、別 Issue として立てる（§6）。

### 3.3 Mermaid 書き出しの検証

`experiments/d2/results/mermaid-validation.md`。実物の `mermaid@11.17.2` のパーサに通した。
**8 件すべて PARSE OK。**

**目視では気づけなかった。** 再発防止のテストを 2 件足した。

## 4. 開発が止まった翌日、図を読む手順（README に書ける粒度）

> **zumen の開発が止まっても、図は読めます。**
>
> 1. `.zumen.yaml`（または Markdown の ```` ```zumen ```` の囲み）は、**ただの YAML** です。
>    エディタで開けば、そのまま人が読めます。
> 2. **図として見たいとき**は、隣に書き出してある `.mmd`（Mermaid）を開いてください。
>    GitHub・VS Code・md-business・その他多くのツールが、そのまま図として描きます。
>    書き出しが無い場合、`src/mermaid.ts` は 140 行ほどの
>    ファイル 1 つで、依存は YAML パーサだけです。
> 3. **形の意味を知りたいとき**は `spec/zumen-format-v1.md` を読んでください。
>    実装を読まなくても、読み書きできるように書いてあります。
> 4. `.svg` も書き出してあります。編集はできませんが、そのまま貼れます。
>
> **失われるもの**: Mermaid には位置・大きさ・線の曲げ方を書く場所がありません。
> 書き出しの先頭に、失われた指定が名指しで列挙されます。黙っては落ちません。

## 5. これを止めるべき条件

- **`pins` を別ファイルに逃がしたくなったとき。** 逃がすと Markdown への同梱が壊れる
  （D4）。逃がす必要が出たなら、D4 を「参照」へ変える判断が先
- **Markdown の囲みに収まらない大きさの図が主になったとき。**
  そのときは D4 を「参照」に変え、この形式のまま外部ファイルにする
- **Mermaid が位置指定を持つようになったとき。** そのときは Mermaid を正本にする案を
  もう一度検討してよい（現時点では書く場所が無い）
- **第三者の実装が現れたとき。** 仕様を別リポジトリへ切り出す（§7）

## 6. 仕様をどこに置くか

**この実装リポジトリの `spec/` に置く。別リポジトリにはしない。**

理由は、**いま別リポにしても同期コストしか増えないから**である。
分離の実質は「実装を読まないと形式が分からない状態にしない」ことであって、
リポジトリを分けることではない。ベースルール §10（古い文書は無い文書より悪い）に照らすと、
同期されない別リポの仕様は、実装の中のコメントより悪い。

**別リポへ切り出す条件は §5 の最後**（第三者の実装が現れたとき）。
