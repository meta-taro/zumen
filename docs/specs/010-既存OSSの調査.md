- 調査日: 2026-09-06
- 問い: **この製品の中核（人の手直しを保持したまま自動レイアウトする）は、
  既に解かれていないか**
- **使えるものは使う。** ゼロから書くのは、使えるものが無かったときだけ

## 1. 研究として何と呼ばれているか

図が変わったときに、人の頭の中の地図（mental map）をどれだけ保てるか、という問題。

- **stability / mental map preservation** — 変化の量を「各ノードが動いた距離」で測る
- **incremental layout** — 変わらない部分の配置を保ったまま、変わった部分だけを並べ直す
- **pinning weights** — ノードの動きやすさに重みを付ける

出典: [An Incremental Layout Method for Visualizing Online Dynamic Graphs](https://vis.cs.ucdavis.edu/papers/tarik_incremental.pdf) /
[Incremental Diagram Layout（yWorks）](https://www.yworks.com/pages/incremental-diagram-layout) /
[Incremental Layout in DynaDAG](https://www.researchgate.net/publication/2328560_Incremental_Layout_in_DynaDAG)

**この語彙を記録しておく。** 次に調べる人が、同じ検索から始められる。

### この製品との違い

研究が扱うのは「**データが変わったときに、機械が置いた位置をどれだけ動かさないか**」。
この製品が扱うのは「**人が置いた位置を、機械が動かさないか**」。

似ているが同じではない。前者は全ノードが機械の持ち物で、後者は
**一部のノードだけが人の持ち物**になる。だから研究の手法をそのまま当てはめられない。

## 2. Structurizr — 同じ問題を、同じ形で解いている

C4 モデルの記述から図を出すツール。**手動レイアウトの保持を実装している。**

やり方（[Workflow](https://docs.structurizr.com/lite/workflow) /
[Manual layout](https://docs.structurizr.com/ui/diagrams/manual-layout)）:

1. DSL を読んで、図を組み立て直す
2. **いまの版から手動レイアウトの情報を取り出す**
3. それを 1 の結果へ**マージする**

**zumen の D5（AI の出力を新しい正本にせず、人の正本へ入れる）と同じ向き。**
向きが正しいことの裏付けになる。

### ただし、同じところで壊れる

> 要素を改名し、かつ作成順を変えると（DSL の行の順序を変えるなど）、
> 要素を照合できず、**その要素の手動レイアウト情報は失われる**

照合は**名前**で行い、だめなら内部 id にフォールバックする。
つまり **S1 の REAL-2（AI が `db` を `maindb` へ改名した回）と同じ場面で、
手直しが失われる。**

### 採用しない理由

**方式としては同じで、そこを真似る必要が無い**（zumen は既に同じ向きで動いている）。

差が出るのは**壊れたときの振る舞い**。

| | Structurizr | zumen |
|---|---|---|
| 改名で照合できないとき | **黙って失う** | **迷子として検出し、人へ出す**（仕様 §3.4 の規則 3） |
| id の扱い | 名前が主、id が予備 | **id が正本の規則**（§5.1。意味が変わらないのに書き換えない） |

**「黙って失わない」ことがこの製品の中身**なので、ここは寄せない。

## 3. LikeC4 — 同じことを試して、**実運用で壊れると自分たちで書いている**

> モデルが変わったとき（要素の追加や改名）、LikeC4 はレイアウトの控えを再利用して
> 位置と大きさを保とうとし、部分的な再配置を行う。**しかし実際には、
> 図が壊れたり歪んだりすることが多い。とくに複数人が同じソースを触る場では顕著**

出典: [RFC: Improving Manual Layouts](https://github.com/likec4/likec4/discussions/2288) /
[Manual Layout](https://github.com/likec4/likec4/discussions/343) /
[export to PNG で手動レイアウトがノードを落とす](https://github.com/likec4/likec4/issues/1594)

### 採用しない理由

- **C4 モデル専用**で、対象が違う（zumen はサーバー・ネットワーク・クラウド構成図）
- そして**この製品が解こうとしているところが、向こうでも未解決**。
  持ってきても問題は付いてくる

**ただし、これは強い裏付けでもある。** 複数人で触ると壊れるという指摘は、
zumen が D10（構造マージ）で先に手を打ったところと同じ場所を指している。

## 4. 重なりの除去 — **ここは先行手法を使う**

`project-status` の既知問題「重なりの回避は解いていない。
人が別のノードの真上へ pin を置けば重なる」に対応する。

これは**解かれている問題**で、手法に名前がある。

| 手法 | 特徴 | 出典 |
|---|---|---|
| **PRISM** | 近接グラフ（Delaunay）＋ proximity stress model。大きい図で速い | [Efficient, Proximity-Preserving Node Overlap Removal](http://emis.icm.edu.pl/journals/JGAA/accepted/2010/GansnerHu2010.14.1.pdf) |
| **GTree** | 近接グラフ上の全域木を「育てて」重なりを解く。**元の配置をよく保つ**。PRISM より最大 8 倍速い | [Node Overlap Removal by Growing a Tree](https://arxiv.org/pdf/1608.02653) |
| **Force-Transfer** | 左右・上下の 2 走査で力を伝える。素直 | [比較研究](https://link.springer.com/content/pdf/10.1007/978-3-030-35802-0_14.pdf) |
| VPSC / VORO | 制約解法・ボロノイ | 同上 |

### 採用の判断

**採る方向。ただし、そのまま使えるものは無い。**

この製品が要るのは「重なりを解く」ではなく
**「人が置いたノードは動かさずに、機械が置いたノードだけを退ける」**。
上の手法はどれも**全ノードを動かす**前提なので、
**固定ノードを持つ変種**にする必要がある。

GTree が「元の配置をよく保つ」ので出発点に向く。**Issue を立てる**（§6）。

## 5. elkjs の対話的レイアウト — **測って、採らないと決めた**

elkjs（採用済み。D6）には `org.eclipse.elk.interactive` と、
`INTERACTIVE` な各戦略（cycleBreaking / layering / crossingMinimization / nodePlacement）がある。

**いまの実装は、人の位置を ELK に渡していない。**
ELK に全部並べさせてから、後で人の位置に上書きしている
（`size` は入力の段階で渡しているのに、`position` だけ扱いが違う）。

### 実測（5 ノード、`d` を (40,40) へ固定）

| | 固定した位置に重なった他ノード |
|---|---|
| いまの作り（後から上書き） | **2 個** |
| `elk.interactive` ＋ 座標を渡す | **1 個** |

### 採用しない理由（いまは）

**ELK の対話的戦略は、座標を「順序の手掛かり」として使うだけで、位置を固定しない。**
実測でも、固定したはずの `d` を ELK は別の場所へ動かした。

**半端に効くのがいちばん困る。** 重なりが 2 個から 1 個に減ると、
直ったように見えて、実際には残る。**§4 の方向（固定ノードを持つ重なり除去）で解く。**

この実測を書き残すのは、**次に同じことを思いついた人が測り直さずに済むため。**

## 7. 調べたが、この問題を解いていないもの

| | 手直しの保持 | zumen での扱い |
|---|---|---|
| **Mermaid** | **無い。** 手動レイアウトの言語 / API を求める [issue #2483](https://github.com/mermaid-js/mermaid/issues/2483) が開いたまま | **書き出し先として採用済み**（翌日読めることの担保） |
| **draw.io** | 位置が正本なので、そもそも「保持」の問題が起きない。代わりに**構造の再生成ができない** | **書き出し先として採用済み**（翌日編集できることの担保） |
| **PlantUML** | 無い（配置は指定するもの） | 採らない |
| **D2** | 独自レイアウト（TALA）を持つが、人の位置を固定する仕組みは中心に無い | 採らない |
| **Graphviz** | `overlap` 属性で PRISM 等を持つ（§4）。ただし**固定ノードの概念は弱い** | **手法だけ参考にする** |

## 8. この調査を止めるべき条件

- **上のどれかが「人が置いたノードを動かさない」を実装した**と分かったとき。
  そのときは**乗り換えを検討する**。この製品の存在理由がそこにあるので、
  解かれたなら自前で持つ理由が消える
- 重なりの除去を自前で書き始めて、**GTree の実装が要件を満たさないと分かった**とき
