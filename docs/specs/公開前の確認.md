# 公開（public への切り替え）前の確認

- 対象: リポジトリの visibility を PRIVATE → PUBLIC にする判断
- **切り替えるのは人。** ここに置くのは、判断に要る材料
- 確認日: 2026-09-07（commit 37 件時点）

---

## 0. なぜ書くか

`PRD.md` も `CLAUDE.md` も **public 前提**で書かれている（ベースルール §25 / §32）。
それなのに `gh repo view` の `visibility` は PRIVATE のままだった。

**公開は取り消せない。** 一度出た履歴は、あとで private へ戻しても
fork / clone 済みのコピーには残る。だから**先に確かめる。**

再現するには、

```bash

bash .github/scripts/oss-privacy-check.sh "$(git rev-list --max-parents=0 HEAD)" HEAD

# いま公開されるファイルの中身そのもの
OSS_SCAN_ALL_FILES=1 bash .github/scripts/oss-privacy-check.sh
```

## 2. 手元では確かめられないこと

**禁止語（実名等）の検査は、手元では走らない。**
一覧はリポジトリの secret（`OSS_DENY_WORDS`）にあり、
**AI も手元の作業も、それを平文で扱わない**（ベースルール §14）。

そこで **CI から手で回せる口**を用意した。

> GitHub の Actions → `oss-privacy-check` → **Run workflow**
> （`最初の commit から全部を検査する` を on のまま実行）

**2026-09-07 に一度回した。** `pnpm-lock.yaml` の 1 行が禁止語に当たったが、
**誤検出だった**（`cpu: [ppc64]` という rollup のプラットフォーム別パッケージの行）。
禁止語を部分一致で見ていたため、英数字の短い語が機械生成の文字列に偶然含まれていた。
英数字の語は語境界を見るように直してある（日本語の語は語の区切りが無いので部分一致のまま）。

**直したあと、もう一度回して通った**（2026-09-07）。**全履歴に禁止語の混入は無い。**

これを回すと、CI の中で secret を使って、

- 全 commit の author / committer / message
- 全履歴の追加行
- **追跡中の全ファイルの中身**

を一度に見る。**秘密情報は手元へ出ない。**

### なぜ push ごとの検査では足りないか

push ごとの検査は、**その push の範囲しか見ない。**
初回 push は比較の基準が無く、commit 検査がスキップされる
（実際、この仕組みではそうなる）。
**最初のあたりが未検査のまま残りうる**ので、公開の前に一度は全部を見る。

## 3. 公開すると見えるようになるもの

169 ファイル。中でも、**普通は社外に出さない類**のものが含まれている。

| | 中身 | 出してよいか |
|---|---|---|
| `.claude/decisions.md` | 16 個の決定と、**却下した案とその理由** | 判断が要る |
| `.claude/issues/` | 15 件。**「注意」欄はたいてい一度失敗したこと** | 判断が要る |
| `.claude/project-status.md` | **既知の問題**（直っていないもの）が並ぶ | 判断が要る |
| `.claude/rules/product-baseline.md` | 開発の作法（**公開版**。完全版は非公開） | 公開前提で書かれている |
| `docs/origin/` | 受領した原案 | 判断が要る |
| `experiments/` | 実測の生データ（**うまくいかなかったものを含む**） | 公開前提で書かれている |

**これは欠点ではなく、この製品の中身そのもの**でもある。
「AI と人がどう作ったか」が丸ごと残っていることに価値があるなら出すし、
出したくないものがあるなら、**公開の前に外す**（あとからでは遅い）。

**ここは AI が決めることではない。**

---

## 4. 公開したあとに要ること

- `SECURITY.md` が案内している **GitHub Security Advisories を有効にする**
  （非公開で脆弱性を受け取る口。無いと公開 issue に書かれる）
- fork からの PR では **secret が渡らない**ので禁止語検査が常にスキップされる。
  CI のログにその旨は出るが、**fork の PR は人が中身を見る**前提で運用する
