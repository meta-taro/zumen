# ロードマップ — zumen（図面）

## 原案のフェーズは採らない

原案 §19 は 7 段（Phase 0〜6）に積んである。**この順は採らない。**

| 原案の順 | 採らない理由 |
|---|---|
| Phase 0 Format → 1 Renderer → 2 Editor → 3 AI | **中核（AI）が 4 番目に来る。** Phase 2 到達時点の成果物は「機能の少ない作図ソフト」で、それは既に世の中にある |
| Phase 2 で編集機能を一式そろえる | 選択・ドラッグ・リサイズ・接続・削除・Undo は**既存ソフトの機能一覧と区別がつかない**。ここを揃えても差が出ない |
| Phase 4 で AWS/GCP 図形 | 図形の量は勝負どころではない。**足すのはいつでもできる** |
| Phase 5 で md-business 連携 | 姉妹プロジェクトである以上、連携は前提であって後付けの機能ではない |

**原案が間違っているのではない。**あれは「完成形へ至る作業の順序」であり、正しい。
ここで要るのは別のもの――**続けるかどうかを判断するための順序**である。

## 測る順と、作る順を分ける

- **測る順** = 成立しなければ企画ごと畳む順。**先に置く**
- **作る順** = 成立が分かってから積む順。原案 §19 をほぼそのまま使ってよい

### 測る順（S1〜S3）— ここで止まったら畳む

| | 何を測るか | 成立しなかったら |
|---|---|---|
| **S1** | 人が手で直した位置・体裁を、AI の再生成が壊さずに保持できるか（原案 §26 の 2・6） | **企画ごと畳む。** ここが本体価値で、代替案が無い |
| **S2** | 保存形式は「この製品が終わっても図が読める」形にできるか（D2） | 独自形式で押し切るなら OSS の存続ゲートに落ちる。**形式を先に他所へ寄せる** |
| **S3** | 文章の指示 1 本から、説明に使える品質の図が出るか（原案 §26 の 1・3） | 品質が足りないだけなら継続可。**S1 とは重みが違う**ので混ぜない |

**S1 を最初に置く。** ここだけは他で埋め合わせができない。
S3（生成品質）は AI 側の進歩でいずれ良くなるが、S1 は誰も解いてくれない。

### 作る順（B1〜B4）— S1・S2 が通ってから

| | 中身 |
|---|---|
| **B1** | 保存形式の確定と検証器。テキスト正本・Git 差分が読める・コメントと順序が保存で壊れない |
| **B2** | レンダラと自動レイアウト。図形は最優先の対象図の分だけ |
| **B3** | 承認のための最小 GUI。**編集機能一式ではなく、AI の書き換えを人が承認できる分だけ**（PRD §2） |
| **B4** | CLI / MCP の口と md-business 連携。**単体で使えることは維持する** |

**B3 の完成度で止まらない。** 汚くてよい。ここに時間を吸われるのが最大の失敗経路で、
「使いやすい作図ソフト」を作り始めた時点で D1 の判断を自分で裏切っている。

## 判断の置き場所

- S1〜S3 の結果は製品リポの `decisions.md` に書く。**成立しなかったことも書く**
- 畳む判断は企画側の記録にも写す
- 期限は切らない。**経路を握ったまま期限を切らない**（切ると、こちらの遅れが担当の未達として記録される）
