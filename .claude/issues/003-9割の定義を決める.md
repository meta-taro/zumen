# 003 — 「AI が 9 割描けた」を何で測るかを決める

- Phase: 測る順（S1 / S3 の前に置く）
- 前提: なし
- 優先度: 高

## 目的

このプロダクトは「AI が 9 割描き、人が 1 割直す」を掲げている。
**その 9 割が測れないと、出来上がりが従来の作図ソフトと同じになっていても気づけない。**

機能が増えるほど「使える」ようには見える。だが人が図形を並べ直しているなら、
それは高機能な作図ソフトであって、この企画ではない。

## 決めること（このリポで決めてよい）

- 何を数えるか。**候補: 人が触った操作の回数 / 人が動かしたノードの割合 /
  最初の生成から完成までの経過時間 / 人が書いた文字数**
- どの図を基準にするか（毎回同じ 1 枚を使わないと比較にならない）
- 合格ラインを数字で

## 作業内容

1. 測る対象を決め、**計測を先に仕込む**（後から足すと、都合の良い数字が出た日だけ記録される）
2. 基準にする構成図を 2〜3 枚決める（**実在の構成を使う。架空の綺麗な例で測らない**）
3. 現状値を取る。この時点では低くてよい。**下がっていないことを後から確認するための基準線**

## 完了条件

- 測る指標が 1 つ以上決まり、数字で書かれている
- 基準となる図が固定され、リポに入っている
- 現状値が記録されている
- **人が図形を手で並べ直し始めたときに数字が悪化する**ことが確認できている
  （悪化しない指標は、この企画では役に立たない）

## 注意

- **指標を増やしすぎない。**1〜2 個でよい。多いと誰も見ない
- **人の作業時間を担当の評価に使わない。**測っているのは製品であって人ではない

## 作業ログ

- 2026-09-06 着手。**計測を別に仕込まずに済む**ことに気づいたのが分かれ目。
  人の手直しは `pins` にしか書かれない（仕様 §3.4）ので、正本 1 つで測れる。
  これで「後から足した計測は、都合の良い数字が出た日だけ記録される」を構造的に防げる

## 結果

**完了。D3 が確定した（未決はこれで無くなった）。**

- 定義: `docs/specs/003-9割の定義.md`
- 実装: `src/measure.ts` / `pnpm measure <図> ...`
- 基準線: `experiments/s3/results/baseline.md`（`pnpm s3` で再生成）
- 基準の図: `experiments/s3/fixtures/`（**実在の構成から起こした 2 枚**）
- 決定: `.claude/decisions.md` の **D3**

### 完了条件との対応

| 完了条件 | 状態 |
|---|---|
| 測る指標が 1 つ以上決まり、数字で書かれている | 済。**2 つ**（自力率 / 配置の自力率）。合格ラインは **90%** |
| 基準となる図が固定され、リポに入っている | 済。**実在の構成 2 枚**（zumen 自身の import / md-business の依存） |
| 現状値が記録されている | 済。`experiments/s3/results/baseline.md` |
| **人が並べ直し始めたときに数字が悪化する**ことが確認できている | 済。全部を手で置くと 100% → **62.1% / 75.8%**。テストでも単調に下がることを確認 |

### 正直な現状 — **S1 の往復は 8 回中 3 回が合格ラインを割っている**

R3 / R4 / R5 が **85.0%**。20 要素の図で人が 3 か所直した、という意味。

**指標を甘くして通していない。**
S1 が測ったのは「手直しが**壊れないか**」であって「手直しが**少ないか**」ではないので、
S1 の Go 判定と矛盾はしない。**別のことを測っている。**

### 注意への対応

- **指標は 2 個で止めた**（3 つ目を作らない）
- **人の作業時間を数えていない。** 測っているのは製品であって人ではない
- `pnpm measure` は不合格でも終了コード 0。**検査ではなく物差し。**
  CI を落とすと、数字を良くするために指標のほうを歪める動機が生まれる
