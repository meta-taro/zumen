# 001 — ★人が手で直した図を、AI の再生成が壊さないか（唯一の勝負どころ）

- Phase: 測る順 S1
- 前提: なし（最初に着手する）
- 優先度: **最高**

## 目的

**この製品の価値は、ここ 1 点に乗っている。**

文章から図を出すだけなら、既存の AI でもできる。既存の作図ソフトは 1 枚目を描く道具として
完成している。**勝負するのは 2 枚目以降**――「構成が変わったので図を直す」場面だけである。

そこで必ず起きるのがこれ。

> 人が「この DB はここに置きたい」と手で動かした。
> そのあと「Redis を足して」と AI に頼んだ。**動かした位置が元に戻った。**

**戻ったらこの製品を使う理由が消える。** 使う人は二度と手で直さなくなり、
結果として「AI が出したまま貼るだけ」になり、既存の生成 AI と同じものになる。

## 問いを間違えないこと

原案 §26 は検証項目を 10 個並べ、「特に 1・2・6」としている。
**このリポでは 2 と 6 を先に、単独で測る。**

- 1（YAML → レイアウト → SVG が綺麗になるか）は**生成品質**の問題で、AI とレイアウト
  エンジンの進歩でいずれ良くなる。**誰かが解いてくれる側**
- 2・6（人の手直しの保持）は**誰も解いてくれない**。ここが本体

## 決めること（このリポで決めてよい・上流へ選択肢を投げ返さない）

- 「壊れていない」の判定基準を、**先に文章で書く**。何が保持されれば合格か
  （位置だけか、サイズ・色・接続の曲がり方まで含むか）
- 人の指定を保持する方式（差分マージ / 位置のピン留め / 人の編集を別レイヤに持つ / その他）
- レイアウトエンジンの選定（S1 を通すのに必要な範囲で。網羅比較はしない）

## 作業内容

1. **判定基準を先に書く。**実装より先に書くこと。後から書くと、実装できた範囲が基準になる
2. 構成図 1 枚を対象に、生成 → 人が手で直す → 再度指示、の往復を成立させる
3. 往復を **3 回以上**繰り返す。1 回だけだと偶然通る
4. 次の 3 つを個別に測る
   - **保持**: 人が直したものが残るか
   - **反映**: AI に頼んだ変更がちゃんと入るか
   - **競合**: 人の指定と AI の変更がぶつかったとき、**どちらが勝つかを人が選べるか**
5. 結果を Go / Conditional / No-Go で書く

## 完了条件

- 判定基準が、実装前に書かれた状態で残っている
- 3 回以上の往復ログが残っている（**入力した指示と、出力された図の両方**）
- 保持・反映・競合の 3 つそれぞれに結果が書かれている
- 判定が 3 つのいずれかで書かれている
  - **Go** — 手直しが保持される
  - **Conditional** — 条件付きで保持される（条件が明記されている）
  - **No-Go** — 保持できない
- **No-Go の場合、何が原因で保持できないのかが書かれている**（レイアウトエンジン側か、
  形式側か、AI の書き換え方か）

## 注意

- **この Issue を省略して先へ進まない。**GUI もレンダラも、ここが成立しない限り価値が出ない
- **綺麗さで判定しない。**この Issue で見るのは保持であって品質ではない（品質は Issue 004）
- **No-Go が出たら企画ごと止める。**代替案を探しに行かず、まずメンテナへ結果を返す。
  ここが成立しないなら、この製品を作る理由が無い
- **Conditional は落とさない。**条件を潰す方向で検討してよい

## 作業ログ

### 2026-09-04 — 判定基準を確定（作業内容 1）

実装より先に判定基準を書いた。`docs/specs/s1-判定基準-手直しの保持.md`。

この Issue が「先に文章で書く」と指定していた 3 点について、次のように決めた。

- **何が保持されれば合格か** — 保持対象を Tier A / B / C の 3 段に分けた。
  Tier A（人が明示した位置・サイズ・ラベル、および「人が決めた」という印）は
  **1 つでも失われたら No-Go**、閾値の妥協を置かない。Tier B（エッジ経路・色・
  グループ所属・コメントとキー順）は 80% 以上かつ欠落を列挙できることを条件に Conditional。
  Tier C（人が触っていない要素の自動配置）は**保持しようとしない** —
  全部固定すると自動レイアウトが死に、「AI に頼んでも図が変わらない」逆方向の失敗になる。
- **3 軸を混ぜて 1 つの点数にしない** — 保持と反映はトレードオフで、
  全部固定すれば保持 100%・反映 0% になる。**数字は必ず 2 つ並べて出す**ことを基準に明記した。
- **競合は 3 項目すべて必須**（検出・選択・持続）。**黙って上書きした時点で No-Go** とした。
  人が気づけない上書きは、保持できないことより悪い。

あわせて、この判定を**自分で無効にする条件**（§7）を先に書いた。
実験中に基準を緩めた場合・AI の書き換え範囲を人為的に狭めた場合・図が下限を下回る場合は、
その回の結果を結論として使わない。

**保存形式（D2 / Issue 002）はここでは決めない。** S1 は実験用の暫定形式の上で測り、
S1 で必要と分かった保持要件を Issue 002 の候補評価へ入力として渡す。

**人が手で直した分は、AI の再生成で壊れなかった。**

往復ログ: `experiments/s1/results/report.md`（`pnpm s1` で再生成できる）。
判定基準: `docs/specs/s1-判定基準-手直しの保持.md`。

**7 往復**（要求は 3 回以上）。**保持と反映は必ず並べて出した**（判定基準 3.2）。

### 3 軸それぞれの結果

**保持 — Tier A は全往復で 100%。**
人が置いた位置・変えた大きさ・書き換えたラベルは、1 つも失われなかった。
Tier B（体裁・線の曲げ方・グループ所属・コメントと並び順）も欠落 0。

**いちばん効いたのは REAL-1。** ここでは実 AI 役が正本を丸ごと書き直しており、
提案の側では**コメントが全部落ち・キーの並びが変わり・`pins` の節ごと消え・
ノードの並びも入れ替わっていた**。それでも人の正本に出た差分は、
AI が実際に足したノード 1 個とエッジ 2 本の **9 行だけ**だった。

理由は 1 つで、**AI の出力を新しい正本にしなかった**から。
AI が出すのは提案で、書き換わるのは人の正本のほう、という向きにしてある。
提案から読むのは semantics だけで、`pins` は読まない。値が同じキーには触らない。

**反映 — 全往復で、事前に書き出した構造変化がすべて入った。**
保持を上げるために書き換えを止めてはいない（判定基準 3.2 の逆方向の失敗）。

**競合 — 検出・選択・持続の 3 つとも成立。**

- **検出**: R4 で、人が置いた位置と AI の位置提案がぶつかったことを競合として返した。
  **黙って上書きは 1 件も起きていない**
- **選択**: 人が「自分の位置を採る」を選べた
- **持続**: 選んだ結果が `locked: true` として**正本へ書かれ**、
  R5 で同じ指示が来ても**聞き直さずに抑止**された（差分は空）。
  実行中の変数に持つ形にしていたら、ここで再び聞くことになっていた

### 分かったこと（Issue 002 / D2 への入力）

1. **成立の条件は「人の指定を semantics と別の節に置く」こと。**
   同じ節に混ぜると、AI が semantics を書き直すたびに人の指定も書き換え対象になる
2. **成立のもう 1 つの条件は、要素の id が安定していること。**
   REAL-2 で AI が `db` を `maindb` に改名した瞬間、人の指定は紐づく先を失った。
   黙って消えはせず競合として出たが、**id の安定は形式側で守る必要がある**
3. 人の指定は**正本と同じ 1 本のテキストの中**に置けた（D4 の同梱の形で成立）

### 残る弱点（隠さず書く）

- **REAL-2 の解決前の状態は汚い。** id が改名されると `db` と `maindb` の両方が
  図に残る（人が競合を解くまで）。**壊れてはいないが、そのまま貼れる図ではない**
- **pin を持つ要素の削除は、その場では反映されない。** 消してから聞いても戻せないので
  残して聞く設計にした。代償として、解決までその 1 要素の反映が遅れる
- **重なりは全往復で 0 だったが、これは pin の置き場所が自動配置と干渉しなかったため。**
  人が別のノードの真上へ置けば重なる（`layout.test.ts` で確認済み）。
  pin と自動配置の共存を「重ならないように寄せる」方向で解いてはいない

### 途中で見つけて直したこと（測定値だけ見ていたら気づかなかった）

**SVG を実際に描いて目で見たところ、pin したノードがグループの枠から出ていた。**
R1・R2 で `db` が vpc の枠外に描かれていた（`groupEscapes` で 2 件）。
3 軸の数字はすべて満点だったので、**表だけ見ていたら通していた。**

直し方は「人の位置を枠の中へ押し戻す」ではなく「**枠のほうを広げる**」にした。
押し戻すのは手直しを壊すこと（判定基準 3.1）であり、枠は「この範囲が VPC」という
意味なので、中身に合わせて動くほうが正しい。
無所属のノードのために枠を広げないことも、あわせてテストで固定した。

`groupEscapes` を測定値として報告に足した（現在は全往復 0）。

### この結果の限界（判定基準 §7・§8 に照らして）

- **実 AI 役の提案（REAL-1 / REAL-2）は、このセッションのモデルが指示と正本から
  書いたものであって、API 経由で自動実行した結果ではない。**
  丸ごと書き直す・コメントを落とす・id を変えるという、実際に起きる壊れ方を
  意図して含めてあるが、**多数のモデル・多数の試行にわたるばらつきは測っていない**
- R1〜R3 の提案は狭い書き換えなので、これだけを根拠にすると判定基準 §7 の
  「AI の書き換え範囲を人為的に狭めた」に当たる。**だから REAL-1 / REAL-2 を並べた**
- 判定基準は実験中に一度も緩めていない。Tier B が未実装のまま Conditional へ
  逃げないよう、大きさ・体裁・線の曲げ方の保持を先に実装した
