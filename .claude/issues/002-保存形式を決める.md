# 002 — ★保存形式を決める（この製品が終わっても図が読めるか）

- Phase: 測る順 S2
- 前提: Issue 001 と並行してよい
- 優先度: **最高**

## 目的

OSS の存続ゲートは「作った人がいなくなっても続くか」である。
図を描く道具にとって、これは実質**保存形式の問題**に落ちる。

> **この製品の開発が止まった日、それまでに描いた図はどうなるか。**

独自形式で持っていると、その日に全部読めなくなる。
**使う人はそのリスクを直感的に嫌がる**ので、形式が決まらないうちは誰も本番の図を預けない。

## 混同しないこと（重要）

`decisions.md` の D1 で **draw.io を部品として組み込む案を却下した**。
これと「draw.io 形式で保存する / 出力する」は**別の判断**であり、両立する。

| 判断 | 中身 | 状態 |
|---|---|---|
| draw.io を**部品として使う** | エディタの中身に組み込む | **却下済み（D1）** |
| draw.io **形式で保存・出力する** | 他所で開けるようにする | **未決定（この Issue）** |

D1 を理由にこの Issue の選択肢から draw.io 形式を外さないこと。

## 決めること（このリポで決めてよい）

- **正本の形式**（人が読めるテキストであること・Git の差分が読めることは前提）
- **他所で読める経路**をどう用意するか（他形式への出力 / 変換器を別に切る / 仕様を実装から分離して公開）
- 形式の仕様をどこに置くか（実装リポの中か、別リポか）

### 決め手

候補 5 つ（zumen YAML / Mermaid / draw.io XML / Graphviz DOT / JSON）を
Issue の 4 つの問いで比べた結果、**「人の手直しを表せるか」の 1 列で決まった。**

- **Mermaid は書く場所が無い。** 位置・大きさ・線の曲げ方の語彙を持たない。
  正本にすると S1 の結論がそのまま乗らない＝**企画の中心を捨てることになる**
- **draw.io XML と DOT は座標を持てるが、「人が決めた」という印が無い。**
  全要素が座標を持つので `pins` の考え方自体が消え、再生成のたびに
  人の手直しがどれだったか分からなくなる
- **JSON はコメントを持てない**（原案 §26 の 9 が最初から落ちる）

### 独自形式にするための条件（3 つとも満たした）

| 条件 | 状態 |
|---|---|
| 仕様を実装から切り離す | `spec/zumen-format-v1.md`。実装を読まずに読み書きできる粒度。適合条件も明記 |
| 他所で読める経路 | Mermaid 書き出し（実物・実パーサ検証済み）＋ SVG 書き出し（実物） |
| 先送りしない | 形式を決めるのと同じ作業で書いた |

### 「開発が止まった翌日に図を読む手順」

比較文書 §4 に、README へそのまま移せる粒度で書いた。要点は
「YAML なので素で読める／図として見るなら隣の `.mmd` を開く／
形の意味は `spec/` を読む／書き出しで落ちるものは黙って落とさない」。

### 仕様の置き場所

**実装リポジトリの `spec/` に置く。別リポにはしない。**
いま分けても同期コストしか増えず、同期されない別リポの仕様は実装内のコメントより悪い
（ベースルール §10）。**別リポへ切り出す条件は「第三者の実装が現れたとき」。**

### 残る弱点

- **Git の衝突は 2 件解けていない**（2 人が別々のノードを動かす／別々のノードを足す）。
  形式では解けず、マージドライバが要る。ただし**ぶつかった中身は人が読める形**で出る
  （draw.io XML なら `<mxGeometry x=... />` の行がぶつかり、誰の意図か読めない）
- draw.io XML 書き出しは未実装。原案 §29 は Import/Export 先としているが急がない

### 決定の根拠（推奨として出したもの）

判断の芯は **潰せるリスクと潰せないリスクの取引**。

- 独自形式のリスクは「形式の意味が実装の中にしかない」こと。**潰せる**（実際に潰した）
- Mermaid / draw.io XML を正本にするリスクは「**中心機能が乗らない**」こと。**潰せない**

加えて、Mermaid を正本にしても**実装は減らない**。ラウンドトリップ可能な
パーサ/シリアライザが無く自前で書くことになり、記法が緩いので正規化も難しい。
「既存形式に乗れば安い」がこの件では成り立たない。

さらに、**替えにくいのは器ではなく「人の指定を semantics と別の節に持つ」設計**であり、
そちらは S1 で実証済み。器のほうは後から替えられる。**危ない決定は既に検証を通っていて、
いま決めるのは安いほう**だった。
