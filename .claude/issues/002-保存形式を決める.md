# 002 — ★保存形式を決める（この製品が終わっても図が読めるか）

- Phase: 測る順 S2
- 前提: Issue 001 と並行してよい
- 優先度: **最高**

## 目的

OSS の存続ゲートは「作った人がいなくなっても続くか」である。
図を描く道具にとって、これは実質**保存形式の問題**に落ちる。

> **この製品の開発が止まった日、それまでに描いた図はどうなるか。**

独自形式で持っていると、その日に全部読めなくなる。
**使う人はそのリスクを直感的に嫌がる**ので、形式が決まらないうちは誰も本番の図を預けない。

## 混同しないこと（重要）

`decisions.md` の D1 で **draw.io を部品として組み込む案を却下した**。
これと「draw.io 形式で保存する / 出力する」は**別の判断**であり、両立する。

| 判断 | 中身 | 状態 |
|---|---|---|
| draw.io を**部品として使う** | エディタの中身に組み込む | **却下済み（D1）** |
| draw.io **形式で保存・出力する** | 他所で開けるようにする | **未決定（この Issue）** |

D1 を理由にこの Issue の選択肢から draw.io 形式を外さないこと。

## 決めること（このリポで決めてよい）

- **正本の形式**（人が読めるテキストであること・Git の差分が読めることは前提）
- **他所で読める経路**をどう用意するか（他形式への出力 / 変換器を別に切る / 仕様を実装から分離して公開）
- 形式の仕様をどこに置くか（実装リポの中か、別リポか）

## 作業内容

1. 候補を 3 つ以上挙げ、それぞれについて次を書く
   - この製品が終わった翌日、**何を使えば図が読めるか**
   - 人が手で直したときの差分が読めるか（`git diff` が意味を持つか）
   - コメント・並び順が保存で壊れないか（原案 §26 の 9）
   - Issue 001 の「手直しの保持」を表現できるか
2. Git の衝突がどこまで抑えられるかを見る（原案 §26 の 10）
3. 決めた形式で、Issue 001 の往復が成立するかを確認する

## 完了条件

- 形式が 1 つに決まっている
- 「開発が止まった翌日に図を読む手順」が **README に書ける粒度**で書かれている
- 仕様が実装から分離されているか、されていないなら**その理由**が書かれている
- 候補の比較表が残っている（**採らなかった案とその理由**を含む）

## 注意

- **「あとで変換器を書けばいい」で先送りしない。**書かれないまま残る
- **正本を画像やバイナリにしない。**この製品の前提が崩れる
- 形式を独自にすること自体は禁止していない。**独自にするなら、仕様を実装から
  切り離して公開すること**が条件になる
