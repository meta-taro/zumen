# 008 — CLI / MCP の口と、姉妹プロジェクトとの境界を決める

- Phase: 作る順 B4

## 目的

原案では姉妹プロジェクト連携が Phase 5（終盤）に置かれている。
**連携は前提であって後付けの機能ではない**ので、後ろに置くと
「単体で完結する別アプリ」として作り込まれ、あとから繋がらなくなる。

ただし **姉妹プロジェクトの機能として作らない。**単体で使えることは維持する。

## 決めること（このリポで決めてよい）

- CLI の口（図の生成・変換・検証をコマンドで叩けるか）
- MCP で公開する操作の範囲。**書き換え系をどこまで開けるか**
- ファイルの置き場所の作法（どこに置けば姉妹側から見えるか）

## 完了条件

- **単体で使う場合に何も欠けないこと**が確認されている
- 姉妹側に依存している箇所があれば、それが明記されている（無いのが望ましい）

## 注意

### 決めたこと（このリポで決めてよい、とされていた 3 点）

**1. CLI の口**

`validate` / `measure` / `svg` / `mermaid` / `drawio` / `embed` / `merge` / `merge-driver`。

**終了コード 1 を返すのは「読めない」ときだけ。**
`measure` の不合格や `merge` の競合で 1 を返すと、
**CI を通すために指標を歪めたり、競合を黙って潰したりする動機が生まれる。**

**2. MCP で開ける範囲 — 書き換え系をどこまで開けるか**

**読みと提案まで。正本を直接書ける口は作らない。**

`merge()` の 1 本だけを通す。`merge()` は構造上、提案から `pins` を読まず、
競合を適用せずに返すので、**この口を通る限り人の指定は壊れない。**

**競合の決着は開けない。** 開けた瞬間、
**AI が自分の提案を自分で承認できてしまう**（この Issue の注意そのもの）。

**3. ファイルの置き場所の作法**

図の正本は**文書の隣**に `<名前>.zumen.yaml`。
別のディレクトリへ隔離すると、文書だけが更新されて図が取り残される。
この名前が `.gitattributes` のマージドライバ（D10）の対象そのものなので、
**別の名前で置くと構造マージが効かない。**

  （画面と人の仕事。D11）
