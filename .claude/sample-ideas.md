（2026-09-12。オーナーの指示）。

> どんどんニッチだけど重要なプロの図面を検索して吸収して zumen アプリで
> つくれるようにしてほしい

ここは**作る前の置き場**。作ったら「作った」へ移す。
**思い付きを消さない** —— 消すと、なぜそれを狙ったかが失われる（ベースルール §24）。

## 見るところ

新しいネタを足すときは、**その業界の実物を 1 枚は見てから**書く。
実物を見ないと「箱と矢印」になる。これは 2026-09-12 に間取り図で実際にやった
（オーナーの指摘「不動産の間取り図レベル」）。

見るのは 4 点。

1. **符号**は何か（`C1` / `R-A01` / `OP-10`）
2. **寸法**が要るか。要るなら何を基準に測るか（通り芯・壁芯・区画界）
3. **向きのある線**か、**繋がっているだけの線**か（`arrows`）
4. **その図が無いと何ができないか**（拾い出し・積算・申請・点検）

#### ~~課題 7~~ —— 断面・立面（**ほぼ解けた**）

**断面図を 1 枚描いて確かめた**（2026-09-12。擁壁の標準断面図）。

| 違い | どうしたか |

#### 課題 8 —— 縦横で縮尺を変える

道路の標準横断図を描いて出てきた（2026-09-12）。

全幅 11.5m と舗装厚 250mm を**同じ縮尺**で描くと、舗装が 13px になって
文字が入らない。**実物は H=1/100・V=1/20 のように縦横で縮尺を変えている。**

縦断図（距離 100m 対 高さ 1m）はもっと極端で、**変えないと図にならない。**

いまは `scale: { mm: 20 }` の 1 つだけ。
`scale: { x: 20, y: 5 }` のように分ければ足りるはずだが、
**寸法の数値が縦横で別の縮尺になる**ので、読み手が取り違えないかを確かめる必要がある
（実物は図面のどこかに「H=1/100 V=1/20」と必ず書いてある）。

**逃げ道はある。** 舗装構成だけを別の図に切り出せば、単一の縮尺で描ける（43 がそれ）。
実物もそうしている（横断図に舗装構成の詳細を吹き出しで付ける）。

#### 課題 7 の残り —— まだ描いていない断面・立面

矩計図・橋梁の一般図・縦断図・擁壁の標準断面図・展開図・立面図。
**「○○図」を業界ごとに数えたら、いちばん多くの図がここで止まっていた。**

平面図は「上から見た配置」で、断面・立面は「横から見た高さ」。
**zumen の `kind` は `structure` / `placement` の 2 つしか無く、どちらも上から見ている。**

要るのは新しい形ではなく、**高さの軸**。
`placement` の座標が (x, y) で平面を指すのに対し、断面では y が高さになる。
`kind: section`（断面）を足せば、**同じ道具立てのまま**描ける可能性がある
—— 通り芯は基準線（GL・FL・天端）に、寸法は高さ寸法になる。

**まず確かめること。** 断面図を 1 枚、いまの `placement` で描いてみる。
`y` を高さとして読み替えるだけで足りるなら、足すのは `kind` の語 1 つで済む。

##### 残り —— シーケンス図

**ライフラインと活性区間**が要る。
縦の時間軸（`mark: tick` を `y` に）は書けるが、
**ライフラインは「縦に伸びる破線」**で、箱でも辺でもない。

いま辺は箱と箱を繋ぐので、**ライフラインの途中に取り付く線**が書けない。
`marker: none` の小さな箱を時刻ごとに並べれば描けるが、
**それは「できる範囲へ図を寄せる」**（オーナーが止めたやり方）。

**メッセージが取り付く先を、箱ではなく「箱と時刻」にできるか**を考えてから作る。

#### 旧 課題 9 の元の記述

UML をひと通り揃えて、**シーケンス図だけが残った**（2026-09-12）。

|---|---|---|
| シーケンス図 | 相手（ライフライン） | **時刻**（上から下へ） |

| 工程表・ネットワーク工程表 | **時刻** | 工程 |

足りないものが「目盛り」だけなら、`grid` の `mark` に `tick`（時刻の目盛り）を
足すだけで済む可能性がある。

**ガントチャートが描ければ、工程表も同時に開く**（建設・製造でよく使う）。

#### 課題 13 —— 目盛りの届く範囲を正本が言えない

`mark: tick` の線は、**箱ぜんたいの範囲**まで伸びる（`src/dimensions.ts`）。
工程表のように図の全部が目盛りの中にあるならこれで正しいが、
**凡例や注記を同じ紙に置くと、その上を線が走る**（2026-09-13。見本 64）。

機械には「ここまでが表、ここからは注記」が分からない。
見本 64 では**凡例を最後の目盛りより右へ出して**避けた。

足すなら「軸がどこまで効くか」を正本が言える形にする。
ただし**課題 3（1 枚に複数の図）と同じ問題**なので、そちらと一緒に考える。

#### 課題 10 —— 重なり順を正本が決められない

**いまは面積の大きい箱から描く**（`src/render.ts` の `stack`）。
たいていはこれで正しい（広い部屋が下、小さい機器が上）が、**下敷きを敷けない。**

実物の停車駅一覧には、乗換駅の位置に**薄い灰色の縦帯**が帯の後ろを通っている。
細くて背が高いので面積が小さく、**帯より前に出てしまう。**

足すなら `z` のような数ではなく、**「下敷き」という 1 語**にする
（数を許すと正本ごとにばらける。`weight` で数を断ったのと同じ筋）。

#### 課題 11 —— 3 段目の文字（ローマ字）

実物の路線図の駅名は**漢字・ふりがな・ローマ字の 3 段**。
zumen には `label` と `technology` の 2 つしか無いので、**2 段までしか出せない。**

見本 54 はふりがなを採った（実物の右の列と同じ）。
ローマ字は `technology` に書けば寝るが、**両方は出せない。**

#### 課題 12 —— 帯の模様（縞・点線の帯）

阪急の停車駅一覧では、**通勤特急が「橙地に白の破線」**になっている
—— 特急と色が近いので、色だけでは見分けられないため。

`hatch` は帯の色で描くので、**帯と同じ色になって見えない。**
模様の色を別に持てるようにするか、`line` を帯にも効かせるか。

#### 閉じた曲線が要る図を数えた（2026-09-13）

**課題 2 のときと同じやり方**で、「代用できるか」を実際に描いて数えた。
描いたのは見本 62（寺院庭園）。**輪に並べた点を 1 本の辺で通す代用は、
1 区間ぶん口が開いた** —— 開いた池は池に見えない。

そこで **`edges[].close`（輪を閉じる）だけ**を入れた（仕様 §3.0.15）。
**面の塗りは入れていない。** 実物の庭園平面図も、池は輪郭と「池」の字で足りている。

数えた結果。

| 図 | 代用できるか | いま描けるか |
|---|---|---|
| 庭園の池・中州（不整形な水面） | ✗ 矩形の池は「矩形の池」 | **輪郭は描ける**（見本 62） |
| 陸上競技場のトラック（オーバル） | ✗ | **輪郭は描ける** |
| ロータリー交差点 | ✗ | **輪郭は描ける** |
| 車両限界・建築限界（鉄道） | ✗ 規格の形そのもの | **輪郭は描ける** |
| 車・船・飛行機の外形（三面図） | ✗ 外形が製品 | **輪郭は描ける**（塗りは無い） |
| 等高線 | ✗ | **描ける**（開いた曲線 ＝ `via`） |
| 野球場・サッカーの扇形スタンド | △ 矩形でも席種と位置関係は読める | 矩形で代用中（見本 60） |
| 電波の到達範囲・警戒区域（円） | ✓ | `radius` で描ける |
| 道路の平面線形・河川の護岸 | ✗ | **描ける**（`via` ＋ `curve`。見本 61） |

**残っているのは「面の塗り」だけ**になった。
輪郭が引ければ、たいていの図は読める —— 塗りが要るのは
**面どうしが重なって、どちらが上か言いたいとき**（水面と中州、車体と窓）。
そこまで来たら課題 5 を開ける。

#### 課題 5 —— 自由形状

**万博の大屋根・車の外形・河川の護岸・地形の等高線。**

ノードが矩形しか無い。**これは課題として残すが、優先度は最も低い。**
「配置と寸法が読めること」が図の仕事で、**外形の忠実さはその次**だから。

## やり方 —— 図を描いて、足りないものを見つける

**オーナーの指示（2026-09-12）。**

> また既存の図もブラッシュアップするために機能を追加する調査をする
> という **PDCA** を行ってください。

回し方はこう。

1. **実物を見る**（画像検索・設計基準・標準図集）
2. **同じ図を zumen で描く**
3. **並べて、差が出たところを数える**（絵の好みではなく、**何が読めないか**）
4. **足りない道具を 1 つだけ足す**。足したら、既にある図を全部描き直す
5. **毎回、既にあるものを 1 つ以上ブラッシュアップする**（下記）

### 5 の意味 —— 細かい指摘は、まだ来ていない

**オーナーの指示（2026-09-13）。**

> 最初なので、これまで全体を通して細かいことは言っていません。
> PDCA の時に、なにか少しでも改善を入れるみたいな時に
> **徐々にブラッシュアップ**してくれたらと思っています

いま出ていない指摘は、**無いのではなく、まだ言われていないだけ。**
「言われていない ＝ 直さなくてよい」と読むと、粗いところが既定になって固まる。

**1 周につき、新しい図や道具とは別に、既にあるものを最低 1 つ良くする。**
何を直したかは、その周の報告に 1 行で出す（黙って直すと、良くなったことも伝わらない）。

直す先の探し方（上から順に見る）。

| 見る所 | 何を探すか |
|---|---|
| `inspect` の観測値 | `crossings` / `hiddenLabels` / `crowdedNames` / `overlappingText` が 0 でないもの |
| 見本を実物と並べる | **今まで「これでいい」と流した所**（線の太さ・間隔・文字の位置） |
| 検証器の警告 | 出ているのに直していないもの |
| 課題の一覧 | 小さく削れるもの（全部は無理でも、1 つ手前まで進める） |
| 文書 | 実装と食い違っている記述（**古い文書は、無い文書より悪い**） |

**「もっと大きな機能」を理由に飛ばさない。** 大きいものは次の周にも残っているが、
細かい粗さは**放置した分だけ実物から遠ざかる。**

この回し方で出てきたもの。

| 間取り | 壁・建具・矢印の有無 | `openings`・平面の描き方 |

**4 の「1 つだけ」を守る。** まとめて足すと、どれが効いたか分からなくなる。

## ずっと先の話（オーナー）

> カメラでぐるーと写真や動画をとると、その内装図がでる

**いまは作らない。** ただし、**出来上がりが `kind: placement` の正本になる**なら、
この製品の形とは繋がる —— 撮って出した図を**人が直せる**ことが、そのまま
この製品の主張（手直しが再生成で壊れない）になるため。

繋がらないのは、**写真から出た図を人が直したあと、撮り直したらどうするか**。
そこが「再生成」にあたる。**S1 と同じ問題**で、そこが解けていない道具は
「一度きりの変換器」にしかならない。

## 業界専用の表示 —— 「できる範囲」で作らない（2026-09-12。オーナーの指摘）

> **その業界専用の表示**を実現してほしい。

**そのとおりだった。** 図を道具に合わせていた。逆をやる。

**これからも、この順で作る。**

1. **実物の表示を先に決める**（記号・模様・符号・寸法の出し方）
2. **足りない道具を足す**
3. できる範囲へ図を寄せない

## コンテナ船の積付図（Bay Plan）の調査（2026-09-14。見本 89）

`.claude/rules/専門図面の調査と実装方針.md` §3 の 13 項目。
英語でも掘った（`bay plan` / `stowage plan` / `slot identification` / `ISO 9711`）。

| | 調べたこと |
|---|---|
| 1 誰が | 本船の一等航海士、ターミナルのプランナー、船社の本船担当 |
| 2 何のため | **積む場所の指示。**あわせて揚げ順・重量配分・復原性の確認 |
| 3 ノード | **スロット（セル）。**1 セル＝コンテナ 1 本。空きスロットも 1 セル |

| 10 業界記号 | `R`（リーファー）／IMDG の Class 番号／`OOG` `OH` `OW`（はみ出し） |
| 11 必須ラベル | 総重量（t）・揚地・サイズ／タイプ |
| 12 手書き | 出港間際の差し替え・追加。**紙に赤で書き込む** |

**番号の付け方**（これを外すと図として成立しない）。

- **Bay** … 船首から船尾へ。**40ft は偶数、20ft は奇数**（34 番の両隣が 33・35）
- **Row** … 中心から外へ。**中心が 00、左舷が偶数、右舷が奇数**
- **Tier** … 船倉は 02 から上へ 2 ずつ。**甲板上は 82 から**

**zumen のプリミティブでどう表したか**（道具は足していない）。

| 意味 | 使ったもの |
|---|---|
| 住所 | `at`（**位置がそのまま Bay-Row-Tier**） |
| 揚地 | `palette` ＋ `color` |
| リーファー・危険物 | `tag` |
| 空きスロット | `hatch: none` |
| ハッチカバー | `hatch: lines` の帯 |

**次に作るならこの並び** —— パレット積付図（段数・目地・はみ出し）、
トラック積載図（軸重と前後の配分）、倉庫ロケーション図は既にある（34）。

### ここで見つかった不具合

**`tag` を「路線記号」だと決めてかかっていた。** 積付図の `tag` は
リーファーと危険物の印で、揚地の符号ではない。それでも
`color-without-code` が「tag に符号が無い」と 6 件鳴った。
**見る場所を節から図ぜんたいへ変えた**（同じ周で直した）。

## 防犯カメラの視野図の調査（2026-09-14。見本 97）

| | 調べたこと |
|---|---|
| 1 誰が | 防犯設備士、店舗のオーナー、工事業者 |
| 2 何のため | **どこが写り、どこが写らないか**を決める。見積もりにも使う |
| 3 ノード | カメラ・棚・出入口・レジ・死角 |
| 4 線・接続 | **視野の扇形**（物ではないので破線） |
| 5 座標 | 位置と**向き**が意味。逆光の向きは使えない |
| 6 寸法 | **距離が段階を決める**（DORI） |
| 7 向き・角度 | **画角そのもの。** 広げるほど識別できる距離が縮む |
| 8 色 | 使わない |
| 9 線種 | 視野は破線（実線は物の輪郭） |
| 10 業界記号 | DORI（識別 250 / 認識 125 / 観察 62 / 検知 25 px/m） |
| 11 必須ラベル | カメラ番号・画素・画角・設置高・用途 |
| 12 手書き | 現地での向きの微調整 |
| 13 情報密度 | カメラ 4〜20 台 ＋ 距離の表 |

**外してはいけない考え方 —— 「写っている」と「誰か分かる」は別。**

DORI（IEC/EN 62676-4）は **1m あたり何ピクセルで写るか**で段階を分ける。

| 段階 | 画素密度 | 何が分かるか |
|---|---|---|
| 識別 Identify | 250 px/m | その人が誰かを特定できる |
| 認識 Recognise | 125 px/m | 前に見た人と同じだと言える |
| 観察 Observe | 62 px/m | 服装などの特徴が分かる |
| 検知 Detect | 25 px/m | 人か車かが分かる |

距離は **画素数 ÷（2 × 距離 × tan(画角/2)）** から出る。
4MP・画角 70° なら識別 7.3m、90° にすると 5.1m まで縮む ——
**画角を広げるほど、識別できる距離は短くなる。**

そのほかの決まり。

- **出入口を外向きに撮らない。** 逆光で顔が飛ぶ。内向きに置いて入店者を撮る
- 設置は 2.4〜3.0m。低いと手が届き、高いと顔が上から潰れる
- トイレ・更衣室は撮らない。写り込む隣地や道路はマスクする
- **視野は重ねて置く。** 重なりが無い置き方は、その隙間がそのまま死角になる

### ここで分かったこと

**扇形は、道具を足さずに描けた。**
`from` と `to` を同じ節にして `via` を並べ、`close: true` にする。

ただし **`via` を書かない自分自身への辺は、長さ 0 の線**になり、
節の真ん中に矢印の粒が出るだけだった。**知らせるものが無かった**ので足した
（`edge-self-open`）。あわせて、この書き方を `zumen_spec` の見本にも書いた ——
**書いていない書き方は、エージェントにとって存在しないのと同じ。**

| | 調べたこと |
|---|---|
| 1 誰が | PA エンジニア、舞台監督、電源とケーブルを引く人 |

| 3 ノード | スピーカー・卓・ステージボックス・モニター |

| 6 寸法 | メインからの距離。会場の広さ |
| 7 向き | スピーカーの向き。**モニターはマイクの後ろへ向ける**（正面はハウる） |
| 8 色 | 使わない |
| 9 線種 | 届く範囲は破線（物ではない） |
| 10 業界記号 | Main / Sub / Delay / FOH / モニター |
| 11 必須ラベル | 距離・遅延（ms）・指向角 |

- 計算値は出発点。**当日の気温と実際の聞こえで詰める**
- FOH は客席の中、メインの軸が交わるところ。端では判断できない
- **届く範囲は重ねる。** 重ならない置き方は、その隙間で音が痩せる
