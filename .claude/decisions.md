## D1（2026-08-28 確定）draw.io を部品として組み込む案は採らない。独立したデスクトップアプリを作る

### 経緯

先に `docs/origin/00b-壁打ち-drawio-mcp統合検討.md` で、draw.io を部品として使う案を検討した。
draw.io は OSS で、成熟していて、周辺の MCP 対応も進んでおり、
ゼロから図形エディタを書かずに済むという点で有力だった。

**この案は不採用。** 却下の理由は 2 つ。

### 却下理由 1 — そこまでの高機能を必要としないケースが多い

draw.io の強みは機能量にある。だが実際に描きたいものはサーバー構成図・
ネットワーク構成図・クラウド構成図で、そこで使う語彙は多くない。
機能の大半は使われないまま、**組み込みの制約と、その機能を前提にした UI だけが残る。**

### 却下理由 2 — デスクトップ版を持ち、既存シリーズに揃えるほうが意義がある

姉妹プロジェクトは既にデスクトップアプリの形を持っている。
同じ形に揃えると、Markdown / TSV / Git / MCP の作法をそのまま共有でき、
利用者から見て「同じ道具の一部」になる。
draw.io を埋め込むと、その内側だけ別の作法になる。

### この判断の性質（重要）

**判断軸は「できるか」ではなく「必要か」だった。**
draw.io を組み込むことは技術的には可能で、その意味では 00b の検討は正しかった。
それでも採らなかったのは、**必要とされていない機能量を抱え込むことになるから**である。

これは UX チェックリスト §0 の 2 問目
「人はなぜ今の方法をやめて、これを使うのか？」への回答そのものになっている。
draw.io を組み込んだものは「draw.io を別の皮で使う理由」を作れない。

> 00b は捨てない。**却下された案ではなく、この判断の根拠として残す。**
> 「なぜ draw.io を使わなかったのか」は必ず後から聞かれる。

## D4（2026-09-04 確定）着地点は「md-business の本文に埋め込まれた図」とする

### 決めたこと

zumen の成果物が最終的に置かれる場所を、**md-business の Markdown 文書の中**と定める。
zumen 単体で図を描いて終わりにしない。

### 根拠

PRD §2 の「動かした点 3」で md-business 連携を最後に置かないと決めていたが、
そこでは「ファイルの置き方と CLI の口を最初から意識する」までしか書いていなかった。
**着地点そのものを決めた**のがこの D4 である。

**md-business 側に、既に受け口がある。**

`apps/desktop/src/lib/markdown/fencedBlocks.ts` が、本文の囲み（```` ``` ````）を
名前で拾って別の書き方へ差し替える汎用の機構を持っている。
`mermaid` / `chart` / `data` の 3 つが、いずれもこの 1 つの口に載っている。

この機構の重要な性質は、**差し替えを DOM ではなく本文の段階で行う**ことにある
（同ファイル冒頭のコメント）。プレビューも PDF も HTML 書き出しも同じ本文を通るため、
描画経路が 1 本で済む。**「画面には出るのに書き出すと消える」が構造的に起きない。**

zumen は新しい仕組みを md-business へ足すのではなく、**この口に 1 つ名前を増やすだけ**で入る。

### この決定が S1 / D2 に課す制約（重要）

md-business には、囲みの中身の持ち方が**2 通り**すでにある。

| 形 | 前例 | 中身 |
|---|---|---|
| **同梱** | `mermaid` / `chart` | 囲みの中に定義そのものを書く |
| **参照** | `data` | 囲みの中に相対パスを書き、外のファイルを読む（`loadData.ts`） |

どちらを採るかは D2（Issue 002）の判断であって、ここでは決めない。
ただし **S1 は同梱の形を前提として測る。**

理由は、**同梱のほうが制約が厳しく、両方を満たすから**である。
同梱では文書の外に別ファイルを置けないため、**人の手直し（pin）を正本と同じ 1 本の
テキストの中に持つ**しかない。ここで保持が成立するなら、参照の形でも成立する。逆は言えない。

**人の指定を別ファイル・別レイヤに逃がす設計は、S1 では採らない。** 逃がすと
測定は通るが、埋め込んだ瞬間に成立しなくなる。

### これを止めるべき条件

- md-business 側の囲み機構が変わり、名前を増やすだけでは載らなくなった場合
- zumen の図が Markdown の囲みに収まらない大きさになり、参照の形が必須になった場合
  （その時点で D2 を「参照」で確定し、S1 の制約も緩めてよい）

### 保留だったもの → **D6 で決着**

レイアウトエンジン `elkjs` のライセンス（EPL-2.0 OR GPL-3.0-or-later）と
MIT の md-business との関係は、**D6 に移した**。
Issue 006（アイコンのライセンス）とは別の話なので、そちらへ混ぜない。

## D5（2026-09-04 確定）AI の出力を新しい正本にしない。提案として人の正本へマージする

### 決めたこと

AI が返すのは**提案**であり、正本ではない。書き換わるのは人が持っている正本のほうで、
提案からは semantics（nodes / edges / groups）だけを読む。**人の指定（`pins`）は読まない。**

### 根拠 — S1 の実測（Issue 001）

`experiments/s1/results/report.md`。7 往復で Tier A の保持は全回 100%。

決め手は REAL-1 の回。実 AI 役が正本を丸ごと書き直し、提案の側では
**コメントが全部落ち・キーの並びが変わり・`pins` の節ごと消え・ノードの並びも
入れ替わっていた**。それでも人の正本に出た差分は、AI が実際に足したノード 1 個と
エッジ 2 本の **9 行だけ**だった。

**向きを逆にしていたら、この回で全部消えていた。** AI の出力を採用する形は、
1 回目は動くように見えて、2 回目に人の手直しを消す。

### この決定が要求すること

1. **人の指定を semantics と別の節に置く。** 同じ節に混ぜると、AI が semantics を
   書き直すたびに人の指定も書き換え対象になる
2. **要素の id が安定していること。** REAL-2 で AI が `db` を `maindb` へ改名した瞬間、
   人の指定は紐づく先を失った（競合として検出はされたが、紐づけ直しはできない）。
   **id の安定は形式側で守る必要がある** → Issue 002 / D2 への入力
3. **黙って上書きしない。** 競合は適用せずに返し、人が選び、選んだ結果を正本へ書く
   （`locked`）。実行中の変数に持つと、次に開いたときに同じことを聞き直す

### これを止めるべき条件

- 提案とマージの往復が遅すぎて実用にならないと分かった場合
  （現状は計測ハーネスでの話であり、実アプリでの応答性は測っていない）
- 人の指定を semantics と別に持てない保存形式を D2 で選んだ場合。
  **その場合は D2 の側を選び直す。** この向きを捨てると S1 の結論ごと無効になる

## D2（2026-09-04 確定）保存形式は zumen 独自の YAML

- 比較と提案: `docs/specs/d2-保存形式-比較と提案.md`
- 仕様: `spec/zumen-format-v1.md`（**確定**）

### 決めたこと

正本は zumen 独自の YAML。`.zumen.yaml`、Markdown へは ```` ```zumen ```` で**同梱**する。

**「確定」は「これを根拠に実装してよい」の意味であって、「二度と変えない」ではない。**
仕様 §9 に版の上げ方がある。実地で足りない点が出たら版を上げる。
これはベースルール §15（決定の独断変更禁止）の例外ではなく、**あらかじめ決めておいた
変更の手順**である。

### 根拠

候補 5 つ（zumen YAML / Mermaid / draw.io XML / Graphviz DOT / JSON）を、
口ではなく**同じ編集を各形式で実際に行った差分**で比べた。
決め手は「人の手直しを表せるか」の 1 列だった。

判断の芯は、**潰せるリスクと潰せないリスクの取引**である。

- 独自形式のリスクは「形式の意味が実装の中にしかない」こと。**これは潰せる。**
  仕様 261 行・Mermaid 書き出し 141 行（依存は YAML パーサだけ）・適合条件をテストの形で用意した
- Mermaid / draw.io XML を正本にするリスクは「**この製品の中心機能が乗らない**」こと。
  Mermaid には人が置いた位置を書く場所が無く、draw.io XML には「人が決めた」という印が無い
  （全要素が座標を持つので `pins` の考え方自体が消える）。**これは工夫では潰せない**

**潰せるリスクのほうを引き受けた。**

### 採らなかった案とその理由

| 案 | 採らなかった理由 |
|---|---|
| **Mermaid を正本にする** | 位置・大きさ・線の曲げ方を書く場所が無い。S1 の結論が乗らない。加えて**実装は減らない** — Mermaid にラウンドトリップ可能なパーサ/シリアライザが無く、自前で書くことになる。記法が緩いので正規化も難しい |
| **draw.io XML を正本にする** | 座標は持てるが「人が決めた」という印が無い。コメントを持てない。差分が読めない（圧縮されると読めなくなる）。D1 とは別の判断として検討したうえで却下 |
| **Graphviz DOT を正本にする** | `pos` は neato 専用で階層レイアウトでは効かない。人／自動の区別も無い |
| **JSON + JSON Schema** | **コメントを持てない**。原案 §26 の 9 が最初から落ちる |

### これを止めるべき条件

- **主な使い方が「他人が作った既存の図を取り込むこと」になったとき。**
  既存形式に寄せる価値が跳ね上がる（現時点では PRD §4 が明示的に否定している）
- **md-business の囲みが参照型（外部ファイル）中心に倒れたとき。**
  Mermaid 正本 + `pins` サイドカーという折衷が現実的になる
- `pins` を別ファイルに逃がしたくなったとき（D4 の同梱が壊れる）
- Mermaid が位置指定を持つようになったとき

### 仕様の置き場所

**実装リポジトリの `spec/` に置く。別リポにはしない。**
いま分けても同期コストしか増えず、同期されない別リポの仕様は実装内のコメントより悪い
（ベースルール §10）。**切り出す条件は「第三者の実装が現れたとき」。**

### 残っている弱点（この決定を採ったうえでの宿題）

- **Git の衝突が 2 件解けていない**（2 人が別々のノードを動かす／別々のノードを足す）。
  形式では解けない（Mermaid でも DOT でも同じ）。マージドライバが要る → Issue 011
- draw.io XML 書き出しは未実装 → Issue 013

## D6（2026-09-04 確定）レイアウトエンジンは elkjs。ライセンスの扱いもここで決める

ベースルール §2 は「**採用理由を decisions.md に残していない技術は採用していないものとして
扱う**」としている。elkjs は S1 から使っているのに理由が残っていなかった。ここで書く。

### 決めたこと

自動レイアウトは **elkjs**（`elk.algorithm: layered`）を使う。

### 採用理由

- **入れ子（グループ／VPC／サブネット）を扱える。** 原案 §26 の 4 が要求している。
  対象が構成図である以上、囲みの中の配置は避けて通れない
- **階層レイアウト（layered）が構成図の形に合う。** 上流から下流へ流れる図が主
- 保守されている（0.12.0 / 最終更新 2026-07-17）

### ライセンス — 事実

| | 値 | 出典 |
|---|---|---|
| elkjs のライセンス | `EPL-2.0 OR GPL-3.0-or-later` | 同梱の `node_modules/elkjs/LICENSE.md`・`package.json` |
| md-business のライセンス | MIT | `md-business/package.json` |
| **前例** | **`@mermaid-js/layout-elk` は MIT で、`elkjs` に依存している**（0.2.3） | `npm view @mermaid-js/layout-elk license dependencies` |

EPL-2.0 は**ファイル単位の弱いコピーレフト**で、より大きな著作物への同梱を認めるかわりに、
EPL の対象部分のソースを入手可能にすることを求める。npm から取得する**未改変の
パッケージをそのまま使う**限り、対象部分のソースは公開されたままである。

### 決めたこと（ライセンス面）

**elkjs を未改変のまま依存として使う。フォークしない・ソースを取り込まない。**

- 改変すると、改変部分が EPL の対象になり、扱いが一気に面倒になる
- **`LICENSES.md` に elkjs と EPL-2.0 を明記する**（表示は安いので、やらない理由が無い）

**ただし、これは法的判断ではない。**
公開・配布の前に、**人がライセンスの最終確認を行うこと**（ベースルール §21）。
ここに書いたのは、確認を行うための事実と前例である。

### これを止めるべき条件

- **法的確認で EPL-2.0 の同梱が不可となった場合。**
  そのときは MIT の代替へ移す — `@dagrejs/dagre`（MIT / 3.1.1）または
  `dagre-d3-es`（MIT / 7.0.14）。**入れ子の扱いが弱くなるので、原案 §26 の 4 を
  どこまで諦めるかを同時に決めることになる**
- 入れ子の性能・品質が実用に足りないと分かった場合

### 移行コスト（いま測っておく）

レイアウトエンジンに触れているのは `src/layout.ts` の 1 ファイルだけで、
`Placed` 型の向こう側（描画・埋め込み・書き出し）はエンジンを知らない。
**差し替えるならこの 1 ファイル。** ベースルール §9（差し替える可能性があるものは
境界の外に出す）に従ってこの形にしてある。

## D7（2026-09-04 確定）クラウド各社の公式アイコンは同梱しない。利用者が自分で入れる

### 決めたこと

**AWS / Azure / Google Cloud / Cloudflare / Docker / Kubernetes の公式アイコンを、
zumen のリポジトリと配布物に 1 つも入れない。**

同梱するのは自作の汎用図形だけ（MIT）。公式アイコンは
`.zumen/icons/<パック名>/` に**利用者が自分で置く**。

### 根拠

調査は `docs/specs/006-図形とアイコンのライセンス.md`（Issue 006）。一次情報で確認した事実：

- **各社とも改変を明確に禁じている**（AWS「changing the proportion, color, or font」、
  Azure「Don't crop, flip, or rotate」、Docker「may not be modified, recombined」、
  Cloudflare、Google、Linux Foundation いずれも同様）
- **「第三者の作図ツールに同梱してよい」と明示的に許可した文は、どこにも無い。**
  Azure が最も明快だが、許諾の範囲は「図・研修資料・文書」での使用であって、
  ツールの素材として配ることは含まれない
- **Google Cloud の icon library ページの原文は取得できなかった**
  （本文が JS 描画）。**取れていない以上、同梱可とは書かない**

### なぜ厳しい側に倒すか

public リポジトリでは、**入れてしまうと履歴に残る**（消しても fork / clone 済みの
コピーからは消えない。ベースルール §25）。**後から緩めるのは安く、締めるのは不可能。**

### この決定が要求すること

1. **アイコンの色をいじらない。** `appearance`（仕様 §4）で色を指定されても、
   アイコンには適用しない（改変にあたる）
2. **`notice`（帰属表示）の既定値を zumen が持たない。** 持てば zumen が
   各社の条件を代弁したことになる。利用者がパックに書く
3. **パックが無い `type` は `generic` として描く。** アイコンが無いことで壊れない

### これを止めるべき条件

- 提供元が第三者ツールへの同梱を明示的に許可していると分かった場合
  （**その提供元だけを動かす。全部まとめて動かさない**）
- draw.io 書き出し（Issue 013）で、アイコン名を書くだけで図が成立すると分かった場合。
  ファイルを持たずに済むなら、この仕組みごと不要になる

## D8（2026-09-04 確定）個人情報チェックの許可リストに「アドレス 1 個」を書けるようにする

### 経緯 — CI が落ちた

commit `3c0fb12` の push で `oss-privacy-check` が落ちた。

```
NG [message-email] 3c0fb12 : n***@***.com
```

原因は **AI が commit message に付ける `Co-Authored-By:` の `noreply@anthropic.com`**。
検査は「commit message に許可ドメイン外のメールがある」として正しく検出している。
**検査の誤りではない。**

### 決めたこと

`OSS_ALLOWED_EMAIL_DOMAINS` の項目に **`@` を含めて書いたら、そのアドレスだけを許可する**
（`@` が無ければ従来どおりドメイン全体）。既定の許可リストに
**`noreply@anthropic.com` を 1 個だけ**加えた。

### 根拠

- ベースルール §25 / §32 が止めたいのは**実在の個人**の名前とメール。
  `noreply@anthropic.com` はベンダの no-reply で、個人ではない
- **ドメイン全体（`anthropic.com`）を許可すると穴が広すぎる。**
  アドレス単位なら穴は 1 個で済む。**同じドメインの別アドレスは今も検出される**
- `3c0fb12` は既に push 済みで、trailer は history に残る。
  **残るのがベンダの no-reply である以上、個人情報は漏れていない**。
  history 書き換えと force push に見合わない

### 回帰テスト

`test/oss-privacy-check.test.ts`。使い捨ての git リポジトリを作り、
**本物のスクリプトを本物の commit にかける**（外部へは繋がない）。

- `noreply@anthropic.com` は message でも追加行でも通る
- **同じドメインの別アドレスは止まる**（穴がドメインへ広がっていないこと）
- 個人のメールは止まり、**ログには原文が出ない**（マスクされている）

### これを止めるべき条件

- 許可リストの項目が増え始めたら止める。**1 個だから許した**のであって、
  「例外を足す場所」を作ったわけではない。2 個目を足したくなったら、
  commit message にメールを書かない方向を先に検討する

### 未解決 — 検査が遅い

追加行 1 行につき subshell と grep を起こすため、**未 push が溜まると数分かかる**
（今回は 13 commit / 追加 6,990 行で CI 上 3 分 10 秒）。**検出は正しい。速度だけの問題**で、
ここでは直していない。

## D9（2026-09-06 確定）利用者に見える文字列は 1 か所に集める。散らばったらテストで落とす

### 経緯

人から、AI との開発でいつも問題になる 3 点として
**多言語化・UI/UX の意識・日本語テキストの違和感**が挙がった。
どれも「気をつける」では解けない類で、**画面を書き始めてからでは間に合わない。**

### 決めたこと

**利用者に見える文字列は `src/messages.ts` にだけ置く。**
`src/` の他の場所に日本語の文字列リテラルがあると `test/messages.test.ts` が落ちる。

ロケールは `ja` / `en`。**`ja` が正本**で、`en` が追随する。
既定は `ja`。`ZUMEN_LOCALE` → `LC_ALL` → `LC_MESSAGES` → `LANG` の順に見る。

### なぜ 1 つの仕組みで 3 点に効くのか

| 挙がった問題 | この仕組みがどう効くか |
|---|---|
| **多言語化** | 画面がまだ無いうちに置いたので、足す手間はほぼ 0。後から入れると文字列を探して回る作業になる |
| **日本語の違和感** | **散らばっていると誰も全文を読まない。** 1 か所なら人が数分で通読して直せる。**文言を直すのは人の仕事**であり、ここはそのための机 |
| **UI/UX** | 同じものの呼び方が揺れない（正本／元ファイル／ソース）。**言葉の揺れは UI の分かりにくさとして出る** |

### 効かせるための条件（守らないと形骸化する）

1. **テストは文面を見ない。** 文言の中身を assert すると、人が日本語を直すたびに
   テストが落ちる。**億劫になった時点で誰も直さなくなる**ので、

   人が書いた文言を AI が勝手に整えると、直した記憶が残らない
3. **語彙は `docs/specs/文言の規則.md` の表に足してから使う。**
   規則は AI が発明したものではなく、**このリポジトリの既存の文章から観察した用法**

### 検出が働いていることの確認

見張りが空回りしていると、散らばりに気づかないまま緑になる。
`src/render.ts` に日本語リテラルを 1 行足して **red になることを実地で確認**し、戻した。
テスト側にも検出器そのものの検査を置いてある。

### UI/UX について — ここでは決めない

`DESIGN.md` は空のまま。**色・タイポグラフィ・レイアウトは AI が埋めない**
（ベースルール §11）。人が「あらかた出来たら操作性を見る」としているので、
**GUI を書くときも見た目の既定値を既成事実にしない**。
当面の作業（検証器・書き出し・マージドライバ）は画面を持たないため、ここは衝突しない。

### 2026-09-07 の追記 — **画面が抜けていた**

D9 を決めたとき、走査していたのは `src/` の `.ts` だけだった。
そのあと画面（`app/`）を作り、**日本語を直書きした。**

- 画面の文言 33 か所を文言表へ移した

### これを止めるべき条件

- ロケールが 3 つ以上に増え、1 ファイルが読み切れなくなった場合は分割する
  （**分割しても「1 か所に集める」原則は変えない**）
- 文言表が実装の都合で肥大し、人が通読しなくなった場合。
  そのときは**通読できる大きさに戻すのが先**で、規則を緩めない

## D10（2026-09-06 確定）Git のマージは構造で解く。ただし本当の衝突は残す

### 経緯

D2 の実測で、6 場面中 2 場面が **Git の行単位マージでは解けない**ことが分かっていた。

| 場面 | なぜ衝突するか |
|---|---|
| 2 人が別々のノードを動かす | 最初の `pins` を書く場所が、両者にとって同じ 1 行 |
| 2 人が別々のノードを足す | `nodes` の末尾が、両者にとって同じ位置 |

**どちらも中身はぶつかっていない。** 同じ場所へ同時に書いた、というだけ。
これは YAML の欠点ではなく、Mermaid でも DOT でも draw.io XML でも同じで、
**行で管理する以上、同じ場所への同時挿入は必ずぶつかる。形式を変えても解けない。**

### 決めたこと

**マージドライバで構造マージする**（`src/git-merge.ts`）。

- `.gitattributes` に `*.zumen.yaml merge=zumen` を置く（リポジトリ側）
- `merge.zumen.driver` の設定は**各自の手元で 1 回**（README に手順）

### 向き — ours を土台にする

**出来上がりは ours の書式を保ち、theirs の変更を構造で当てる。**
`src/merge.ts`（AI の提案を人の正本へ入れる）と同じ向きで、
**書式・コメント・並び順を持っているほうを土台にする**（D5 と同じ考え方）。

theirs の節は JSON へ落とさずそのまま置く。落として作り直すと
`{ x: 1, y: 2 }` のような書き方が展開され、**人が書いていない行の形が変わる。**

### 黙って通さない

**衝突しなければ良いドライバ、ではない。**
黙って片方を採ると、人の直しが片方だけ消え、しかも**消えたことが誰にも見えない。**

- 両方が同じ要素を別々に変えたら、**ぶつかったまま返す**
- 印は Git と同じ `<<<<<<<` 形式。独自の印にすると、
  エディタの競合表示や `git checkout --ours` が効かなくなる
- **囲むのはぶつかった要素だけ。** 前後の行を巻き込まない
  （巻き込むことが、そもそもの動機だった）

### 実測（`pnpm d2:conflict` で再生成）

| | 期待どおりだった場面 |
|---|---|
| 既定（ドライバ未設定） | **6 中 4** |
| ドライバ有り | **6 中 6** |

衝突せずに通った結果は、いずれも形式として読める（検証器で確認）。
**「2 人が同じノードを別の場所へ動かす」は、ドライバ有りでも衝突したまま**で、これが正しい。

### 設定を利用の前提にしない

**設定していない人は Git の既定へ落ちるだけで、壊れない。**
実測の「既定」列がそれを示している（従来どおり 6 中 4）。
ドライバは、複数人で同じ図を触る人への上乗せであって、必須ではない。

### これを止めるべき条件

- 構造マージが、行マージなら解けたはずのものを解けなくする場面が見つかった場合
- ドライバの設定手順が重すぎて誰も入れない場合。**そのときは手順を減らす**のであって、
  「黙って通す」方向へは緩めない

## D11（2026-09-06 確定）v0 の GUI は 8 操作。承認に紐づかない操作は作らない

### 決めたこと

承認に要る 3 つ（**A** AI が何を書き換えたか見える／**B** 人が動かしたものを AI が
戻していないか見える／**C** 戻されていたらそこだけ固定できる）から逆算して、
**v0 の操作を 8 個に限る。**

開く・保存／見る（Zoom・Pan）／1 つ選ぶ／**ドラッグして位置を決める**／
文章で頼んで提案を受け取る／**適用前に差分を見る**／**競合を選ぶ**／人の指定に印が出る。

一覧と理由は `docs/specs/005-承認のための最小GUI.md`。

### 作らないもの

リサイズ・接続の作成削除・画面上でのラベル編集・要素の追加削除・**Undo / Redo**・
複数選択・整列・図形パレット・テーマ設定。

**Undo を作らないのは手抜きではない。** 正本はテキストで Git にあるので、
取り消しは `git checkout` と `git diff` で足りる。
専用の履歴を持つと**正本と二重管理**になり、どちらが本当かが分からなくなる。

### 根拠

原案 §7 の v0 必須操作は、**既存の作図ソフトの機能一覧と区別がつかない。**
揃えることを目標にすると、機能の少ない作図ソフトが出来上がり、
draw.io を部品にしなかった判断（D1）を自分で裏切る。

ドラッグを入れたのは作図のためではなく、**保持を試すため**。
人が 1 つ動かし、もう一度頼み、戻っていないことを目で確かめる — この 1 往復が
この製品の全部（S1）で、そこに要る最小の操作がドラッグと「人の指定の印」。

### これを止めるべき条件

- 8 個の外にある操作を「使いにくいから」で足そうとしている
- 承認の 3 つに紐づかない画面を作っている
- **見た目の調整に時間を使っている**（汚くてよい、が守れていない）

**足したくなったら Issue 003 の指標が改善するかで判断する。
改善しない機能は、この製品の機能ではない。**

## D13（2026-09-06 確定）MCP に開けるのは読みと提案まで。正本を直接書ける口を作らない

### 決めたこと

| | |
|---|---|
| **CLI** | `validate` / `measure` / `svg` / `mermaid` / `drawio` / `embed` / `merge` / `merge-driver` の 8 つ |
| **MCP（範囲だけ決定。未実装）** | 読み・検査・計測・書き出し・**提案の取り込み**まで |
| **MCP に開けない** | 正本への直接の書き込み／`pins` の書き換え／**競合の決着** |

一覧と理由は `docs/specs/008-CLIとMCPの口.md`。

### なぜこの線か

**D5 の向きを、規約ではなく道具の形で守るため。**

AI が返すのは提案であって正本ではない。MCP から正本を直接書ける口を開けると、
**その口を通って D5 が崩れる。規約で「書かない」ことにしても、
書ける口があればいつか書かれる。**

書き込みを伴う場合も、通るのは `merge()` の 1 本だけにする。
`merge()` は構造上、**提案から `pins` を読まず、競合を適用せずに返す**ので、
**この口を通る限り人の指定は壊れない。**

**競合の決着を開けないのが要点。** 開けた瞬間、
**AI が自分の提案を自分で承認できてしまう**（Issue 005 / D11 と同じ理由）。

### 終了コードの考え方

**1 を返すのは「読めない」ときだけ。**

`measure` の不合格や `merge` の競合で 1 を返すと、
**CI を通すために指標を歪めたり、競合を黙って潰したりする動機が生まれる。**

### 単体で完結する

**姉妹側への依存は 0。** `src/` のどこからも md-business を参照していない。
連携は前提だが、**姉妹プロジェクトの機能として作らない。**

### これを止めるべき条件

- **MCP から正本を直接書きたくなったとき。** なぜ `merge()` を通せないのかを先に書く
- CLI の命令が 12 個を超えたとき。**覚えられない口は使われない**
- 姉妹側への依存が 1 つでも入ったとき

**ただし正本は `pnpm-workspace.yaml`。** 両方に書くとズレるので、

図が 1 つも描かれていなかった。**

同時に、見れば分かる問題が 3 つ見つかった。

- 線と矢印が地に沈んで読めない（ヘアライン用の色を線に当てていた）
- テーマに追随せず、**人の Chrome では強制ダークで潰れていた**
- 競合の一覧に「db」と出ても、**図に同じラベルの箱が 2 つあって、どちらか分からない**

**どれも「動かして見る」だけで分かるもので、人に頼む必要が無かった。**

### 決めたこと

1. **画面の確認は AI がやる。** dev サーバも headless Chrome も AI が立てる。
   `pnpm gui:check`（`scripts/gui-check.mjs`）が 8 操作を通して 23 項目を見る
2. **人へ渡すのは判断だけ** — 見た目・操作感の良し悪し、実物の貼り先での見え方、
   秘密情報の投入、push の最終確認
3. **「ビルドが通った」を動作の報告に使わない**

### 人にしかできないこと（ベースルール §29 の裏返し）

§29 は「人にしかできない工程が止まったら AI が人を呼ぶ」と言っている。
**その裏返しも同じくらい大事で、AI ができることを人へ渡さない。**

| | 誰がやるか |
|---|---|
| 立てる・開く・操作する・撮る | **AI** |
| 動くかどうかの確認 | **AI** |
| 良し悪しの判断 | 人 |
| 実物の貼り先（PowerPoint 等）での確認 | 人（アプリを持っていないと確かめられない） |
| 秘密情報の投入・push | 人 |

### これを止めるべき条件

- Chrome を前提にできない環境で開発することになった場合。
  **そのときは「確認できなかった」と言う。** 黙って通さない
- `gui:check` が遅くなって誰も回さなくなった場合。**速くするのが先**で、
  確認を人へ戻さない

## D16（2026-09-07 確定）zumen は API の鍵を持たない

### 経緯

Issue 004（生成品質の実測）を「API の鍵が要るので人の作業」として止めていた。
人から**「API の鍵？どこの API ですか」**と問われて、詰めていなかったことが分かった。

### 決めたこと

**zumen は API の鍵を持たない。** 3 通りのうち、A を採らない。

| | zumen が鍵を持つか | 採否 |
|---|---|---|
| **A. zumen が Anthropic の Messages API を直接叩く** | **持つ** | **採らない** |
| **B. MCP 経由**（D13 で決めた形） | 持たない。エージェント側が持つ | **製品としてはこれ** |
| **C. 手元の `claude` CLI を子プロセスで叩く** | 持たない。既存の認証を使う | **実測はこれ** |

### 根拠

- **D13 で「AI は MCP から提案を出す」と既に決めてある。** B なら鍵の投入が発生しない
- **鍵を持つと、置き場所・暗号化・失効・誤って commit する経路が全部ついてくる。**
  ベースルール §14 は「AI は秘密情報を作らない・置かない・貼らない」としており、
  **持たない設計にできるなら、そちらのほうが安い**
- 実測（Issue 004）は C で足りる。`claude -p` が非対話で動き、
  **既存の認証を使うので鍵は要らない**（実際に確かめた）

### この決定が要求すること

- **画面の「提案を読む」は、いまのまま**（提案の YAML を読み込む）。
  API を叩くボタンを足さない
- 実測のハーネス（`experiments/s3-quality/`）は `claude` CLI を前提にする。
  **無い環境では「測れなかった」と言って終わる。** 黙って通さない

### これを止めるべき条件

- **利用者が MCP を使えない環境しか無いと分かった場合。**
  そのときは A を検討するが、**鍵の投入は人の作業**という線は動かさない
- `claude` CLI が非対話で使えなくなった場合。実測の手段を選び直す
