# zumen 図形式 v1（仕様）

- 状態: **確定**（2026-09-04・D2）。**「確定」は「これを根拠に実装してよい」の意味であって、
  「二度と変えない」の意味ではない。** 版の上げ方は §9。実地で足りない点が出たら版を上げる
- 対象: `.zumen.yaml` ファイル、および Markdown 中の ```` ```zumen ```` 囲み

> **この文書は実装から独立して読めるように書く。**
> zumen の開発が止まっても、この文書と YAML パーサがあれば図を読み直せる、
> という状態を保つのが目的（PRD §5 の 4 問目）。
> 実装（`src/`）を読まないと分からない規則が出てきたら、それはこの文書の不足。

---

## 1. 何のための形式か

**AI が書き、人が直し、また AI が読む**ための形式である。

そのために、他の作図形式と違う要求が 1 つある。

> **人が手で決めたことと、機械が自動で決めたことを、区別して持てること。**

区別が無いと、AI が再生成するたびに人の手直しが自動配置に上書きされる。
この 1 点がこの形式の存在理由であり、他はすべてこれに従属する。

### やらないこと

- 描画の細部（色コード・線幅・フォント）を正本に持たない。**意味だけを持つ**
- 図形の網羅を追わない。対象はサーバー・ネットワーク・クラウド構成図
- 他形式の完全な相互変換を保証しない（**書き出しは行うが、往復の無損失は保証しない**）

## 2. 置き方

### 2.1 単体のファイル

```text
<名前>.zumen.yaml
```

### 2.2 Markdown への埋め込み

```text
```zumen
<この文書が定める YAML>
```
```

囲みの中身は、単体ファイルと**同じもの**である。別の書き方を用意しない。

### 2.3 図の種類（`kind`）

```yaml
kind: placement # 省略すると structure
```

| | | 置き場所を決めるのは |
|---|---|---|
| `structure`（既定） | 構成図。**何がどこへ繋がるか**が内容 | **機械** |
| `placement` | 配置図。**どこに在るか**が内容 | **人** |
| `construction` | **作図**。円と比の関係が内容（§3.6。D36） | **作図の手順**（座標を書かない） |

**これは、置き場所の出どころの指定です。**

```yaml
kind: placement
nodes:
  - id: jimu
    label: 事務室
    at: { x: 420, y: 200 } # ← 機械は並べ直さない
```

| | 書くのは | 強さ |
|---|---|---|
| `nodes[].at` | **AI が書いてよい** | 弱い |
| `pins.position` | **人だけ**（AI は書けない。§3.4） | **強い。常に勝つ** |

`label` と同じ形です —— `nodes[].label` は AI、`pins.label` は人。
**D5 の向きは、配置図でも変わりません。**

`at` が無い要素は、機械が置きます（**黙って重ねない**）。

**大きさも同じ形です。**

| | 書くのは | 強さ |
|---|---|---|
| `nodes[].size` | **AI が書いてよい** | 弱い |
| `pins.size` | **人だけ** | **強い。常に勝つ** |
| 書かなければ | ラベルから見積もる | いちばん弱い |

**大きさは構成図でも効きます**（並べ方と関係ないため）。

間取りを描かせてみて分かったことです —— **部屋の大きさが全部同じでは図になりません。**
16 畳の LDK と便所が同じ箱で出ました。

### 縮尺について

**縮尺の仕組みは持ちません。** 図の題に書けば足ります。

```yaml
title: 1 階・約 62 m²（1 マス = 910mm を 40px として）
```

寸法の単位を形式が持つと、**単位系・丸め・累積誤差を全部引き受ける**ことになります。
それは作図ソフトの仕事で、この製品の勝負どころではありません（PRD §4）。

**物差しは構成図と同じ向きです。** 当初「配置図では自力率が反転する」と考えましたが、
**それは「配置は人がやるもの」という誤った前提**でした。
AI が `at` に置けるので、「人が触った要素が少ないほど良い」がそのまま成り立ちます。

**増やすのは、測り方が増えるときだけ**です。
「立面図」「断面図」を足したくなっても、**測り方が配置図と同じなら足しません**（PRD §4）。

3 つ目の `construction` は、そこに当たりました。**座標を持たない**ので、
「置き場所を人が決めた割合」という問いが**成立しません**。
数えるのは「**人が pin した定数の数**」です（`docs/specs/003-9割の定義.md`）。

## 3. 文書の構造

最上位は写像（mapping）で、次のキーを持つ。

| キー | 必須 | 型 | 意味 |
|---|---|---|---|
| `version` | ○ | 整数 | 形式の版。v1 では `1` |
| `title` | | 文字列 | 図の題。**絵には描かないが、SVG の `<title>` と Markdown の代替文字になる** |
| `kind` | | 文字列 | **図の種類**（§2.3）。`structure`（既定）か `placement` |
| `direction` | | 文字列 | 流れる向き。`right`（既定）か `down` |
| `groups` | | 並び | 囲み（VPC・サブネット等） |
| `nodes` | ○ | 並び | 要素 |
| `edges` | | 並び | 要素どうしの関係 |
| `pins` | | 写像 | **人が手で決めたこと** |
| `review` | | 写像 | **人が見たという記録**（§3.5）。GUI だけが書く |
| `views` | | 並び | **1 枚に複数の図**（各階平面図・一般配置図・三面図）。図ごとの寸法系（§3.0.18） |

**無いキーを空で書かなくてよい。** 読み手は欠けたキーを空として扱う。
書き手は、**中身の無いキーを勝手に足してはならない**（人が書いていない行を増やさない）。

### 3.1 `nodes`

```yaml
nodes:
  - id: web01
    type: server
    label: Web 01
    group: vpc
    technology: Apache
```

| キー | 必須 | 意味 |
|---|---|---|
| `id` | ○ | 文書内で一意。**§5 の規則に従う** |
| `type` | | 種別。**下記のいずれか。** 未知の値は `generic` として描く |
| `at` | | **置き場所**（`{ x, y }`）。**配置図でだけ効く**（§2.3）。AI が書いてよい |
| `size` | | **大きさ**（`{ w, h }`）。AI が書いてよい。**構成図でも効く** |
| `tag` | | **符号**（`C1` / `2"-CS-101`）。箱の左上に小さく描く（§3.1.3）。AI が書いてよい |
| `openings` | | **建具**（扉・窓）。**配置図でだけ効く**（§3.1.2）。AI が書いてよい |
| `label` | | 表示名。無ければ `id` を使う。**空文字なら何も書かない**（名前を持たない印） |
| `technology` | | 副題（版・役割・広さ）。箱の中に小さく描く |
| `group` | | 属する `groups` の `id` |
| `radius` | | **範囲の円**（作業半径・警戒区域）。配置図でだけ描く（§3.0.5） |
| `marker` | | **印の描き方**（`box` / `circle` / `double` / `ellipse` / `diamond` / `bar` / `none`）。配置図でだけ効く（§3.0.6） |
| `hatch` | | **材料と区域の模様**（`none` / `solid` / `dots` / `lines` / `cross`）。配置図でだけ効く（§3.0.7） |
| `write` | | **縦組み**（`across` / `down`）。配置図でだけ効く（§3.0.14） |
| `align` | | **文字の寄せ**（`left` / `center` / `right`）。配置図でだけ効く（§3.0.17） |
| `symbol` | | **電気・電子の図記号**（IEC／JIS）。枠を描かず記号だけ（§3.0.10） |
| `color` | | **`palette` の鍵**。枠の線と `hatch: solid` の塗りに乗る（§3.0.13） |
| `fill` | | **`palette` の鍵**。**面だけ**を薄く敷く。枠も文字も染めない（§3.0.13） |
| `label` の改行 | | **名前を 2 行以上で書ける**（`"Shoes-in\nCloset"`）。配置図で箱に収まるときだけ積む |
| `floor` | | **どの階にあるか**（`floors` の名前）。**位置は変えない**（§3.0.16） |
| その他 | | 自由。読み手は知らないキーを**捨てずに保つ** |

**`appearance` は書かない。** 体裁は人が `pins` に書くもの（§4）で、
`nodes` に書いても効かない（検証器が `appearance-in-nodes` で知らせる）。

`type` に書ける語は次の 11 個。**うち 6 個は形が変わる**（§3.1.1）。

```
server / database / storage / cache / queue / internet
load-balancer / container / cluster / network / generic
```

**知らない語を書いてもよい**（`generic` として描かれ、値は捨てずに保たれる）。

#### 3.1.1 形

**`type` は形になる**（Issue #9）。色ではなく形で意味を持たせるのは、
**白黒でも色覚特性でも縮小でも失われない**ため（`DESIGN.md` §7）。

| `type` | 形 | draw.io |
|---|---|---|
| `database` | 円柱 | `shape=cylinder` |
| `storage` | 積み重ね | **四角へ落ちる** |
| `internet` | 雲 | `shape=cloud` |
| `cache` | 六角形 | `shape=hexagon` |
| `queue` | 仕切りのある矩形 | `shape=process` |
| `container` | 二重の枠 | **四角へ落ちる** |
| 上記以外 | 矩形 | 矩形 |

**全部に別の形を与えない。** 見分けが付くことが目的で、形を増やすのが目的ではない。

**ベンダーのロゴは持ち込まない**（D7）。AWS のアイコンを使うと
「AWS 上にある」と読まれ、自前サーバの図に使えない。

#### 3.0.1 折り返し（`wrap`）

**長い鎖を折り返すか。既定は折り返さない。**

```yaml
version: 1
wrap: true
```

折り返さないと、7 工程の業務フローが **横 2584 × 縦 124（比 20.8）** で出る。
資料に貼ると幅に合わせて縮むので、**文字が読めない。**
縦向き（`direction: down`）にしても 0.27:1 になるだけで解決しない。

| ノード数 | 折り返し無し | `wrap: true` |
|---|---|---|
| 2 | 3.42 | **3.42（折り返さない）** |
| 3 | 5.16 | 2.18 |
| 5 | 8.65 | 3.14 |
| 8 | 13.87 | 2.17 |
| 12 | 20.84 | 2.83 |

**既定にしない理由。** 折り返すと 2 行目の先頭が 1 行目の末尾より左に来るので、
繋ぐ辺が図を右から左へ戻る —— [#1](https://github.com/meta-taro/zumen/issues/1) で
報告された壊れ方（終点が最上段に来て、全高を逆流する矢印が生まれた）と**同じ絵**になる。

実際、既定にしたら `test/groups.test.ts` の 4 件が落ちた。
**落ちたテストを消さずに、既定を変えないほうを採った。**

折り返してよいかは図による —— 工程が 10 個ある業務フローなら折り返したいし、
4 個の鎖なら一直線のほうが読める。**それを決めるのは人。**

#### 3.0.2 通り芯・縮尺・方位（`grid` / `scale` / `north`）

**配置図でだけ効く。** 書かなければ描かない。

```yaml
kind: placement
scale: { mm: 15 } # 1 px = 15 mm
north: up
grid:
  x:
    - { id: X1, at: 40 }
    - { id: X2, at: 240 }
  y:
    - { id: Y1, at: 40 }
    - { id: Y2, at: 320 }
```

| キー | 意味 |
|---|---|
| `grid.x` | 縦に走る芯（左右の位置を決める）。`id` は符号、`at` は図の座標 |
| `grid.y` | 横に走る芯（上下の位置を決める） |
| `scale.mm` | **1 px が何 mm か。** これが無いと寸法の数値を出さない |
| `scale.in` | **1 px が何インチか。** こちらで書くと、**寸法がフィートとインチで出る** |
| `north` | `up` / `right` / `down` / `left` |

描かれるもの。

- **通り芯** —— 一点鎖線。建物を**貫いて**外まで伸び、両端に符号を丸で囲んで置く
- **寸法線** —— 建物の外に、内から順に「芯どうし」「総寸法」の 2 段。
  端は斜線（図面では矢印より斜線が普通）。**数値のところで線を切る**
- **方位記号** —— 右上

##### 単位は、縮尺が決める

| 書き方 | 1 px | 寸法の出方 |
|---|---|---|
| `scale: { mm: 40 }` | 40 mm | `14,000` |
| `scale: { mm: 200 }` | 200 mm | `60.0 m`（1 px が 100 mm 以上なら m）|
| `scale: { in: 1.5 }` | 1.5 インチ | **`46'-0"`** |

**環境でもロケールでも切り替わらない。正本が言う。**
同じ図に `12'-6"` と `3,800` が並ぶことはない（図ぜんたいで 1 つ）。

- フィート表記は **1 インチまで丸める。** 1/2 や 1/4 を出すのは詳細図の仕事
- **12 インチは 1 フィートへ繰り上げる**（`11'-12"` とは書かない）
- 1 フィートに満たなければインチだけ（`9"`）
- **`mm` と `in` の両方を書いたら `mm` を採る**（`scale-two-units` が知らせる）

**寸法は通り芯からしか出さない。** 部屋の箱から出すと、
壁の厚みをどちらに数えるかで値が変わり、**現場で食い違う。**
実物の図面が通り芯を基準にしているのは、そこを一意にするため。

**単位は縮尺が決める**（2026-09-14）。

| 1 px | 図 | 単位 |
|---|---|---|
| 100 mm 未満 | 間取り・伏図・断面・駐車場の区画 | **mm**（`7,000`） |
| 100 mm 以上 | 仮設計画・圃場整備・ダム・保安距離 | **m**（`45 m`） |

**1 px が 100 mm 以上の図は、1:100 より小さい縮尺。**
その縮尺の図面をミリで書く業界は無い（ダムの平面図に `200000` と出ていた）。
**数値の大きさでは決めない** —— 同じ図に `45 m` と `5,000` が並ぶことになる。

**`scale` が無ければ数値を出さない。** 知らない縮尺で数値を書くより、
出さないほうがよい。現場では、**寸法が間違っていることの害が、無いことより大きい。**

**芯が 2 本なら総寸法を重ねて書かない**（芯どうしの寸法と同じ数字になる）。

**桁を揃える空白を入れない。** 書き戻しで詰められるので §6.1 に反する
（`round-trip-changed` で落ちる。2026-09-12 に実際に踏んだ）。

| 書き方 | 書き戻すと |
|---|---|
| `at: { x: 40 }   # ← 注記` | **`#` の前の空白が 1 つに詰まる** |
| `x: [{ id: X1, at: 40 }]` | `x: [ { id: X1, at: 40 } ]`（括弧の内側に空白が入る） |
| `at:   { x: 40, y: 40 }` | `at: { x: 40, y: 40 }` |

##### `mark: tick` —— 時間軸

工程表・ガントチャート・タイムチャート。

```yaml
grid:
  x:
    - { id: 4月, at: 0, mark: tick }
    - { id: 5月, at: 30, mark: tick }
```

| | 通り芯（`code`） | 時間軸（`tick`） |
|---|---|---|
| 印 | 丸で囲んだ符号 | **名前だけ**（`4月`・`T+0`） |
| 寸法 | 芯どうしと総寸法 | **引かない** |
| 縮尺 | 要る | **要らない** |

丸で囲むと「通り芯」に見え、寸法を引くと
**`60 / 60 / 60 / 総 240` という意味のない数字**が並ぶ（名前が既に時刻を言っている）。

**作業名は、本体より左の列に置く。**
負の座標（`at: { x: -120 }`）に `marker: none` の箱を並べる —— §3.0.11 参照。

**通り芯は 1 行 1 本の並びで書く。**

**流れ形式（`{ ... }`）の中の値にカンマを入れるときは、引用符で囲む。**
YAML はカンマを区切りと読むので、囲まないと**値が黙って割れる。**

```yaml
- { id: 天端 +3,000, at: 0 }      # → id が「天端 +3」になり、0 が別の鍵になる
- { id: "天端 +3,000", at: 0 }    # 正しい
```

`2FL+3,200` のようなレベルの値でよく踏む。
**§6.1 の書き戻しの検査が `error` で止める**ので、気づかずには進めない
（2026-09-12 に実際に踏んだ）。

**目で見ても分からない。** 書き戻しの差は、目で追う種類のものではない
（`test/docs-samples.test.ts` が、文書に載せた見本を毎回検査する）。

#### 3.0.2b 書き出しと、**自分で見ること**

| 形 | 何のため |
|---|---|
| `svg` | 見せる（貼り先へ持ち出す）|
| **`png`** | **自分で見る。** 絵そのものが返る（MCP では画像として） |
| `mermaid` | 翌日読める |
| `drawio` | 翌日編集できる |

**数の検査は「読めるか」しか見ていない。**
名前が扉の弧に乗る・線が設備を横切る・扇の半径が読めない —— これらは
**絵にして見るまで分からない**（2026-09-18 に png を足した理由）。
`png` は Chrome を使う（**同梱しない**。無ければ、無いと言う）。

#### 3.0.3 壁の厚み（`wall`）

**配置図でだけ効く。`scale` が無ければ何も変えない**（mm を px にできない）。

```yaml
scale: { mm: 15 }
wall: { mm: 105, outer: 180 } # 間仕切 105・外壁 180
```

**インチでも書ける**（`scale.in` と揃える）。

```yaml
scale: { in: 1.5 }
wall: { in: 4, outer: 8 } # 2x4 の間仕切 4"・外壁 8"
```

`outer` を書かなければ、間仕切の 1.5 倍。`in` で書いたときは `outer` もインチ。

##### どれが外壁になるか

**他の箱を包んでいて、どれにも包まれていない箱**が外壁として描かれる（2026-09-18）。
平面図の外形は、囲み（`groups`）ではなく**部屋を包む 1 つの箱**で描くのがふつうだからである。

```yaml
nodes:
  # これが外壁（部屋を包み、どれにも包まれていない）
  - id: unit
    label: ""
    at: { x: 0, y: 0 }
    size: { w: 400, h: 300 }
  - id: ldk
    label: LDK
    at: { x: 0, y: 0 }
    size: { w: 200, h: 300 }
```

外形の箱を置かなければ、**全部が間仕切の太さ**で描かれる（これまでどおり）。
同じ大きさの箱は「包んでいる」と見ない（重ねて置いた板が、互いを外壁にし合う）。

**1 本線では壁に見えない。** 部屋と部屋を分ける**境界線**には見えても、
厚みのある**壁**には見えない。厚みは飾りではなく、

- **有効寸法が変わる**（芯々 1,820 の廊下は、壁厚 120 なら内法 1,700）
- **建具の幅が壁の厚みの中に収まる**ことが、見て分かる

**2 本線ではなく塗り潰し。** 実物は縮尺で描き分けられている。

| 縮尺 | 壁の描き方 |
|---|---|
| 1/50 以上（平面詳細図） | 2 本線。間に仕上げの線も入る |
| 1/100 前後（平面図・伏図） | **塗り潰し**（ポシェ） |

zumen が出す図は 1/100 前後の粗さなので、**塗り潰しのほうが実物に近い。**
2 本線にしても、この大きさでは 2 本が潰れて 1 本の太線に見えるだけで、
**描画は複雑になるのに絵は同じ**になる。

太さには上限がある（24px）。厚い壁を大きな縮尺で描くと、
**壁が部屋を食い潰す。** そこまで行くなら、それは詳細図で描くもの。

#### 3.0.4 配置図では、動線を箱の上に描く

部屋の塗りは透けないので、下に置くと**隣どうしの矢印が完全に消える。**
壁に厚みを付けたところ、避難経路の矢印が丸ごと壁の下に入った（2026-09-12）。
**避難経路図は矢印が主役**の図で、消えたら図の意味が無い。

構成図では、これまでどおり辺は箱の下（箱が辺の端を隠して、繋がって見える）。

**矢印を出すかは正本が決める。** 辺を書かなければ出ない（間取りがそれ）。

#### 3.0.5 範囲を示す円（`nodes[].radius`）

**配置図でだけ効く。** 単位は px。`scale` があれば半径を書き添える（単位は上の表のとおり）。

```yaml
  - id: crane
    label: クレーン
    tag: CR-1
    technology: 25t 吊・定格 5.0t/10m
    at: { x: 200, y: 228 }
    size: { w: 120, h: 54 }
    radius: 250
```

[#4](https://github.com/meta-taro/zumen/issues/4) の原題は**総合仮設計画図**だった。
実物に必ず入る 10 種のうち、**揚重機だけが矩形では描けなかった。**
クレーンの作業計画に要るのは、機種・定格荷重・**作業半径**・揚程・据付位置で、
**作業半径が描けないと、そのクレーンで届くかが図から読めない。**

| | 何に使うか |
|---|---|
| 仮設計画図 | クレーンの作業半径 |
| 消防設備図 | 消火器の警戒区域（**歩行距離 20m 以内**） |
| 太陽光の架台配置 | 影の離隔 |
| 設備図 | 電波・照明・スプリンクラーの到達 |

**`type` を増やす話ではない。** クレーンは円ではなく、**円はクレーンが届く範囲**で、
寸法線と同じ種類の注記。語彙は `radius` の 1 つだけで、業界が増えても増えない。

**破線で描く。** 実線は「物がある」ことを言うので、
実線にすると**届く範囲と物の輪郭が見分けられなくなる。**

#### 3.0.6 配置図での印（`nodes[].marker`）

**配置図でだけ効く。** 書かなければ矩形。

```yaml
  - id: chuo
    label: 中央
    tag: H03
    marker: double
    at: { x: 200, y: 100 }
    size: { w: 34, h: 34 }
```

| 値 | 絵 | そう描く図 |
|---|---|---|
| `box`（既定） | 矩形 | 部屋・区画・棚 |
| `circle` | 丸 | 路線図の駅、経穴、計器 |
| `double` | 二重丸 | 路線図の乗換駅 |
| `ellipse` | 楕円 | UML のユースケース |
| `diamond` | 菱形 | UML の判断（分岐） |
| `bar` | 太い帯 | UML のフォーク／ジョイン |
| `none` | 枠を描かない | 折れ点・注記だけの場所 |

**`type` を増やす話ではない。**

| | `type` | `marker` |
|---|---|---|
| 何を言うか | 「これは**円柱**だ」＝ 物の種類 | 「ここは**丸で印を付ける**」＝ 図の描き方 |
| 語の数 | 業界ごとに増える | **4 つで閉じる** |
| どこで効くか | どの図でも | **配置図だけ** |

平面図で壁を塗り潰したのと、断面で基準線を三角にしたのと同じ筋
—— **その図の決まった描き方**を、正本から選べるようにしただけ。

**値は幾何の名前だけ。** `marker: extinguisher`（消火器）のような
**意味の語は足さない。** そこを開けると設備記号の裏口になり、
D22 で断った「業界ごとに語彙が増える」がそのまま起きる。

**丸の大きさは箱の短いほうの半分。** 正本に半径を書かせない（`size` と食い違う）。
**楕円と菱形は箱いっぱい**（横長の名前が入る）。
**楕円・菱形の文字は中に、帯の文字は外に**（塗った面の中に書くと読めない）。
**名前は印の外へ出る**（丸の中には入らない）。**符号は印の中に残る**
—— 実物の路線図も、駅番号は丸の中で駅名は外。

#### 3.0.7 ハッチング（`nodes[].hatch`）

**配置図でだけ効く。** 書かなければ無地。

```yaml
  - id: rosho
    label: 路床
    technology: 設計 CBR 6・t=1,000
    hatch: lines
```

| 値 | 模様 | 何に当てるか |
|---|---|---|
| `none`（既定） | 無地 | ふつうの部屋・区画 |
| `solid` | 塗り潰し | アスコン・コンクリート・躯体 |
| `dots` | 点 | 砕石・砂・盛土 |
| `lines` | 斜線（45 度） | 地盤・路床・既存部分 |
| `cross` | 格子 | 撤去・除外・立入禁止の区域 |

**模様は飾りではない。**

- **名前を読まなくても材料が分かる。** 図面は縮小して見るもので、
  小さくすると**文字は消えるが模様は残る**
- 同じ材料が離れた場所にあることが、一目で分かる（区域の塗り分け）
- 白黒で印刷しても消えない（`DESIGN.md` §7 と同じ考え）

**値は模様の名前だけ。** `hatch: asphalt`（アスコン）のような
**材料の語は足さない**（`marker` と同じ約束）。

**`<pattern>` は使わない。** 貼り先で崩れる恐れがあるため（Issue 007）、
線と点を数えて置く。間隔には下限があり、**細かすぎて黒い面になることは無い。**

**文字の下地は抜く。** 模様の上に文字を重ねると読めないので、
文字のところで模様を切る（寸法線の数値と同じ扱い）。
`solid` の上では**文字を地の色にする**（黒地に黒い文字は読めない）。

**別の箱の模様の上に載った文字も抜く**（2026-09-15）。
以前は**自分の箱が持つ模様しか見ていなかった**ので、
帯（`solid`）の上に置いたタブ名が、同じ濃さで沈んでいた。
見るのは**その文字が丸ごと入っている箱**だけ ——
半分かかっている程度で抜くと、かえって汚くなる。

#### 3.0.8 辺の端の記号（`edges[].ends`）

```yaml
edges:
  - from: kokyaku
    to: juchu
    ends: { from: bar, to: crow }
```

| 値 | 絵 | 何に使うか |
|---|---|---|
| `none`（既定） | 何も描かない | ふつうの線 |
| `arrow` | 矢印 | 流れ・依存 |
| `bar` | 棒 1 本 | ER の「1」・端子 |
| `crow` | 鳥の足 | ER の「多」 |
| `dot` | 丸 | 接続点 |
| `dot-bar` | 丸 ＋ 棒 | ER の「0 または 1」 |
| `dot-crow` | 丸 ＋ 鳥の足 | ER の「0 以上」 |
| `triangle` | 中抜きの三角 | UML の汎化（継承）・実現 |
| `diamond` | 中抜きの菱形 | UML の集約 |
| `solid-diamond` | 塗った菱形 | UML のコンポジション |

**ER 図の多重度は、文字ではなく記号で書く。**
データベースをやる人は**端の形で読む**。文字（「1 対 多」）で書くと、
**辺が増えるほど置き場が無くなって消える**（§3.3 の `hiddenLabels`）。
記号は辺の端に必ず置ける。

**値は形の名前だけ。** `ends: one-to-many` のような意味の語は足さない
（`marker` と `hatch` と同じ約束）。

**端の記号を書いた辺には、既定の矢印を付けない。**
記号が矢印の代わりで、両方出すと**向きが二重に言われて読めなくなる。**

**`ends: { to: none }` と書くことと、`ends` を書かないことは違う。**

| | 矢印 |
|---|---|
| `ends` を書かない | **出る**（既定） |
| `ends: { to: none }` | **出ない** |

UML の関連線は**無向**なので、`ends: { to: none }` と書いて矢印を止める。
書いたのに矢印が出ると、「向きがある」という**別の意味**になる。

**鳥の足は実体へ向かって開く。** 逆に描くと矢印に見えて、
向きを言っているように読まれる（2026-09-12 に一度そう描いて直した）。

**向きは線から決める。** 正本に角度を書かせない。

#### 3.0.9 辺の線種（`edges[].line`）

```yaml
  - from: sqlrepo
    to: repo
    line: dashed
    ends: { to: triangle }
```

| 値 | 線 | 何に使うか |
|---|---|---|
| `solid`（既定） | 実線 | ふつうの関係 |
| `dashed` | 破線 | UML の実現・依存、仮設・計画線 |
| `dotted` | 点線 | 将来増設・撤去予定 |
| `double` | 二重線 | **婚姻**（相続関係説明図・家系図）、区画の境 |
| `chain` | **一点鎖線** | **中心線・対称軸・光軸・基準線・切断線**（JIS Z 8312 の細い一点鎖線） |

**端の記号が同じでも、線種で意味が変わる。**

`chain` は**実線でも破線でもない。** 線種そのものが「**これは実体ではなく基準だ**」と
言っている。刻みは通り芯（`grid`）と同じで、**1 枚の紙で基準線の見た目が割れない。**
点線で代用しないこと —— 点線は「見えない輪郭」の意味を持つので、別の意味に読まれる。

`double` は**太さでも破線でも代わりにならない。** 相続関係説明図は
**婚姻が二重線、親子が単線**と決まっていて（法務局の記載例）、
読む側はそれで見分けている。描き方は「太い線の上に地の色の細い線を重ねる」ので、
**下にあるものは隠れる**（実物の二重線も紙を占める）。

| UML | 線 | 端 |
|---|---|---|
| 汎化（継承） | **実線** | `triangle` |
| 実現（インタフェース） | **破線** | `triangle` |
| 依存 | **破線** | `arrow` |
| 集約 | 実線 | `diamond` |
| コンポジション | 実線 | `solid-diamond` |

**汎化と実現は、線種でしか区別できない。**

##### UML のクラス図では、属性と操作を描かない

`Order` の中に `- id: int` `+ save()` を並べない。

**コードに書いてあるものを図へ写すと、コードが変わった瞬間に図が嘘になる**
（PRD §1。この製品が向き合っているのは、まさにその腐り方）。

zumen が描くのは**関係**。属性はコードが正本で、図はそれを繰り返さない。

#### 3.0.10 電気・電子の図記号（`nodes[].symbol`）

**配置図でだけ効く。** 書かなければ記号は出ない。

```yaml
  - id: r1
    label: R1
    technology: 330Ω
    symbol: resistor
    at: { x: 100, y: 0 }
    size: { w: 80, h: 40 }
```

描ける記号は 14。**IEC／JIS の形**（抵抗は長方形。ジグザグの ANSI 形は採らない）。

```
resistor / variable-resistor / capacitor / polarized-capacitor / inductor
diode / led / battery / source / ground / switch / fuse / lamp / cell
```

- `battery` は**長短の組を 2 つ**（JIS の電池）、`cell` は**乾電池 1 個**（長短 1 組）。
  小学校の理科の回路図は `cell` を使う —— `battery` を 2 つ並べると、
  **紙の上では電池 4 個**に見えて、直列と並列を教える図が嘘になる

- **枠は描かず、記号だけを描く。** 抵抗に枠は無い
  （枠があると「箱の中に部品がある」ように見える）
- **部品名と値は記号の脇へ出る**（実物の回路図もそう）
- **記号は足（端子）の位置を自分で知っている。**
  2 本足の部品は、辺が近いほうの足へ自動で繋がる。正本に何も書かなくてよい
- **配線は自動で直角に曲がる。** 斜めの線は配線に見えず、追えない
- 接地は**箱が横長でも縦向き**（横向きの接地記号は無い）

##### `type` を増やす話ではない

D22 が心配したのは「**同じものを違う語で書く人が増えて差分が読めなくなる**」こと。

| | `type` を増やす | `symbol` |
|---|---|---|
| 語を決めるのは | **こちら**（勝手に足せる） | **規格**（IEC 60617 / JIS C 0617） |
| 同じものを違う語で書けるか | 書ける（`server` と `host`） | **書けない** |
| `type` の 11 語 | 増える | **増えない** |

ISA のタグ（`TIC-101`）や WHO の経穴番号（`LU-1`）を `tag` に受け入れたのと同じ筋。

##### 止める条件

記号は際限なく増やせる（JIS C 0617 は 1,900 記号）。
次のどれかに当たったら、**そこで止めて人へ返す。**

1. **1 つの図で 20 記号を超えて要求されたとき。**
   それは「回路図を描く道具」を作り始めている（専用ソフトの領域）
2. **記号の中に文字を入れろと言われたとき**（IC のピン番号表など）。
   それは図ではなく表
3. **同じ記号を業界ごとに違う形で描けと言われたとき**（ANSI と IEC の混在）。
   どちらか一方に決める（ここは IEC／JIS）

##### まだ描けないもの

**トランジスタとオペアンプ。** 足が 3 本以上あり、**どの足に繋ぐかを書く場所が無い**
（`from: q1.b` のような書き方が要る）。

#### 3.0.11 負の座標

**原点が左上だとは限らない。**

工程表は**本体より左に見出しの列**を置き、座席図も列名を左に置く。
`at: { x: -120 }` と書ける。

SVG に負の画用紙は無いので、**負があるときだけ図ぜんたいをまとめてずらす**
（相対の位置関係は変わらない。正本の値は動かさない）。

**負が無ければ 1 px も動かさない。**
人が `pins.position` に書いた座標がそのまま出ることは、この製品の保証
（判定基準 3.1）。**近いだけで動かしてはいけない。**

> 1 回目は**負の座標が画用紙の外へ落ちて消えた**（右下の端だけを測っていた）。
> 2 回目は直しすぎて、**原点から 24px 以内のものまで動かした**

#### 3.0.12 辺の太さ（`edges[].weight`）

```yaml
  - from: nishi
    to: sakura
    weight: thick
```

| 値 | 太さ | 何に使うか |
|---|---|---|
| `thin` | 1px | 補助線 |
| `normal`（既定） | これまでどおり | ふつうの線 |
| `thick` | 5px・**角と端を丸める** | 路線図の路線 |

**値は太さの名前だけ。** `weight: 5` のような数は受けない ——
数を許すと正本ごとに太さがばらけて、**図の見え方が揃わなくなる。**

##### 日本の路線図を描くとき

実物の決まりごと。

| | |
|---|---|
| 線の角度 | **水平・垂直・斜め 45 度のみ** |
| 駅の識別 | **駅ナンバリング**（路線記号＋番号）。色と番号で読む |
| 線 | 太く、**角を丸く** |
| 乗換駅 | 駅名を白枠に収める |

- **45 度は座標で書く**（`at` の差を縦横で等しくする）
- **駅番号は `tag`、駅名は `label`。**
  印の中に置けるのは 1 つだけで、**符号があるなら中はそれのもの**
  —— 実物の路線図も、丸の中は駅番号で駅名は外
- 乗換駅は `marker: double`

色は §3.0.13（`palette`）で付ける。**色と駅ナンバリングの両方**で読ませること
—— 実物の東京メトロもそうしている（`G-09` の `G` とオレンジ）。

#### 3.0.13 路線の色（`palette` ／ `nodes[].color` ／ `edges[].color`）

```yaml
version: 1
kind: placement
# H が本線、S が南北線。鍵は路線記号そのもの。
palette:
  H: "#0072bc"
  S: "#e5171f"
nodes:
  - id: nishi
    label: 西ヶ丘
    # 路線記号（H01 の H）が palette の鍵と揃っている。
    tag: H01
    color: H
    marker: circle
    at: { x: 0, y: 0 }
    size: { w: 34, h: 34 }
  - id: sakura
    label: 桜台
    tag: H02
    color: H
    marker: circle
    at: { x: 120, y: 0 }
    size: { w: 34, h: 34 }
edges:
  - from: nishi
    to: sakura
    color: H
    weight: thick
```

##### なぜ色を入れたか（`DESIGN.md` §7 の例外）

`DESIGN.md` §7 は「**色ではなく形で意味を持たせる**」と決めている。
白黒で刷っても、色覚特性でも、縮小しても失われないため。

**色が記法そのものである業界では、その決まりが優先される。**
日本の路線図では色が路線の名前で（銀座線はオレンジ、丸ノ内線は赤）、
「オレンジの線」と言えば銀座線のこと ——「**色を落とすと名前が消える**」。
同じことが配管の識別色（JIS Z 9102）・電線の相色・危険物の標識にもある。

##### zumen は色を持たない

**正本が色を決める。** 銀座線のオレンジを zumen が覚えていると、
事業者が色を変えた日から嘘になる。`palette` に書いてあるものだけを使う。

| | |
|---|---|
| 書き方 | `#rrggbb` だけ（3 桁も色名も受けない） |
| 鍵 | **路線記号そのもの**にする（`H` / `G` / `M`） |
| 乗る所 | 枠の線・辺の線・`hatch: solid` の塗り。**文字には乗らない** |
| `palette` に無い鍵 | 色を付けない（`color-unknown` で知らせる） |

##### 線の色（`color`）と、面の色（`fill`）

**別のものとして書く。** 2026-09-18 に `fill` を足した。

```yaml
palette:
  # 居間・食堂・台所
  LDK: "#e8a33d"
  # 浴室・洗面・便所
  水まわり: "#3d9ae8"
nodes:
  - id: ldk
    label: LDK
    # 面だけが色になる。壁は墨のまま。
    fill: LDK
```

| | `color`（線） | `fill`（面） |
|---|---|---|
| 乗る所 | 枠・辺・`hatch: solid` の塗り | **面だけ** |
| 濃さ | そのままの色 | **地の上へ薄く敷く**（不透明度 0.16） |
| `color-faint`（3:1） | **当たる** | **当たらない**（線ではないので沈まない） |
| `color-without-code` | 当たる | **当たる**（色だけに頼らせないのは同じ） |

**なぜ `color` を流用しないか。** `color` は枠の線に乗る。
淡い色を `color` に書くと、**枠（＝壁）まで淡くなって消える。**
壁が消えた間取り図は、間取り図ではない。

**なぜ薄く敷くのか。** 面は地を置き換えない。地の上へ薄く敷く。
こうすると同じ正本から、ライトでは淡い色、ダークでは沈んだ色が出て、
**どちらの地でも上の文字がそのまま読める**（不透明で塗ると、片方で必ず潰れる）。

実物では、**販売図面の居室と水まわりの色分け**・工程表の工区・
区画図の用途がこれ（見本 166）。

##### 方位の置き場所（`north.at`）

方位は語だけでも書けるが、**置き場所を足して書ける**（2026-09-18）。

これまでどおり、紙の右上へ置く。

```yaml
north: up
```

置き場所を選ぶ（図のそばへ寄せる）。

```yaml
north: { face: up, at: { x: 700, y: 560 } }
```

**足した理由。** 印は紙の右上に置かれる。図が紙いっぱいならそれでよいが、
**右半分が表**の紙では、印が図から遠く離れて浮く（見本 166・173）。
実物の販売図面は、**必ず図のそば**に小さく置いてある。

向きの語は同じ 4 つ（`up` / `right` / `down` / `left`）。
`at` が数でなければ、**紙の右上へ戻す**（図は出る）。

##### 名前を 2 行で書く（`label` の中の改行）

**実物の図面は、部屋の名前を積む。** `Shoes-in / Closet`、`Walk-in / Closet`、
`Living Dining / Room` —— 横へ伸ばすと部屋からはみ出す名前を、**折って収める**。

```yaml
nodes:
  - id: sic
    label: "Shoes-in\nCloset"
    at: { x: 0, y: 0 }
    size: { w: 80, h: 50 }
```

| | |
|---|---|
| 幅の測り方 | **いちばん長い行**で測る（つないだ長さではない）|
| 積む場所 | **配置図で、箱の中に収まるときだけ** |
| 高さが足りない | これまでどおり**外へ出し、1 行に戻す**（枠を突き抜けさせない）|
| 縦組み・回した字・繋いだ字 | 改行は**空白に潰す**（行の意味が変わるため）|
| 書き出し | draw.io は `<br>`、Mermaid は空白 |

##### 面をその色で塗り潰す（`fill` ＋ `hatch: solid`）

**薄く敷いたのでは足りない図がある。** モザイクの割り付け図（見本 170）は
**面が中身そのもの**で、1 マスの色が「何色の部品を置くか」の指示になっている。

`hatch: solid`（塗り潰し）と組み合わせたときだけ、**面をしっかり塗る**。
**語は足していない** —— すでにある 2 つの語の組み合わせで言えている。

| 書き方 | 面 | 枠 |
|---|---|---|
| `fill: X` | **薄く敷く**（0.16） | 墨 |
| `fill: X` ＋ `hatch: solid` | **塗り潰す**（0.82） | 墨 |
| `color: X` ＋ `hatch: solid` | 塗り潰す（0.82） | **その色** |

**塗りの上の文字は、その塗りの明るさで決まる。**
濃い塗りの上では地の色、淡い塗りの上では墨 ——
見るのは「塗り潰しかどうか」ではなく、**その塗りから遠いインクはどちらか**。

##### 色だけに頼らせない（4 つの警告）

| 符号 | いつ出るか | なぜ |
|---|---|---|
| `color-unknown` | 鍵が `palette` に無い | 色が付かないまま出る |
| `color-not-hex` | **`palette` の値が `#rrggbb` でない**（`#a33`・色名） | 鍵はあるのに色が付かない。**鍵のせいだと誤解させない** |
| `color-faint` | **ライトとダークの両方の地**で 3:1 未満（**線に使う鍵だけ**） | **地に沈んで線が消える** |
| `color-without-code` | **鍵が図のどこにも文字として出ていない** | **色だけで示している** |

どれも警告で、図は出る。**止めない**のは、白黒で読めない図でも
「今すぐ貼りたい」ことがあるため。ただし黙って通しはしない。

##### 実在の色は、下限を割ることが多い

実測（2026-09-14）。**実在の路線色は、白地か暗い地のどちらかで 3:1 を割るものが多い。**

| 路線 | 色 | 白地 | 暗い地 |
|---|---|---|---|
| 山手線 うぐいす | `#9ACD32` | **1.88** | 10.16 |
| 阪神 | `#FFE200` | **1.30** | 14.69 |
| 阪急 マルーン | `#8B0000` | 10.01 | **1.91** |
| 東京メトロ 日比谷線 シルバー | `#8F8F86` | 2.83 | **—** |

**このとき色を作り変えない。** 変えた時点で、それは別の路線の色になる
（`palette` を入れた理由そのものが消える）。

警告は正しい —— 実物もその色だけでは読めないので、
**駅ナンバリングと駅名を併記している。** 色だけに頼っていないことは、実物でも守られている。

#### 3.0.15 辺の通り道と、その丸め方（`edges[].via` ／ `edges[].curve`）

**配置図（`kind: placement`）でだけ効く。**

```yaml
version: 1
kind: placement
arrows: false
nodes:
  - id: st
    label: 起点
    marker: circle
    at: { x: 40, y: 280 }
    size: { w: 32, h: 32 }
  - id: en
    label: 終点
    marker: circle
    at: { x: 440, y: 120 }
    size: { w: 32, h: 32 }
edges:
  - from: st
    to: en
    curve: smooth
    weight: thick
    via:
      - { x: 180, y: 300 }
      - { x: 300, y: 140 }
```

| 値 | 描き方 | 何に使うか |
|---|---|---|
| `none`（既定） | 折れ線 | ふつうの線 |
| `smooth` | **通り道を通る曲線** | 道路の平面線形・河川・庭園の園路・配管の曲がり |

- **`via` は通る点。** 書いた順に通り、**両端は箱の縁で切る**
- **`smooth` は点の上を通る。** 近くを通るだけにしない ——
  「ここを通る」と書いたものを外したら、書いた意味が無い
- **2 点しかなければ直線。** 丸める角が無い

##### 閉じた輪の中を塗る（`edges[].hatch`）

**閉じた辺には `hatch` が書ける**（2026-09-15）。池・敷地・区画のように、
**輪郭ではなく面**を表す図で要る。値は節の `hatch` と同じ
（`none`（既定）/ `solid` / `dots` / `lines` / `cross`）。

```yaml
edges:
  - from: p0
    to: p17
    curve: smooth
    close: true
    hatch: dots
    via:
      - { x: 641, y: 344 }
      - { x: 459, y: 396 }
```

**閉じていない辺では効かない**（面が無いので塗りようがない。`edge-hatch-ignored`）。
塗りは**線より先に描く**ので、輪郭は模様の上に残る。

##### 閉じた形を描く（扇形・輪郭）

**`from` と `to` を同じ節にして、`via` を並べ、`close: true`**（2026-09-14）。

```yaml
edges:
  # from と to を同じ節にする
  - from: cam
    to: cam
    close: true
    line: dashed
    ends: { from: none, to: none }
    # 弧の上を刻んだ点
    via:
      - { x: 120, y: 180 }
      - { x: 200, y: 150 }
      - { x: 280, y: 180 }
```

カメラの視野・照明の照射・立入禁止の範囲のような、
**節から広がる閉じた形**がこれで描ける（見本 97）。

**`via` を書かない自分自身への辺は、長さ 0 の線**になり、
節の真ん中に矢印の粒が出るだけになる（`edge-self-open` で知らせる）。

##### `via` と `pins.waypoints`

**`nodes[].at` と `pins.position` の関係と同じ。**

| | 誰が書くか | 何を言うか |
|---|---|---|
| `via` | **正本（AI も書く）** | この線はここを通る（内容） |
| `pins.waypoints` | **人だけ** | いや、こう通してほしい（上書き） |

**両方あれば人が勝つ**（§3.4）。曲線でもこの保証は変わらない。

##### 輪を閉じる（`close`）

```yaml
  - from: p0
    to: p17
    curve: smooth
    close: true       # 最後から最初へ戻る
    via: [ ... ]
```

池・陸上競技場のトラック・ロータリー・車両限界・車の外形。
**輪郭が閉じていることが「面」の意味そのもの**で、1 区間でも開くと面に見えない。

- **継ぎ目でも滑らか。** 端の制御点を輪の反対側から取る
- **閉じた輪に矢印は付けない。** 矢印は「こちらへ向かう」意味だが、輪は出発点へ戻る
- **面の塗りは入らない。** 輪郭だけ —— 実物の庭園平面図も、池は輪郭と「池」の字で足りる

##### 曲線でしか描けないもの

課題 2 は「**代用できるうちは入れない**」で保留していた。
2026-09-13 に代用できない図が出た ——
**道路の平面線形は「どこで曲がるか」が図の中身そのもの**で、
直角で代用すると別の道になる。河川・庭園の園路も同じ。

**閉じた曲線は `close` で描ける**（上）。**面の塗りはまだ無い** ——
面どうしが重なって「どちらが上か」を言いたくなったら、そこで考える。

#### 3.0.16 階と、階をまたぐ動線（`floors` ／ `nodes[].floor` ／ `edges[].vertical`）

**配置図（`kind: placement`）でだけ効く。**

```yaml
version: 1
kind: placement
# floors は下から上へ並べる。名前は正本が決める。
floors:
  - B1
  - 1F
nodes:
  - id: gate
    label: 改札
    floor: 1F
    at: { x: 40, y: 40 }
    size: { w: 120, h: 40 }
  - id: es1
    label: ES
    floor: 1F
    at: { x: 200, y: 40 }
    size: { w: 40, h: 40 }
  - id: esb
    label: ES
    floor: B1
    at: { x: 200, y: 240 }
    size: { w: 40, h: 40 }
edges:
  - from: es1
    to: esb
    vertical: escalator
```

- **階の枠と階名は機械が描く。** その階の箱をぜんぶ囲む
- **箱は 1 px も動かない。** `floor` は「どの枠に属するか」を言うだけ
- **階に属さないもの**（凡例・注記）は `floor` を書かない。どの枠にも入らない

##### 階の名前は正本が決める

`B2` / `1F` / `M2`（中 2 階）/ `ロビー階` —— **建物ごとに違う。**
こちらは名前を持たず、**並び順だけ**を `floors` から受け取る（`palette` と同じ筋）。

| 符号 | いつ出るか |
|---|---|
| `floors-missing` | `floor` を書いたのに `floors` の一覧が無い |
| `floor-unknown` | 一覧に無い階（枠が描かれない） |

##### 縦動線の語は JIS が決めている

| 値 | |
|---|---|
| `none`（既定） | ふつうの線 |
| `stair` / `escalator` / `elevator` | **JIS Z 8210（案内用図記号）**の語 |

決めているのは我々ではない —— `symbol` を IEC 60617 へ委ねたのと同じ筋。
**図記号そのものはまだ持っていない**ので、描くのは文字。

**同じ階どうしを結ぶと知らせる**（`vertical-same-floor`）——
階をまたがないものは縦動線ではない。

##### 3D はここから先（D26）

**3D は別モードの「描き手」**で、正本は 1 つのまま。
`floors` と `vertical` があれば、2D は各階を並べ、3D は同じ正本を高さ方向に積める。
**「下の階が透けて見える」は描き手の表現**であって、正本の話ではない。

#### 3.0.14 縦組み（`nodes[].write`）

**配置図（`kind: placement`）でだけ効く。**

```yaml
  - id: nm3
    label: 西中島南方
    technology: にしなかじまみなみがた
    marker: none
    write: down
    at: { x: 200, y: 260 }
    size: { w: 34, h: 110 }
```

| 値 | 組み方 | 何に使うか |
|---|---|---|
| `across`（既定） | 横組み | ふつうの図 |
| `down` | **字を 1 つずつ上から積む** | 路線の駅名一覧・停車駅案内図 |

- **副題（`technology`）は右の列へ、小さく**（ふりがなの定位置）
- **ラテン文字だけは寝る**（時計回り 90 度。JIS X 4051 の横倒し）。
  **文字列ぜんたいで決める** —— 1 文字ずつ見分けると「JR 線」がばらばらの向きになる
- **入らなくても消さない。** 箱の大きさは正本が決める

##### 回す（`along`）のとは別

`along`（帯に沿って縦へ）は**寝かせる**。用水路や廊下の名前で自動的に選ばれる。
**実物の路線図は寝かせていない** —— 字が上を向いたまま積んである。
駅の間隔を詰めても隣の駅名とぶつからないので、何十駅でも 1 枚に並ぶ。

#### 3.0.17 文字の寄せ（`nodes[].align`）

**配置図（`kind: placement`）でだけ効く。**

```yaml
  - id: note1
    label: ・1 つの閉塞区間に入れる列車は 1 本だけ
    marker: none
    align: left
    at: { x: 1090, y: 300 }
    size: { w: 530, h: 24 }
```

| 値 | 寄せ先 | 何に使うか |
|---|---|---|
| `left` | 左端へ | **注記を何行も並べるとき**・表の見出し列 |
| `center`（既定） | 中央 | 部屋名・駅名・ふつうの箱 |
| `right` | 右端へ | 数量・寸法の列 |

zumen の文字は長いあいだ**すべて中央寄せ**だった。箱の中の名前はそれでよく、
部屋名も駅名も中央にある。**注記だけは違う** ——
行の長さが揃わないので、中央に置くと**行ごとに左端がずれ**、箇条書きに見えない。

- **枠のある箱では、線から少し内へ入れて書く**（6px）。
  **印の無い箱（`marker: none`）では入れない** —— 枠が無いのだから、
  書き手が置いた `at.x` がそのまま行頭であってほしい
- **縦組み（`down`）・回した字（`along`）・箱の外へ出した名前では効かない。**
  どれも「左」の指すものが変わる。分からない所では既定のまま
- **既定は `center`。** 書かなければ、いままでと同じ絵が出る

#### 3.0.18 1 枚に複数の図（`views`）

**配置図（`kind: placement`）でだけ効く。** 書かなければ、これまでどおり紙ぜんたいで 1 つの図。

```yaml
kind: placement
views:
  - id: upper
    title: 上甲板（Upper Deck）
    at: { x: 60, y: 60 }
    size: { w: 980, h: 150 }
    scale: { mm: 120 }
    grid:
      x:
        - { id: FR.0, at: 60 }
        - { id: FR.40, at: 420 }
        - { id: FR.80, at: 780 }
  - id: second
    title: 第 2 甲板（Second Deck）
    at: { x: 60, y: 380 }
    size: { w: 980, h: 150 }
    scale: { mm: 120 }
    grid:
      x:
        - { id: FR.0, at: 60 }
        - { id: FR.40, at: 420 }
```

| キー | 必須 | 意味 |
|---|---|---|
| `id` | ○ | 図の名前（機械が読む）。**同じ id を 2 つ書かない** |
| `at` | ○ | 図が占める矩形の左上（`{ x, y }`） |
| `size` | ○ | 矩形の大きさ（`{ w, h }`） |
| `title` | | 絵に描く図の名前（「上甲板」「1 階平面図」）。**書かなければ描かない** |
| `grid` | | **その図だけの通り芯**（§3.0.2 と同じ書き方） |
| `scale` | | **その図だけの縮尺。** 書かなければ図ぜんたいの `scale` |

**節（`nodes`）は `views` に属さない。** 座標で置く図なので、
どの図の中にあるかは座標が決めている。`views` が持つのは**寸法系だけ**。

##### なぜ要るか

1 枚に 2 つの図を置くと、`grid` と `scale` が図ぜんたいに 1 組しかないため
**通しで測ってしまう。** 駅の構内図（見本 45）で
**「2 階を合わせた全長 82,000」という意味のない数字**が出た。
通り芯も 2 階分を貫いた。

`views` を書くと、

- **通り芯はその図の枠の中だけを走る**（隣の図を串刺しにしない）
- **寸法の鎖と総寸法は、その図の芯だけで測る**
- **縮尺を図ごとに変えられる** —— 全体図 1/200 の横に詳細図 1/20 を置ける
- 図の名前が、その図の下に出る

##### 1 枚に複数の図が要る場面

| | |
|---|---|
| 各階平面図 | 1F・2F・B1F を並べる |
| 船の一般配置図 | 甲板ごとに 1 枚ずつ積む |
| 三面図 | 正面・側面・平面 |
| 展開図 | 室内の四面 |
| 全体 ＋ 詳細 | 横断図に舗装構成を添える |

##### 図の下と左右を空ける

**図の下には、通り芯の符号（90 px）と図の名前（116 px）が出る。**
そこへ次の図や注記を置くと重なる。**130 px 以上空けること。**

左右も同じで、**符号は図の両側に出る** ——
1 枚に 2 つ横へ並べるなら **260 px は離す。**

**数の検査は鳴らない。** `overlappingText` は節の文字どうししか見ていないので、
符号・寸法の数値・図の名前は数えていない
（`test/paper.test.ts` の「文字どうしが重なっていない」が書き出した SVG で見ている）。

##### まだ無いもの

**図どうしの寸法が通っているかは見ていない。**
三面図では、同じ部材の高さが正面図と側面図で一致していなければならない。
これは「図ごとに測る」より重く、**図どうしの整合を機械が見る**話になる。

#### 3.1.2 建具（`openings`）

**配置図（`kind: placement`）でだけ効く。** 間取り図を実物と並べたとき、
いちばん大きく違ったのが**建具が無いこと**だった（2026-09-12。人の指摘）。
扉があることを絵で言えないと、間取り図は間取り図にならない。

```yaml
  - id: ldk
    label: LDK
    at: { x: 40, y: 40 }
    size: { w: 320, h: 280 }
    openings:
      - { kind: window, side: top, at: 0.25, width: 90 }
      - { kind: door, side: bottom, at: 0.83, width: 70 }
```

| キー | 既定 | 意味 |
|---|---|---|
| `kind` | ○ | `door` / `slide` / `window` / `double` / `open` |
| `side` | ○ | `top` / `right` / `bottom` / `left` |
| `at` | `0.5` | 辺のどこか（0〜1） |
| `width` | `36` | 幅（px） |

| `kind` | 絵 |
|---|---|
| `door` | 片開き戸（戸と開き勝手の弧） |
| `double` | 両開き戸（弧が 2 つ） |
| `slide` | 引き戸（ずらした 2 本の平行線。**弧は無い**） |
| `window` | 窓（細い 2 本線） |
| `open` | 開口（**壁が無いだけ**。記号を描かない） |

**建具は壁に開く穴**なので、まず壁を消してから記号を描く。
`kind` と `side` が既定の語でなければ、その建具は**黙って落とす**
（描けないものを描いたことにしない）。

**設備（浴槽・便器・流し）と表題欄は入れない。**
建具は壁の話の続きで済むが、設備は**物の形**で、入れ始めると `type` が
30 語を超える。表題欄は図ではなく用紙の話で、貼り先が持っている。

> **訂正（2026-09-12）。** ここには「通り芯・寸法線も入れない」と書いてあったが、
> **取り消した**（§3.0.2）。オーナーから
> 「工事現場では使えない。**不動産の間取り図レベル**」と指摘され、そのとおりだった。
> **寸法が無い図では、何も建てられない。**

#### 3.1.3 符号（`tag`）

**業界ごとの専門性は、形ではなく符号で表されている**（D22）。

| 業界 | 符号の例 |
|---|---|
| 建築・構造 | `C1`（柱）`G1`（大梁）`B1`（小梁）`S1`（床）`F1`（基礎）`W1`（壁） |
| 配管（P&ID） | `P-101A`（ポンプ）`TK-101`（タンク）`2"-CS-101`（ライン番号） |
| 電気 | `LBS-1`（開閉器）`T-1`（変圧器）`MCC-1`（動力盤） |
| 工場 | 工程番号・設備番号 |

`C1` は**円柱の絵ではなく、矩形の中に書く 2 文字**。
一級建築士が図面を読むとき見ているのは部材の形ではなく、
**符号と、符号表（断面リスト）との対応**。

```yaml
  - id: c1a
    label: 柱
    tag: C1
    technology: 700×700
```

**`label` の代わりではない。** 名前と符号は別のもので、図面は両方を出す。
符号は**箱の左上**に置く（中央のラベルと重ねない）。読み手は符号だけを
拾って表と突き合わせるので、**中央に混ぜるとその拾い読みができなくなる。**

**`type` は増やさない。** 業界が増えても 11 語のまま。
語彙が増えるほど、同じものを違う語で書く人が増え、**差分が読めなくなる**
（[#6](https://github.com/meta-taro/zumen/issues/6) の報告者が警告した広がり方）。

#### 3.1.4 入らない文字の置き方

**配置図では、箱の大きさを人と AI が書く**ので、**文字が入らない箱が出る。**
構成図では起きない（箱の大きさをラベルから決めるので、必ず入る）。

置き先を 5 段で選ぶ。

| | 置き方 | そうなる図 |
|---|---|---|
| 1 | そのまま中へ | ふつうの部屋 |
| 2 | 名前と副題を**1 行に繋いで**中へ | 通路・農道（背が低い） |
| 3 | 名前は中へ、**副題を横に回して**添える | 駐車場の区画（`W1`／`車椅子 3,500`） |
| 4 | 帯に沿って**縦へ** | 用水路・廊下（横に入らない） |
| 5 | 箱の**外へ** | それ以外 |

**5 のときは、当たりを見る。** 上下を試し、**他の箱にも、先に置いた文字にも
当たらない**ほうを選ぶ。図の外へ出る側は先に落とす（`y` が負になると消える）。

**どこも空いていなければ、いちばん当たりの少ない所へ置いて、
`zumen_inspect` の `crowdedNames` へ id を返す。**

**消さない。** 辺のラベルは消してよいが（どこへ繋がるかは線で分かる）、
**名前は線では分からない。** 部屋の名前が消えるのは、重なるより悪い。

**中に収まった文字どうしの重なりは、`overlappingText` へ返す**（2026-09-14）。
**`validate` も、配置図なら置いてみて同じものを見る**（`text-overlap`）。
正本だけを読んでいると「書いたのに読めない」状態が分からず、
`zumen_inspect` を叩けるエージェントにしか見えていなかった。
`crowdedNames` は外へ出した名前を、`overlaps` は箱を見ている。
**箱の重なりは意図のことがある**（枠の中に節を入れる、盤の上に石を置く）が、
**文字の重なりはほぼ必ず間違い**なので分けて数える。

よく出るのは**器の名前**。`Header` のように中身を持つ箱は、
名前が中央へ来て子の名前に乗る。**器の名前は端の欄へ出すこと。**

#### 3.1.5 描く順

**配置図では、大きいものから先に描く。**

箱の塗りは透けないので、後に描いたものが前に出る。
伏図でスラブが正本の後ろにあり、**大梁と柱の線をスラブが塗り潰した。**
間取りでも、広い部屋が狭い部屋の壁を消す同じ壊れ方になる。

構成図では並べ替えない（箱が重ならない）。
**正本の順序は、読み手が意味を持たせている可能性がある。**

**形によって箱の寸法が変わる**（円柱は上下、六角形は左右に余分が要る）。
`src/shapes.ts` の `growFor()` が返す分を配置が足す。
MCP では `zumen_spec` が同じ一覧を返す。

**`nodes` の並び順には意味がある。** 人が読む順序であり、書き手は理由なく並べ替えない。

### 3.2 `edges`

```yaml
edges:
  - from: web01
    to: db
    label: replication
    protocol: HTTPS
```

`from` / `to` は `nodes` の `id` を指す。
エッジ自身の `id` は持たない。**`<from>>​<to>` の組が識別子**である（§5.2）。

| キー | 必須 | 意味 |
|---|---|---|
| `from` / `to` | ○ | `nodes` の `id` |
| `label` | | 線に添える文字。**置き場所が無ければ描かない**（§3.0 の規則） |
| `protocol` | | `label` が無いときに代わりに使う |
| `ends` | | **端の記号**（`{ from, to }`。ER の多重度・UML の関係。§3.0.9） |
| `line` | | **線種**（`solid` / `dashed` / `dotted` / `double`。§3.0.9） |
| `hatch` | | **閉じた輪の中の模様**（`close: true` のときだけ効く） |
| `weight` | | **太さ**（`thin` / `normal` / `thick`。§3.0.12） |
| `via` | | **通り道**（`{ x, y }` の並び）。配置図でだけ効く（§3.0.15） |
| `curve` | | **丸め方**（`none` / `smooth`）。§3.0.15 |
| `close` | | **輪を閉じるか**（`true` / `false`）。§3.0.15 |
| `vertical` | | **階をまたぐ動線**（`stair` / `escalator` / `elevator`）。§3.0.16 |
| `color` | | **`palette` の鍵**（§3.0.13） |
| `fill` | | **`palette` の鍵**。面の色（§3.0.13） |
| その他 | | 自由。読み手は知らないキーを**捨てずに保つ** |

**通り道を人が上書きするときは `pins.<from>><to>.waypoints`**（§3.4）。
両方あれば**人が勝つ**。

### 3.4 `pins` — **この形式の中心**

```yaml
pins:
  db:
    position: { x: 620, y: 410 }
    size: { w: 240, h: 96 }
  monitor:
    label: 監視（Zabbix）
    appearance: primary
  web01>db:
    waypoints:
      - { x: 340, y: 300 }
```

鍵はノードの `id`、またはエッジの `<from>>​<to>`。

| キー | 意味 |
|---|---|
| `position` | 人が置いた座標。**自動配置より優先する** |
| `size` | 人が決めた大きさ |
| `label` | 人が書き換えた表示名。`nodes` の `label` より優先する |
| `appearance` | 人が指定した体裁（意味の語で書く。色コードを書かない） |
| `waypoints` | 人が曲げた線の通り道 |
| `locked` | **人が「AI の再配置より自分の指定を採る」と決めた印**（§6.3） |

#### `pins` についての規則（守らないと形式の意味が消える）

1. **`pins` に書いてよいのは人だけ。** AI は書かない。AI が書いた `pins` は捨てる
2. **`pins` に無い要素の位置は、自動配置が決めてよい。**
   すべての要素に `position` を書かない。全部を固定すると自動配置が死ぬ
3. `pins` の鍵が、どの `nodes` / `edges` も指していない状態を**迷子**と呼ぶ。
   読み手は迷子を**黙って捨ててはならない**（§6.2）

### 3.5 `review` — **人が見たという記録**

```yaml
review:
  at: 2026-09-08T04:00:00Z
  of: 3f2a1b9c7e4d5068
```

`pins` は「人が**直した**」記録。**これは「人が見て、直す必要が無いと判断した」記録。**

この 2 つが無いと区別できない。

| 実際に起きたこと | 自力率 |
|---|---|
| AI が描いて、**人が見て、直すところが無かった** | 100% |
| AI が描いて、**誰も見ていない** | 100% |

**後者はこの製品の失敗そのもの。** 図は理解を共有するために描くので、
誰も見ないまま貼られる図は、この製品が無くても得られる。

| 鍵 | 意味 |
|---|---|
| `at` | 最後に見た時刻（ISO 8601） |
| `of` | **そのとき見た意味の指紋** |

**個人を書かない。** 誰が見たかは記録しない（公開リポジトリに置かれるため）。

#### 何に対する承認か

見たのは**そのときの意味**であって、ファイルではない。

- `version` / `title` / `groups` / `nodes` / `edges` が変われば、**印は外れる**
- **`pins` が変わっても外れない。** それは人が自分で動かした結果で、動かした人は図を見ている
- 註釈・空行の違いでは外れない。**意味は同じだから**

印が外れても `at` は残す。**「一度も見ていない」と「見たあとに変わった」は別の状態**で、
人へ見せる文言も違う。

#### **書ける場所**

| | |
|---|---|
| GUI | ○ 人が押す |
| CLI / MCP / `propose` | **✗ 開けない** |

開けた瞬間、**AI が自分の絵を自分で承認できる。**
`propose` は**提案の `review` を読まない**（`pins` を読まないのと同じ）。

`of` は改竄を防ぐためのものではない。**防ぐ相手（AI）にはそもそも書く口が無い。**
正本を手で書き換えられる人は指紋も書き換えられるので、
暗号学的な強さを足しても守れるものが増えない。

### 3.6 `construction` — **座標を書かずに作る**（D36）

**`kind: construction` のときだけ効く。** 骨格は `docs/specs/011-作図の骨格.md`。

```yaml
version: 1
kind: construction
# **これだけが与えられたもの**
let:
  R: 100
  H: 200
  # 語で書ける定数（golden / sqrt2 / sqrt3 / pi）
  phi: golden
# 式。**前の行だけを参照できる**
lengths:
  stem: R * phi ^ 6
  weight: H / phi ^ 5
# **書いた順に評価する。**点・円・線を混ぜて書ける
steps:
  # 与える点（**ここだけ座標を書く**）
  - id: O
    at: { x: 0, y: 0 }
  - id: bowl
    center: O
    r: R
  # 水平線（x: なら垂直線、through: なら 2 点を通る直線）
  - id: base
    y: 0
  - id: P
    # 2 円、または円と直線
    intersect:
      - bowl
      - base
    # **2 つある交点のどちらか。書かなければ断る**
    take: right
arcs:
  - of: bowl
    # 端は点で指す（角を数で書いてもよい）
    from: P
    to: 180
    weight: weight
    cap: round
# 定規で引く分（lines は交点を出すためのもので、描かない）
segments:
  - from: O
    to: P
    weight: weight
```

| 節 | 何を書くか |
|---|---|
| `let` | 定数。**人が pin できるのはここ** |
| `lengths` | 式で出す長さ。`+ - * / ^`・括弧・`distance(A, B)` |
| `steps` | 点・円・線。**書いた順に評価する** |
| `arcs` | 描く弧。`circles[].draw: true` で円をそのまま描いてもよい |
| `segments` | **描く線分**（`from` と `to` で 2 点を結ぶ）。定規で引く分 |
| `define` / `place` | **同じかたまりを何度も置く**（字・部品・繰り返し模様） |

**ソルバではない。**各手順は前の手順の結果だけから決まる（表計算と同じ）。
だから「解けなかった」は起きず、起きるのは**交点が無い**ことだけ。

**`tangent-to`（接する）は入れない。**接する円は一般に一意でないので、
それを入れると拘束を解くことになる（＝ CAD）。

#### 人の手直し

**`pins` は「定数」に効く。**位置ではない。

```yaml
pins:
  R:
    # 人が基準を変えた。**1 つ直すと図全体が比を保ったまま動く**
    value: 120
```

**`pins.position` を書いたら、黙って無視せずに断る**（`pin-position-in-construction`）。
黙って消えるのが唯一の本当の事故で、
**利用者から見ると D5 が壊れたのと区別が付かない。**

#### 同じかたまりを何度も置く（`define` / `place`）

```yaml
define:
  u:
    steps:
      - id: O
        at: { x: R, y: R }
    arcs:
      - of: O
        weight: weight
steps:
  - place: u
    as: g0
  - place: u
    as: g1
    after: g0
    gap: gap
```

- かたまりの中の名前は**その中だけのもの**。外からは `as.名前` で引く
- **長さ（`lengths`）だけ共有する** —— 比は図ぜんたいで 1 つ
- **送り幅は書かない。** `after` で繋ぐと、**置いたものの外接から機械が出す**
  —— 書かせると、形を直したときに数字が置き去りになる

## 4. 体裁（`appearance`）## 4. 体裁（`appearance`）

正本には**意味の語**を書き、色や線幅は描き手が決める。

v1 が定める語は 2 つ。

| 語 | 意味 |
|---|---|
| `primary` | 説明の主役 |
| `muted` | 背景として添えるもの |

知らない語は**捨てずに保ち**、既定の体裁で描く。

## 5. 識別子

### 5.1 ノードの `id`

- 文書内で一意
- **一度付けた `id` を、意味が変わらないのに書き換えない**

これは飾りの規則ではない。**人の手直しは `id` に紐づいている。**
`id` が変わった瞬間、その要素に対する人の指定は行き先を失う（迷子になる）。

書き手（AI を含む）は、既存の要素を指すときは既存の `id` をそのまま使う。

### 5.2 エッジの識別

`<from>` と `<to>` を `>` で繋いだもの。例: `web01>db`。

同じ 2 点間に複数のエッジを引くことは v1 では想定しない。

## 6. 読み書きの規則

### 6.1 書き戻し（往復して壊さない）

読んで書き戻したとき、**コメント・空行・キーの並び順・数値の書き方が変わってはならない。**

これは体裁の好みではない。図の差分は「人が何を直したか」の記録であり、
機械が触った行が差分に出ると、記録として読めなくなる。

### 6.2 再生成のときの向き（**最重要**）

AI が返したものを**新しい正本にしてはならない。**

```text
AI の出力 = 提案（semantics だけ）
        ↓
人の正本へ入れる（pins・コメント・並び順は正本の側のものを保つ）
        ↓
新しい正本
```

向きを逆にすると、AI が丸ごと書き直した回に、人の手直しとコメントが全部消える。
（実測: `experiments/s1/results/report.md` の REAL-1）

入れるときの規則。

- 提案の `pins` は**読まない**
- 値が同じキーには**触らない**
- 提案に無い要素を消す場合、その要素に `pins` があるなら**消さずに競合として返す**
  （消してから人に聞いても戻せない）

### 6.3 競合

人の指定と、提案が持ち込む指定がぶつかったとき。

1. **検出** — 適用せず、ぶつかったことを人に見える形で返す。**黙って上書きしない**
2. **選択** — 人・提案のどちらを採るかを人が選ぶ
3. **持続** — 選んだ結果を**正本へ書く**。人を採ったなら `locked: true` を書く。
   以後、同じ提案が来ても聞き直さない

`locked` を実行中の状態として持つのは、この仕様に**適合しない**。
次に開いたときに消え、同じことを聞き直すことになるため。

## 7. 他形式への書き出し

**この製品が無くなっても図が読めること**を、書き出しで担保する。

| 先 | 何を担保するか | 状態 | 失われるもの |
|---|---|---|---|
| Mermaid | 翌日**読める** | 実装済み（`src/mermaid.ts`） | `position` / `size` / `waypoints` |
| SVG | 図として残る | 実装済み（`src/render.ts`） | 図としてのみ。再編集はできない |
| draw.io XML | 翌日**編集できる** | 実装済み（`src/drawio.ts`） | **人の指定と自動配置の区別** / `appearance` の語 / コメントと並び順 / `locked` / **`storage` と `container` の形**（四角へ落ちる） |

**失われるものを黙って落としてはならない。**
Mermaid も draw.io も、落ちたものを先頭のコメントに列挙する。

### draw.io について

- **人の指定と自動配置の区別が写せない。** draw.io は全要素が座標を持つので、
  形式にその区別が無い。`zumenPinned="1"` を添えて残すが、
  **draw.io で保存し直すと失われることがある**
- **`appearance` は色に変換される。** 意味の語（`primary` / `muted`）は残らない
- **圧縮しない。** draw.io は既定で deflate + base64 するが、
  それをすると差分が読めなくなり、テキスト正本にした意味が消える
- **書き出しであって取り込みではない**（PRD §4）。正本は `.zumen.yaml` の側

## 8. 適合（conformance）

この形式を読み書きすると称する実装は、次をすべて満たすこと。

1. §6.1 の書き戻し（コメント・空行・並び順が変わらない）
2. §3.4 の `pins` の規則 3 点
3. §6.2 の向き（提案を正本にしない）
4. §6.3 の競合 3 点（検出・選択・持続）
5. §5.1 の `id` を書き換えない

`test/` のテストが、そのまま適合の確認になる。

### 8.1 機械で確かめられるもの／確かめられないもの

適合の 5 項目は、**文書 1 つを見て確かめられるもの**と、
**実装の振る舞いを見なければ確かめられないもの**に分かれる。

| | 文書だけで確かめられるか | 何を見るか |
|---|---|---|
| 1. §6.1 の書き戻し | **できる** | 読んで書き戻し、行が変わらないこと |
| 2. §3.4 の `pins` の規則 | **一部できる** | 規則 3（迷子）は文書だけで分かる。規則 1・2 は書き手の振る舞いなので分からない |
| 3. §6.2 の向き | できない | 往復させてはじめて分かる |
| 4. §6.3 の競合 3 点 | できない | 競合を起こしてはじめて分かる |
| 5. §5.1 の `id` を書き換えない | できない | 2 つの版を比べてはじめて分かる |

文書だけで確かめられるものは、これに加えて次を見る。

- 必須キー（`version` / `nodes`）があること
- ノードの `id` が文書内で一意であること
- `edges` の `from` / `to` が実在するノードを指していること
- **AI が書く指定が、効く形になっていること**（下記）

#### AI が書く指定の検査（すべて `warning`）

`at` / `size` / `openings` / `kind` / `direction` / `wrap` は、
**どれも AI が書いてよい。** 知らない語や壊れた形を書いても、
描画側は既定へ落ちるので**読めない文書にはならない。**

だが**黙って落とすと、書いた側は「効かない」理由が分からない。**
同じ間違いを書き続け、人は図を見るまで気づけない。

| 印 | 何を見るか |
|---|---|
| `syntax` | **YAML として読めるか**（読めなければ止める） |
| `not-mapping` | 文書の一番外側が対応表か（並びや文字列を受けない） |
| `version-missing` | `version` があるか |
| `version-unsupported` | `version` が 1 か |
| `nodes-missing` | `nodes` があるか |
| `nodes-not-sequence` | `nodes` が並びか |
| `node-id-missing` | 各ノードに `id` があるか |
| `node-id-duplicated` | `id` が文書内で一意か |
| `node-group-unknown` | `group` が `groups` にある id か |
| `edge-endpoint-missing` | 各辺に `from` と `to` があるか |
| `edge-endpoint-unknown` | 辺の端が `nodes` にある id か |
| `appearance-unknown` | `pins` の体裁が `primary` / `muted` か |
| `pin-orphan` | **`pins` が指す要素が正本に無い**（消さずに知らせる。§3.4） |
| `node-at-invalid` | `at` が `{ x: 数, y: 数 }` か |
| `node-at-ignored` | **構成図に `at` を書いていないか**（置き場所は機械が決める） |
| `node-size-invalid` | `size` が `{ w: 正の数, h: 正の数 }` か |
| `opening-kind-unknown` | 建具が `door` / `double` / `slide` / `window` / `open` か |
| `opening-side-unknown` | 建具の辺が `top` / `right` / `bottom` / `left` か |
| `opening-ignored` | **構成図に建具を書いていないか** |
| `kind-unknown` | `structure` / `placement` か |
| `direction-unknown` | `right` / `down` か |
| `wrap-not-boolean` | `wrap` が真偽値か（`wrap: "true"` は折り返さない） |
| `grid-axis-invalid` | 通り芯が `{ id: 符号, at: 数 }` か |
| `grid-ignored` | **構成図に通り芯を書いていないか** |
| `scale-missing` | **通り芯はあるが縮尺が無い**（寸法の数値だけが出ない） |
| `scale-invalid` | `scale.mm` が正の数か |
| `north-unknown` | `up` / `right` / `down` / `left` か |
| `views-invalid` | `views` が並びか |
| `views-ignored` | **構成図に `views` を書いていないか** |
| `view-id-missing` | 図に `id` があるか（無い図は描かれない） |
| `view-id-duplicate` | **同じ `id` の図が 2 つ無いか**（どちらの寸法か読めない） |
| `view-frame-missing` | 図に `at` と `size` があるか（無い図は描かれない） |
| `views-no-grid` | **どの図にも通り芯が無いか**（寸法も符号も出ない） |
| `pin-position-in-construction` | **作図で位置を pin していないか**（位置は手順が決める。**明示で断る**） |
| `construction-nothing-drawn` | 作図に描くものがあるか（`arcs` か `circles[].draw`） |
| `id-shared-with-group` | **同じ id を囲みと節で使っていないか**（囲みが二重に描かれる） |
| `number-text-changed` | **文字のつもりが数として読まれていないか**（`32.0` が `32` になる） |
| `wall-invalid` | `wall.mm` が正の数か |
| `wall-needs-scale` | **壁の厚みはあるが縮尺が無い**（太さが変わらない） |
| `radius-invalid` | `radius` が正の数か |
| `radius-ignored` | **構成図に `radius` を書いていないか** |
| `marker-unknown` | `box` / `circle` / `double` / `ellipse` / `diamond` / `bar` / `none` か |
| `edge-under-box` | **`arrows: false` で、箱の塗りに隠れる線を引いていないか** |
| `align-unknown` | `left` / `center` / `right` か |
| `align-ignored` | **構成図に `align` を書いていないか** |
| `write-unknown` | `across` / `down` か |
| `write-ignored` | **構成図に `write` を書いていないか** |
| `grid-mark-unknown` | 通り芯の `mark` が `axis` / `level` / `tick` か |
| `curve-unknown` | `none` / `smooth` か |
| `close-not-boolean` | `close` が真偽値か |
| `close-ignored` | **構成図に `close` を書いていないか** |
| `via-invalid` | `via` が `{ x: 数, y: 数 }` の並びか |
| `via-ignored` | **構成図に `via` を書いていないか** |
| `vertical-unknown` | `none` / `stair` / `escalator` / `elevator` か（JIS Z 8210） |
| `marker-ignored` | **構成図に `marker` を書いていないか** |
| `hatch-unknown` | `none` / `solid` / `dots` / `lines` / `cross` か |
| `symbol-unknown` | 図記号が `SYMBOLS` の語か |
| `hatch-ignored` | **構成図に `hatch` を書いていないか** |
| `ends-unknown` | 端の記号が `ENDS` の語か |
| `line-unknown` | 線種が `solid` / `dashed` / `dotted` / `double` か |
| `text-overlap` | **文字どうしが重なっていないか**（配置図。**置いてみないと分からない**） |
| `edge-self-open` | **自分自身への辺に `via` があるか**（無いと長さ 0 の線になる） |
| `edge-hatch-ignored` | **閉じていない辺に `hatch` を書いていないか**（面が無い） |
| `label-markdown` | **名前に `**` を残していないか**（名前は素のテキスト。印はそのまま絵に出る） |
| `edge-fill-ignored` | **辺に `fill` を書いていないか**（面の色は `nodes[].fill`。閉じた輪の中は `hatch` ＋ `color`） |
| `name-adrift` | **幅のある箱から名前が出ていっていないか**（表の欄が空に見える） |
| `tag-hidden` | **符号が印に入りきって描かれるか**（配置図。同上） |
| `name-crowded` | **入りきらない名前の行き先があるか**（重なるか、紙の縁で切れる） |
| `too-small-to-print` | **A3 に印刷して字が読める大きさか**（割ったら紙を小さくする。文字は大きくしない）。**長辺の向きと、その両端にいる要素の id** まで言う |
| `weight-unknown` | 太さが `thin` / `normal` / `thick` か |

**どれも `error` にしない。** 弾くと、v1 の「捨てずに保つ」を壊す。

**確かめられないものを、文書の検査で代用しない。**
3〜5 は往復のテストで担保する領域であり、静的な検査で通ったことを
適合の証明にしてはならない。

#### 迷子と、知らないもの

**迷子（規則 3）は失敗ではない。** 人が競合として解くものであり、
検査は見つけて知らせるところまでを行う。
同じく、**知らないキーと知らない体裁の語も失敗ではない**（§9）。
弾くと、v1 の「捨てずに保つ」という規則そのものを壊す。
