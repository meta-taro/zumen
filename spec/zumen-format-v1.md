# zumen 図形式 v1（仕様）

- 状態: **確定**（2026-09-04・D2）。**「確定」は「これを根拠に実装してよい」の意味であって、
  「二度と変えない」の意味ではない。** 版の上げ方は §9。実地で足りない点が出たら版を上げる
- 対象: `.zumen.yaml` ファイル、および Markdown 中の ```` ```zumen ```` 囲み

> **この文書は実装から独立して読めるように書く。**
> zumen の開発が止まっても、この文書と YAML パーサがあれば図を読み直せる、
> という状態を保つのが目的（PRD §5 の 4 問目）。
> 実装（`src/`）を読まないと分からない規則が出てきたら、それはこの文書の不足。

---

## 1. 何のための形式か

**AI が書き、人が直し、また AI が読む**ための形式である。

そのために、他の作図形式と違う要求が 1 つある。

> **人が手で決めたことと、機械が自動で決めたことを、区別して持てること。**

区別が無いと、AI が再生成するたびに人の手直しが自動配置に上書きされる。
この 1 点がこの形式の存在理由であり、他はすべてこれに従属する。

### やらないこと

- 描画の細部（色コード・線幅・フォント）を正本に持たない。**意味だけを持つ**
- 図形の網羅を追わない。対象はサーバー・ネットワーク・クラウド構成図
- 他形式の完全な相互変換を保証しない（**書き出しは行うが、往復の無損失は保証しない**）

---

## 2. 置き方

### 2.1 単体のファイル

```text
<名前>.zumen.yaml
```

### 2.2 Markdown への埋め込み

```text
```zumen
<この文書が定める YAML>
```
```

囲みの中身は、単体ファイルと**同じもの**である。別の書き方を用意しない。

---

### 2.3 図の種類（`kind`）

```yaml
kind: placement # 省略すると structure
```

| | | 置き場所を決めるのは |
|---|---|---|
| `structure`（既定） | 構成図。**何がどこへ繋がるか**が内容 | **機械** |
| `placement` | 配置図。**どこに在るか**が内容 | **人** |

**これは、置き場所の出どころの指定です。**

```yaml
kind: placement
nodes:
  - id: jimu
    label: 事務室
    at: { x: 420, y: 200 } # ← 機械は並べ直さない
```

| | 書くのは | 強さ |
|---|---|---|
| `nodes[].at` | **AI が書いてよい** | 弱い |
| `pins.position` | **人だけ**（AI は書けない。§3.4） | **強い。常に勝つ** |

`label` と同じ形です —— `nodes[].label` は AI、`pins.label` は人。
**D5 の向きは、配置図でも変わりません。**

`at` が無い要素は、機械が置きます（**黙って重ねない**）。

**大きさも同じ形です。**

| | 書くのは | 強さ |
|---|---|---|
| `nodes[].size` | **AI が書いてよい** | 弱い |
| `pins.size` | **人だけ** | **強い。常に勝つ** |
| 書かなければ | ラベルから見積もる | いちばん弱い |

**大きさは構成図でも効きます**（並べ方と関係ないため）。

間取りを描かせてみて分かったことです —— **部屋の大きさが全部同じでは図になりません。**
16 畳の LDK と便所が同じ箱で出ました。

### 縮尺について

**縮尺の仕組みは持ちません。** 図の題に書けば足ります。

```yaml
title: 1 階・約 62 m²（1 マス = 910mm を 40px として）
```

寸法の単位を形式が持つと、**単位系・丸め・累積誤差を全部引き受ける**ことになります。
それは作図ソフトの仕事で、この製品の勝負どころではありません（PRD §4）。

**物差しは構成図と同じ向きです。** 当初「配置図では自力率が反転する」と考えましたが、
**それは「配置は人がやるもの」という誤った前提**でした。
AI が `at` に置けるので、「人が触った要素が少ないほど良い」がそのまま成り立ちます。

**種類は 2 つだけです。** 増やすのは、**測り方が増えるときだけ**。
「立面図」「断面図」を足したくなっても、**測り方が配置図と同じなら足しません**（PRD §4）。

## 3. 文書の構造

最上位は写像（mapping）で、次のキーを持つ。

| キー | 必須 | 型 | 意味 |
|---|---|---|---|
| `version` | ○ | 整数 | 形式の版。v1 では `1` |
| `title` | | 文字列 | 図の題 |
| `kind` | | 文字列 | **図の種類**（§2.3）。`structure`（既定）か `placement` |
| `direction` | | 文字列 | 流れる向き。`right`（既定）か `down` |
| `groups` | | 並び | 囲み（VPC・サブネット等） |
| `nodes` | ○ | 並び | 要素 |
| `edges` | | 並び | 要素どうしの関係 |
| `pins` | | 写像 | **人が手で決めたこと** |
| `review` | | 写像 | **人が見たという記録**（§3.5）。GUI だけが書く |

**無いキーを空で書かなくてよい。** 読み手は欠けたキーを空として扱う。
書き手は、**中身の無いキーを勝手に足してはならない**（人が書いていない行を増やさない）。

### 3.1 `nodes`

```yaml
nodes:
  - id: web01
    type: server
    label: Web 01
    group: vpc
    technology: Apache
```

| キー | 必須 | 意味 |
|---|---|---|
| `id` | ○ | 文書内で一意。**§5 の規則に従う** |
| `type` | | 種別。**下記のいずれか。** 未知の値は `generic` として描く |
| `at` | | **置き場所**（`{ x, y }`）。**配置図でだけ効く**（§2.3）。AI が書いてよい |
| `size` | | **大きさ**（`{ w, h }`）。AI が書いてよい。**構成図でも効く** |
| `tag` | | **符号**（`C1` / `2"-CS-101`）。箱の左上に小さく描く（§3.1.3）。AI が書いてよい |
| `openings` | | **建具**（扉・窓）。**配置図でだけ効く**（§3.1.2）。AI が書いてよい |
| `label` | | 表示名。無ければ `id` を使う |
| `group` | | 属する `groups` の `id` |
| その他 | | 自由。読み手は知らないキーを**捨てずに保つ** |

`type` に書ける語は次の 11 個。**うち 6 個は形が変わる**（§3.1.1）。

```
server / database / storage / cache / queue / internet
load-balancer / container / cluster / network / generic
```

**知らない語を書いてもよい**（`generic` として描かれ、値は捨てずに保たれる）。

#### 3.1.1 形

**`type` は形になる**（Issue #9）。色ではなく形で意味を持たせるのは、
**白黒でも色覚特性でも縮小でも失われない**ため（`DESIGN.md` §7）。

| `type` | 形 | draw.io |
|---|---|---|
| `database` | 円柱 | `shape=cylinder` |
| `storage` | 積み重ね | **四角へ落ちる** |
| `internet` | 雲 | `shape=cloud` |
| `cache` | 六角形 | `shape=hexagon` |
| `queue` | 仕切りのある矩形 | `shape=process` |
| `container` | 二重の枠 | **四角へ落ちる** |
| 上記以外 | 矩形 | 矩形 |

**全部に別の形を与えない。** 見分けが付くことが目的で、形を増やすのが目的ではない。

**ベンダーのロゴは持ち込まない**（D7）。AWS のアイコンを使うと
「AWS 上にある」と読まれ、自前サーバの図に使えない。

#### 3.0.1 折り返し（`wrap`）

**長い鎖を折り返すか。既定は折り返さない。**

```yaml
version: 1
wrap: true
```

折り返さないと、7 工程の業務フローが **横 2584 × 縦 124（比 20.8）** で出る。
資料に貼ると幅に合わせて縮むので、**文字が読めない。**
縦向き（`direction: down`）にしても 0.27:1 になるだけで解決しない。

| ノード数 | 折り返し無し | `wrap: true` |
|---|---|---|
| 2 | 3.42 | **3.42（折り返さない）** |
| 3 | 5.16 | 2.18 |
| 5 | 8.65 | 3.14 |
| 8 | 13.87 | 2.17 |
| 12 | 20.84 | 2.83 |

**既定にしない理由。** 折り返すと 2 行目の先頭が 1 行目の末尾より左に来るので、
繋ぐ辺が図を右から左へ戻る —— [#1](https://github.com/meta-taro/zumen/issues/1) で
報告された壊れ方（終点が最上段に来て、全高を逆流する矢印が生まれた）と**同じ絵**になる。

実際、既定にしたら `test/groups.test.ts` の 4 件が落ちた。
**落ちたテストを消さずに、既定を変えないほうを採った。**

折り返してよいかは図による —— 工程が 10 個ある業務フローなら折り返したいし、
4 個の鎖なら一直線のほうが読める。**それを決めるのは人。**

#### 3.0.2 通り芯・縮尺・方位（`grid` / `scale` / `north`）

**配置図でだけ効く。** 書かなければ描かない。

```yaml
kind: placement
scale: { mm: 15 } # 1 px = 15 mm
north: up
grid:
  x:
    - { id: X1, at: 40 }
    - { id: X2, at: 240 }
  y:
    - { id: Y1, at: 40 }
    - { id: Y2, at: 320 }
```

| キー | 意味 |
|---|---|
| `grid.x` | 縦に走る芯（左右の位置を決める）。`id` は符号、`at` は図の座標 |
| `grid.y` | 横に走る芯（上下の位置を決める） |
| `scale.mm` | **1 px が何 mm か。** これが無いと寸法の数値を出さない |
| `north` | `up` / `right` / `down` / `left` |

描かれるもの。

- **通り芯** —— 一点鎖線。建物を**貫いて**外まで伸び、両端に符号を丸で囲んで置く
- **寸法線** —— 建物の外に、内から順に「芯どうし」「総寸法」の 2 段。
  端は斜線（図面では矢印より斜線が普通）。**数値のところで線を切る**
- **方位記号** —— 右上

**寸法は通り芯からしか出さない。** 部屋の箱から出すと、
壁の厚みをどちらに数えるかで値が変わり、**現場で食い違う。**
実物の図面が通り芯を基準にしているのは、そこを一意にするため。

**`scale` が無ければ数値を出さない。** 知らない縮尺で数値を書くより、
出さないほうがよい。現場では、**寸法が間違っていることの害が、無いことより大きい。**

**芯が 2 本なら総寸法を重ねて書かない**（芯どうしの寸法と同じ数字になる）。

**桁を揃える空白を入れない。** 書き戻しで詰められるので §6.1 に反する
（`round-trip-changed` で落ちる。2026-09-12 に実際に踏んだ）。

| 書き方 | 書き戻すと |
|---|---|
| `at: { x: 40 }   # ← 注記` | **`#` の前の空白が 1 つに詰まる** |
| `x: [{ id: X1, at: 40 }]` | `x: [ { id: X1, at: 40 } ]`（括弧の内側に空白が入る） |
| `at:   { x: 40, y: 40 }` | `at: { x: 40, y: 40 }` |

**通り芯は 1 行 1 本の並びで書く。**

**流れ形式（`{ ... }`）の中の値にカンマを入れるときは、引用符で囲む。**
YAML はカンマを区切りと読むので、囲まないと**値が黙って割れる。**

```yaml
- { id: 天端 +3,000, at: 0 }      # → id が「天端 +3」になり、0 が別の鍵になる
- { id: "天端 +3,000", at: 0 }    # 正しい
```

`2FL+3,200` のようなレベルの値でよく踏む。
**§6.1 の書き戻しの検査が `error` で止める**ので、気づかずには進めない
（2026-09-12 に実際に踏んだ）。

**目で見ても分からない。** 書き戻しの差は、目で追う種類のものではない
（`test/docs-samples.test.ts` が、文書に載せた見本を毎回検査する）。

#### 3.0.3 壁の厚み（`wall`）

**配置図でだけ効く。`scale` が無ければ何も変えない**（mm を px にできない）。

```yaml
scale: { mm: 15 }
wall: { mm: 105, outer: 180 } # 間仕切 105・外壁 180
```

`outer` を書かなければ、間仕切の 1.5 倍。

**1 本線では壁に見えない。** 部屋と部屋を分ける**境界線**には見えても、
厚みのある**壁**には見えない。厚みは飾りではなく、

- **有効寸法が変わる**（芯々 1,820 の廊下は、壁厚 120 なら内法 1,700）
- **建具の幅が壁の厚みの中に収まる**ことが、見て分かる

**2 本線ではなく塗り潰し。** 実物は縮尺で描き分けられている。

| 縮尺 | 壁の描き方 |
|---|---|
| 1/50 以上（平面詳細図） | 2 本線。間に仕上げの線も入る |
| 1/100 前後（平面図・伏図） | **塗り潰し**（ポシェ） |

zumen が出す図は 1/100 前後の粗さなので、**塗り潰しのほうが実物に近い。**
2 本線にしても、この大きさでは 2 本が潰れて 1 本の太線に見えるだけで、
**描画は複雑になるのに絵は同じ**になる。

太さには上限がある（24px）。厚い壁を大きな縮尺で描くと、
**壁が部屋を食い潰す。** そこまで行くなら、それは詳細図で描くもの。

#### 3.0.4 配置図では、動線を箱の上に描く

部屋の塗りは透けないので、下に置くと**隣どうしの矢印が完全に消える。**
壁に厚みを付けたところ、避難経路の矢印が丸ごと壁の下に入った（2026-09-12）。
**避難経路図は矢印が主役**の図で、消えたら図の意味が無い。

構成図では、これまでどおり辺は箱の下（箱が辺の端を隠して、繋がって見える）。

**矢印を出すかは正本が決める。** 辺を書かなければ出ない（間取りがそれ）。

#### 3.0.5 範囲を示す円（`nodes[].radius`）

**配置図でだけ効く。** 単位は px。`scale` があれば半径を mm で書き添える。

```yaml
  - id: crane
    label: クレーン
    tag: CR-1
    technology: 25t 吊・定格 5.0t/10m
    at: { x: 200, y: 228 }
    size: { w: 120, h: 54 }
    radius: 250
```

[#4](https://github.com/meta-taro/zumen/issues/4) の原題は**総合仮設計画図**だった。
実物に必ず入る 10 種のうち、**揚重機だけが矩形では描けなかった。**
クレーンの作業計画に要るのは、機種・定格荷重・**作業半径**・揚程・据付位置で、
**作業半径が描けないと、そのクレーンで届くかが図から読めない。**

| | 何に使うか |
|---|---|
| 仮設計画図 | クレーンの作業半径 |
| 消防設備図 | 消火器の警戒区域（**歩行距離 20m 以内**） |
| 太陽光の架台配置 | 影の離隔 |
| 設備図 | 電波・照明・スプリンクラーの到達 |

**`type` を増やす話ではない。** クレーンは円ではなく、**円はクレーンが届く範囲**で、
寸法線と同じ種類の注記。語彙は `radius` の 1 つだけで、業界が増えても増えない。

**破線で描く。** 実線は「物がある」ことを言うので、
実線にすると**届く範囲と物の輪郭が見分けられなくなる。**

#### 3.1.2 建具（`openings`）

**配置図（`kind: placement`）でだけ効く。** 間取り図を実物と並べたとき、
いちばん大きく違ったのが**建具が無いこと**だった（2026-09-12。人の指摘）。
扉があることを絵で言えないと、間取り図は間取り図にならない。

```yaml
  - id: ldk
    label: LDK
    at: { x: 40, y: 40 }
    size: { w: 320, h: 280 }
    openings:
      - { kind: window, side: top, at: 0.25, width: 90 }
      - { kind: door, side: bottom, at: 0.83, width: 70 }
```

| キー | 既定 | 意味 |
|---|---|---|
| `kind` | ○ | `door` / `slide` / `window` / `double` / `open` |
| `side` | ○ | `top` / `right` / `bottom` / `left` |
| `at` | `0.5` | 辺のどこか（0〜1） |
| `width` | `36` | 幅（px） |

| `kind` | 絵 |
|---|---|
| `door` | 片開き戸（戸と開き勝手の弧） |
| `double` | 両開き戸（弧が 2 つ） |
| `slide` | 引き戸（ずらした 2 本の平行線。**弧は無い**） |
| `window` | 窓（細い 2 本線） |
| `open` | 開口（**壁が無いだけ**。記号を描かない） |

**建具は壁に開く穴**なので、まず壁を消してから記号を描く。
`kind` と `side` が既定の語でなければ、その建具は**黙って落とす**
（描けないものを描いたことにしない）。

**設備（浴槽・便器・流し）と表題欄は入れない。**
建具は壁の話の続きで済むが、設備は**物の形**で、入れ始めると `type` が
30 語を超える。表題欄は図ではなく用紙の話で、貼り先が持っている。

> **訂正（2026-09-12）。** ここには「通り芯・寸法線も入れない」と書いてあったが、
> **取り消した**（§3.0.2）。オーナーから
> 「工事現場では使えない。**不動産の間取り図レベル**」と指摘され、そのとおりだった。
> **寸法が無い図では、何も建てられない。**

#### 3.1.3 符号（`tag`）

**業界ごとの専門性は、形ではなく符号で表されている**（D22）。

| 業界 | 符号の例 |
|---|---|
| 建築・構造 | `C1`（柱）`G1`（大梁）`B1`（小梁）`S1`（床）`F1`（基礎）`W1`（壁） |
| 配管（P&ID） | `P-101A`（ポンプ）`TK-101`（タンク）`2"-CS-101`（ライン番号） |
| 電気 | `LBS-1`（開閉器）`T-1`（変圧器）`MCC-1`（動力盤） |
| 工場 | 工程番号・設備番号 |

`C1` は**円柱の絵ではなく、矩形の中に書く 2 文字**。
一級建築士が図面を読むとき見ているのは部材の形ではなく、
**符号と、符号表（断面リスト）との対応**。

```yaml
  - id: c1a
    label: 柱
    tag: C1
    technology: 700×700
```

**`label` の代わりではない。** 名前と符号は別のもので、図面は両方を出す。
符号は**箱の左上**に置く（中央のラベルと重ねない）。読み手は符号だけを
拾って表と突き合わせるので、**中央に混ぜるとその拾い読みができなくなる。**

**`type` は増やさない。** 業界が増えても 11 語のまま。
語彙が増えるほど、同じものを違う語で書く人が増え、**差分が読めなくなる**
（[#6](https://github.com/meta-taro/zumen/issues/6) の報告者が警告した広がり方）。

#### 3.1.4 入らない文字の置き方

**配置図では、箱の大きさを人と AI が書く**ので、**文字が入らない箱が出る。**
構成図では起きない（箱の大きさをラベルから決めるので、必ず入る）。

置き先を 5 段で選ぶ。

| | 置き方 | そうなる図 |
|---|---|---|
| 1 | そのまま中へ | ふつうの部屋 |
| 2 | 名前と副題を**1 行に繋いで**中へ | 通路・農道（背が低い） |
| 3 | 名前は中へ、**副題を横に回して**添える | 駐車場の区画（`W1`／`車椅子 3,500`） |
| 4 | 帯に沿って**縦へ** | 用水路・廊下（横に入らない） |
| 5 | 箱の**外へ** | それ以外 |

**5 のときは、当たりを見る。** 上下を試し、**他の箱にも、先に置いた文字にも
当たらない**ほうを選ぶ。図の外へ出る側は先に落とす（`y` が負になると消える）。

**どこも空いていなければ、いちばん当たりの少ない所へ置いて、
`zumen_inspect` の `crowdedNames` へ id を返す。**

**消さない。** 辺のラベルは消してよいが（どこへ繋がるかは線で分かる）、
**名前は線では分からない。** 部屋の名前が消えるのは、重なるより悪い。

#### 3.1.5 描く順

**配置図では、大きいものから先に描く。**

箱の塗りは透けないので、後に描いたものが前に出る。
伏図でスラブが正本の後ろにあり、**大梁と柱の線をスラブが塗り潰した。**
間取りでも、広い部屋が狭い部屋の壁を消す同じ壊れ方になる。

構成図では並べ替えない（箱が重ならない）。
**正本の順序は、読み手が意味を持たせている可能性がある。**

**形によって箱の寸法が変わる**（円柱は上下、六角形は左右に余分が要る）。
`src/shapes.ts` の `growFor()` が返す分を配置が足す。
MCP では `zumen_spec` が同じ一覧を返す。

**`nodes` の並び順には意味がある。** 人が読む順序であり、書き手は理由なく並べ替えない。

### 3.2 `edges`

```yaml
edges:
  - from: web01
    to: db
    label: replication
    protocol: HTTPS
```

`from` / `to` は `nodes` の `id` を指す。
エッジ自身の `id` は持たない。**`<from>>​<to>` の組が識別子**である（§5.2）。

### 3.3 `groups`

```yaml
groups:
  - id: vpc
    label: Production VPC
```

入れ子は v1 では持たない。

### 3.4 `pins` — **この形式の中心**

```yaml
pins:
  db:
    position: { x: 620, y: 410 }
    size: { w: 240, h: 96 }
  monitor:
    label: 監視（Zabbix）
    appearance: primary
  web01>db:
    waypoints:
      - { x: 340, y: 300 }
```

鍵はノードの `id`、またはエッジの `<from>>​<to>`。

| キー | 意味 |
|---|---|
| `position` | 人が置いた座標。**自動配置より優先する** |
| `size` | 人が決めた大きさ |
| `label` | 人が書き換えた表示名。`nodes` の `label` より優先する |
| `appearance` | 人が指定した体裁（意味の語で書く。色コードを書かない） |
| `waypoints` | 人が曲げた線の通り道 |
| `locked` | **人が「AI の再配置より自分の指定を採る」と決めた印**（§6.3） |

#### `pins` についての規則（守らないと形式の意味が消える）

1. **`pins` に書いてよいのは人だけ。** AI は書かない。AI が書いた `pins` は捨てる
2. **`pins` に無い要素の位置は、自動配置が決めてよい。**
   すべての要素に `position` を書かない。全部を固定すると自動配置が死ぬ
3. `pins` の鍵が、どの `nodes` / `edges` も指していない状態を**迷子**と呼ぶ。
   読み手は迷子を**黙って捨ててはならない**（§6.2）

---

### 3.5 `review` — **人が見たという記録**

```yaml
review:
  at: 2026-09-08T04:00:00Z
  of: 3f2a1b9c7e4d5068
```

`pins` は「人が**直した**」記録。**これは「人が見て、直す必要が無いと判断した」記録。**

この 2 つが無いと区別できない。

| 実際に起きたこと | 自力率 |
|---|---|
| AI が描いて、**人が見て、直すところが無かった** | 100% |
| AI が描いて、**誰も見ていない** | 100% |

**後者はこの製品の失敗そのもの。** 図は理解を共有するために描くので、
誰も見ないまま貼られる図は、この製品が無くても得られる。

| 鍵 | 意味 |
|---|---|
| `at` | 最後に見た時刻（ISO 8601） |
| `of` | **そのとき見た意味の指紋** |

**個人を書かない。** 誰が見たかは記録しない（公開リポジトリに置かれるため）。

#### 何に対する承認か

見たのは**そのときの意味**であって、ファイルではない。

- `version` / `title` / `groups` / `nodes` / `edges` が変われば、**印は外れる**
- **`pins` が変わっても外れない。** それは人が自分で動かした結果で、動かした人は図を見ている
- 註釈・空行の違いでは外れない。**意味は同じだから**

印が外れても `at` は残す。**「一度も見ていない」と「見たあとに変わった」は別の状態**で、
人へ見せる文言も違う。

#### **書ける場所**

| | |
|---|---|
| GUI | ○ 人が押す |
| CLI / MCP / `propose` | **✗ 開けない** |

開けた瞬間、**AI が自分の絵を自分で承認できる。**
`propose` は**提案の `review` を読まない**（`pins` を読まないのと同じ）。

`of` は改竄を防ぐためのものではない。**防ぐ相手（AI）にはそもそも書く口が無い。**
正本を手で書き換えられる人は指紋も書き換えられるので、
暗号学的な強さを足しても守れるものが増えない。

## 4. 体裁（`appearance`）

正本には**意味の語**を書き、色や線幅は描き手が決める。

v1 が定める語は 2 つ。

| 語 | 意味 |
|---|---|
| `primary` | 説明の主役 |
| `muted` | 背景として添えるもの |

知らない語は**捨てずに保ち**、既定の体裁で描く。

---

## 5. 識別子

### 5.1 ノードの `id`

- 文書内で一意
- **一度付けた `id` を、意味が変わらないのに書き換えない**

これは飾りの規則ではない。**人の手直しは `id` に紐づいている。**
`id` が変わった瞬間、その要素に対する人の指定は行き先を失う（迷子になる）。

書き手（AI を含む）は、既存の要素を指すときは既存の `id` をそのまま使う。

### 5.2 エッジの識別

`<from>` と `<to>` を `>` で繋いだもの。例: `web01>db`。

同じ 2 点間に複数のエッジを引くことは v1 では想定しない。

---

## 6. 読み書きの規則

### 6.1 書き戻し（往復して壊さない）

読んで書き戻したとき、**コメント・空行・キーの並び順・数値の書き方が変わってはならない。**

これは体裁の好みではない。図の差分は「人が何を直したか」の記録であり、
機械が触った行が差分に出ると、記録として読めなくなる。

### 6.2 再生成のときの向き（**最重要**）

AI が返したものを**新しい正本にしてはならない。**

```text
AI の出力 = 提案（semantics だけ）
        ↓
人の正本へ入れる（pins・コメント・並び順は正本の側のものを保つ）
        ↓
新しい正本
```

向きを逆にすると、AI が丸ごと書き直した回に、人の手直しとコメントが全部消える。
（実測: `experiments/s1/results/report.md` の REAL-1）

入れるときの規則。

- 提案の `pins` は**読まない**
- 値が同じキーには**触らない**
- 提案に無い要素を消す場合、その要素に `pins` があるなら**消さずに競合として返す**
  （消してから人に聞いても戻せない）

### 6.3 競合

人の指定と、提案が持ち込む指定がぶつかったとき。

1. **検出** — 適用せず、ぶつかったことを人に見える形で返す。**黙って上書きしない**
2. **選択** — 人・提案のどちらを採るかを人が選ぶ
3. **持続** — 選んだ結果を**正本へ書く**。人を採ったなら `locked: true` を書く。
   以後、同じ提案が来ても聞き直さない

`locked` を実行中の状態として持つのは、この仕様に**適合しない**。
次に開いたときに消え、同じことを聞き直すことになるため。

## 7. 他形式への書き出し

**この製品が無くなっても図が読めること**を、書き出しで担保する。

| 先 | 何を担保するか | 状態 | 失われるもの |
|---|---|---|---|
| Mermaid | 翌日**読める** | 実装済み（`src/mermaid.ts`） | `position` / `size` / `waypoints` |
| SVG | 図として残る | 実装済み（`src/render.ts`） | 図としてのみ。再編集はできない |
| draw.io XML | 翌日**編集できる** | 実装済み（`src/drawio.ts`） | **人の指定と自動配置の区別** / `appearance` の語 / コメントと並び順 / `locked` / **`storage` と `container` の形**（四角へ落ちる） |

**失われるものを黙って落としてはならない。**
Mermaid も draw.io も、落ちたものを先頭のコメントに列挙する。

### draw.io について

- **人の指定と自動配置の区別が写せない。** draw.io は全要素が座標を持つので、
  形式にその区別が無い。`zumenPinned="1"` を添えて残すが、
  **draw.io で保存し直すと失われることがある**
- **`appearance` は色に変換される。** 意味の語（`primary` / `muted`）は残らない
- **圧縮しない。** draw.io は既定で deflate + base64 するが、
  それをすると差分が読めなくなり、テキスト正本にした意味が消える
- **書き出しであって取り込みではない**（PRD §4）。正本は `.zumen.yaml` の側

---

## 8. 適合（conformance）

この形式を読み書きすると称する実装は、次をすべて満たすこと。

1. §6.1 の書き戻し（コメント・空行・並び順が変わらない）
2. §3.4 の `pins` の規則 3 点
3. §6.2 の向き（提案を正本にしない）
4. §6.3 の競合 3 点（検出・選択・持続）
5. §5.1 の `id` を書き換えない

`test/` のテストが、そのまま適合の確認になる。

### 8.1 機械で確かめられるもの／確かめられないもの

適合の 5 項目は、**文書 1 つを見て確かめられるもの**と、
**実装の振る舞いを見なければ確かめられないもの**に分かれる。

| | 文書だけで確かめられるか | 何を見るか |
|---|---|---|
| 1. §6.1 の書き戻し | **できる** | 読んで書き戻し、行が変わらないこと |
| 2. §3.4 の `pins` の規則 | **一部できる** | 規則 3（迷子）は文書だけで分かる。規則 1・2 は書き手の振る舞いなので分からない |
| 3. §6.2 の向き | できない | 往復させてはじめて分かる |
| 4. §6.3 の競合 3 点 | できない | 競合を起こしてはじめて分かる |
| 5. §5.1 の `id` を書き換えない | できない | 2 つの版を比べてはじめて分かる |

文書だけで確かめられるものは、これに加えて次を見る。

- 必須キー（`version` / `nodes`）があること
- ノードの `id` が文書内で一意であること
- `edges` の `from` / `to` が実在するノードを指していること
- **AI が書く指定が、効く形になっていること**（下記）

#### AI が書く指定の検査（すべて `warning`）

`at` / `size` / `openings` / `kind` / `direction` / `wrap` は、
**どれも AI が書いてよい。** 知らない語や壊れた形を書いても、
描画側は既定へ落ちるので**読めない文書にはならない。**

だが**黙って落とすと、書いた側は「効かない」理由が分からない。**
同じ間違いを書き続け、人は図を見るまで気づけない。

| 印 | 何を見るか |
|---|---|
| `node-at-invalid` | `at` が `{ x: 数, y: 数 }` か |
| `node-at-ignored` | **構成図に `at` を書いていないか**（置き場所は機械が決める） |
| `node-size-invalid` | `size` が `{ w: 正の数, h: 正の数 }` か |
| `opening-kind-unknown` | 建具が `door` / `double` / `slide` / `window` / `open` か |
| `opening-side-unknown` | 建具の辺が `top` / `right` / `bottom` / `left` か |
| `opening-ignored` | **構成図に建具を書いていないか** |
| `kind-unknown` | `structure` / `placement` か |
| `direction-unknown` | `right` / `down` か |
| `wrap-not-boolean` | `wrap` が真偽値か（`wrap: "true"` は折り返さない） |
| `grid-axis-invalid` | 通り芯が `{ id: 符号, at: 数 }` か |
| `grid-ignored` | **構成図に通り芯を書いていないか** |
| `scale-missing` | **通り芯はあるが縮尺が無い**（寸法の数値だけが出ない） |
| `scale-invalid` | `scale.mm` が正の数か |
| `north-unknown` | `up` / `right` / `down` / `left` か |
| `wall-invalid` | `wall.mm` が正の数か |
| `wall-needs-scale` | **壁の厚みはあるが縮尺が無い**（太さが変わらない） |
| `radius-invalid` | `radius` が正の数か |
| `radius-ignored` | **構成図に `radius` を書いていないか** |

**どれも `error` にしない。** 弾くと、v1 の「捨てずに保つ」を壊す。

**確かめられないものを、文書の検査で代用しない。**
3〜5 は往復のテストで担保する領域であり、静的な検査で通ったことを
適合の証明にしてはならない。

#### 迷子と、知らないもの

**迷子（規則 3）は失敗ではない。** 人が競合として解くものであり、
検査は見つけて知らせるところまでを行う。
同じく、**知らないキーと知らない体裁の語も失敗ではない**（§9）。
弾くと、v1 の「捨てずに保つ」という規則そのものを壊す。

## 9. 版

- 破壊的な変更は `version` を上げる
- **v1 の読み手は、知らないキーを捨てない。** 捨てると、新しい版で書かれた図を
  古い実装で開いて保存した瞬間に情報が消える
